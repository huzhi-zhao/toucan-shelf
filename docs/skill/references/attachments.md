# 附件

**一句话**：附件是**只读语料**。它们被下载到本地，正是为了让你能**读**；
但你**永不编辑、永不删除、永不移动、永不上传**它们。

---

## 1. 附件是什么，存在哪

附件是挂在某篇文档（memo）上的上传文件：图片、音频、视频、PDF、EPUB、
以及任意非媒体文件。字节存在实例配置的存储后端（本地 / 数据库 / S3-兼容），
和文档正文是两套东西。

memogit 检出时，附件被下载到所属 workspace 的：

```
<workspace>/_attachments/<附件 uid>/<原始文件名>
```

- **单向下载**：`clone` 和 `pull` 把字节拉下来（本地已有未变化的副本则跳过）；
  **`push` 从不上传附件**。你改了 `_attachments/` 里的文件，改动既不会回传，
  也可能在下次 pull 时被覆盖——纯粹的损失。
- 附件**不是**知识库文档，没有 `memogit-id`，不在文档树里。

## 1.1 怎么知道一篇文档有哪些附件

看**文件末尾的 `memogit-attachments` 注释块**，就在 `memogit-id` 那行的上面：

```
<!-- memogit-attachments: read-only, never edited or uploaded.
Paths are relative to the workspace content root, not to this file.
inline:
- 架构图.png (image/png, 240 KB) -> _attachments/d4e5f6/架构图.png
mounted:
- 2024年度报告.pdf (application/pdf, 12.4 MB) -> _attachments/a1b2c3/2024年度报告.pdf
- 原始数据.csv (text/csv, 8.0 KB) -> _attachments/b7c8d9/原始数据.csv
-->
```

没有这个块，就是这篇文档没有附件（或者附件下载失败了，下次 pull 会重试）。

三件要点：

- **路径相对于 workspace 根，不是相对于当前文件。** 文档在 `notes/a/b.md`，
  附件路径仍然是 `_attachments/...` 开头，别拼成 `notes/a/_attachments/...`。
- **`inline` 是正文里用 `![](...)` 引到的**，`mounted` 是只挂在附件区、正文完全没提的。
  这个区分直接影响你怎么判断，见 §3。
- **这个块和 `memogit-id` 一样是本地的**，`push` 时会被剥掉，服务器正文里没有它。
  所以**别编辑它、别删它**——改了不会同步到任何地方，只会让下次 pull 把它覆盖回去。

## 2. 正文里的附件引用

**内联引用（`![](...)`）memogit 刻意不改写**，保持服务器上的原样。
字节下载在 `_attachments/` 里，引用不动。

> **别为了"修好链接"去改写这些引用。** 那会让文件看起来被本地编辑，
> 制造假冲突（`.remote` 副本 + 需要人工合并），而且没有任何收益——
> 服务器端那个引用本来就是对的。

**为什么正文里没有 `![](clip.mp4)` 这种内联音视频**：Markdown 管线用
`rehype-sanitize`，会剥掉手写的 `<audio>` / `<video>` 标签。播放器来自**附件路径**，
不是自定义 Markdown 语法：媒体附件（图片/音频/视频）在预览时渲染在**文档底部**、
带真正可播放的播放器；非媒体附件按文件名列成链接。

编辑器里的行为差异（了解即可，你不参与）：**粘贴**媒体 → 上传并在**光标处**插入
站内 `![](…)` 引用；**工具栏 + → 媒体** → 上传后放进**附件区**（不内联）。
非媒体文件一律进附件区。媒体单文件上限 10 MB。

## 3. 值不值得打开：怎么判断

附件被下载下来就是给你用的，**读是安全的、被鼓励的**，用你正常的文件读取能力就行
（PDF、图片都能直接读）。但"读哪个"要判断——清单只告诉你有什么，判断得你自己做。

### 3.1 直接读，不用犹豫

- **用户点名了。** 让你总结、提取、引用、核对某个附件，直接读。
- **文档是 PDF 文档**（`*.pdf.md`）。那个 `.pdf.md` 只是引用桩，**没有可编辑正文**，
  内容全在 `_attachments/<uid>/xxx.pdf` 里。要理解这篇"文档"讲什么，**必须**去读字节。
- **正文提到了它。** 清单里的文件名或它的主题在正文里出现过，
  或者它是 `inline` 那一组、而那张图正是理解上下文所必需的（图表、截图、示意图）。

### 3.2 文件名看不出内容时，**不要猜**

`IMG_2034.pdf`、`扫描件(1).pdf`、`未命名.png`、`document.pdf`、`新建文档.docx`——
这类文件名不携带任何信息。`mounted` 组尤其容易出现这种：它们在正文里没有任何上下文，
文件名是唯一的线索，而这条线索是空的。

**这时候问用户，不要赌。** 比如：

> 这篇文档挂了 3 个附件，从文件名看不出内容（`IMG_2034.pdf`、`扫描件(1).pdf`、
> `data.xlsx`）。要我打开哪个？

赌错的代价（读了一份不相关的 12 MB 扫描件，然后基于它得出结论）比问一句大得多。

### 3.3 任何情况下，都要说清楚你**没读**哪些

这是最重要的一条。清单是可见的，所以你永远有能力在回答末尾补一句：

> 这篇文档还挂着 `原始数据.csv` 和 `会议纪要.pdf` 我没有打开，需要的话我去看。

**漏读本身不可怕，静默漏读才可怕。** 说出来，用户一句话就能纠正；不说，
他根本不知道你的结论少了一块依据。

### 3.4 也别读过头

一篇挂了二十张截图的文档，全部打开会烧光上下文，还会把不相关的内容混进你的判断。

- 单个附件**超过约 5 MB，先问再开**（清单里有大小，就是给你做这个判断的）。
- 一次任务里**主动打开的附件控制在 3 个以内**；超过这个数，就把清单列给用户让他挑。

多读和少读的代价不对称：少读是答案不完整，用户追问一句就补上；
多读是烧时间和上下文，还可能让你基于不相关的材料得出错的结论。**所以偏保守，靠 §3.3 兜底。**

## 4. 什么时候你**绝不**碰附件

| 动作 | 为什么不行 |
|------|-----------|
| 编辑 `_attachments/` 下的文件 | 单向下载，改动不回传，下次 pull 可能被覆盖 |
| 删除 `_attachments/` 下的文件 | 同上；且这不是"删除服务器附件"的正确方式，只是本地自残 |
| 移动/重命名附件目录 | 目录名是附件 uid，是索引，不是给人看的名字 |
| 编辑 `*.pdf.md` 引用桩 | 生成物，push 忽略它，改它不产生任何效果 |
| 编辑/删除末尾的 `memogit-attachments` 块 | 本地生成物，push 时被剥掉，改它同样不产生任何效果，下次 pull 覆盖回去 |
| 试图"上传"附件 | 未实现（见 `memogit.md` 的限制章节）。需要加附件请让用户在 app 里做 |
| 帮用户"清理没用的附件" | 你看不到全部引用关系（评论、其他文档、分享链接都可能引用），删了不可逆 |

用户要求删附件或换附件时，**告诉他在 app 里操作**，不要自己动本地文件。

## 5. PDF 与 EPUB 的边界

- **PDF 是一种 doc_type**，但由上传的文件字节支撑。本地是 `.pdf.md` 桩 + `_attachments/`
  里的真实 PDF。在 app 里它用 pdf.js 查看器渲染，支持文本层选中、六色高亮/下划线、
  评论侧栏、文本提取。
- **EPUB 不是 doc_type**，就是一个普通附件（`application/epub+zip`）。
  在附件预览页会打开一个 e-reader（翻页/连续滚动、字体、背景、目录、书内批注）。
  阅读外观按书**存在服务端**、跨设备跟随；阅读位置按书缓存。
- 两者的**批注/评论都不在文件字节里**——是所属 memo 的子 comment memo
  （PDF 用页码 + 文本引用锚定，EPUB 用 CFI 锚定）。所以你读到的 PDF/EPUB 字节
  **看不到任何高亮和评论**，而你也无法通过改字节去影响它们。

## 6. 存储与访问控制（背景知识，不需要你操作）

- S3 存储走 **memos 域名代理**，不下发原始预签名 URL：上传和读取都经过服务端签名转发。
  好处是网络隔离、权限统一在 memos 自己的会话模型里、URL 可缓存/走 CDN。
- 附件的可访问性**跟随所属文档的可见性**（PUBLIC 匿名可读 / PROTECTED 需登录 /
  PRIVATE 仅创建者；未挂文档的附件仅创建者可见；归档文档的附件同样收紧）。
- 数据库备份**不含附件**——备份只覆盖 SQLite 数据库文件本身。
  用户问"备份了吗"时不要把附件算进去。

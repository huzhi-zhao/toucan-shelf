# 单机本地部署（standalone local deploy）

## 需求概述

把 ToucanShelf 打包成**一个可执行文件**，让没有服务器的个人开发者能直接在自己的电脑
（典型场景：常年开机的 Mac mini + 局域网访问）上跑起来，数据落本地 SQLite，定期把数据库
快照备份到 S3，图片等附件也走 S3。

目标是把使用成本压到「下载一个文件、双击、打开浏览器」。

## 前置结论：打包这件事今天已经成立

验证过（2026-08-04）：

```bash
CGO_ENABLED=0 go build -o memos ./cmd/memos
```

产出 68MB 单文件，`GOOS=windows` 交叉编译同样通过。原因是两个已有的设计决策：

- 前端已经 `go:embed dist/*`，见 [frontend.go:20](../../../server/router/frontend/frontend.go:20)
- SQLite 驱动是纯 Go 的 `modernc.org/sqlite`，没有 cgo

所以**打包本身零改动**，本计划的工作量不在这里。

## 现状盘点

S3 侧的基础设施大部分已经存在：

| 能力 | 现状 |
|---|---|
| 单可执行文件 | 已成立，见上 |
| S3 客户端 | [internal/storage/s3/s3.go](../../../internal/storage/s3/s3.go) |
| 附件走 S3 | 已有，attachment service |
| DB 备份到 S3 | [server/backup/backup.go](../../../server/backup/backup.go)：`VACUUM INTO` 快照 + gzip + 上传 |
| 定时备份 | [runner.go](../../../server/runner/backup/runner.go)，**间隔硬编码 7 天，且有 bug 导致从未执行过，见 [02-backup-bugs.md](02-backup-bugs.md)** |
| 手动备份 | `BackupNow` API |
| 备份状态 | 记在 `InstanceSetting_BACKUP`，UI 可见 |
| **从 S3 恢复** | **完全没有 —— 备份目前是单向的** |

**本计划的核心就是补上「回来」这半程。**

## 关键决策

### 1. 不引入 Litestream

Litestream 是这类需求的常规答案，这里明确不用：

- 它是独立进程。用它就变成「两个二进制 + 一个 yml」，和单文件目标直接冲突，
  个人用户在自己电脑上部署的体验会崩掉。
- 作为 Go 库嵌入（`benbjohnson/litestream`）技术上可行，但该包 API 从未承诺稳定，
  是给自家 CLI 用的，绑上去是长期维护负担。
- 它的价值是秒级 RPO 和 WAL 增量上传。个人笔记库只有几十 MB，全量传一次几秒钟，
  省下的带宽换不来这份复杂度；而全量单文件快照的恢复逻辑简单到不容易出错。

**改为：复用现有 `VACUUM INTO` 全量快照方案，把备份间隔改成可配（默认 10~15 分钟），
并在进程退出时 flush 一次。**

### 2. 不支持多端，写进文档

原始设想里有「可多端启动」。评估后砍掉。

SQLite + 对象存储备份**只能有一个写者**。两台机器先后启动会这样：

- A 机启动 → 拉最新快照 → 写了一天 → 上传
- B 机启动 → 拉到的是 A 上传前的快照 → 也写 → 上传 → **A 的一天被覆盖**

而且是**静默丢失**，用户收不到任何错误。这比「数据没备份」糟糕得多。

要安全支持多端就必须做 S3 租约（`owner.json` 记录持有者 + epoch，启动时抢占、
后台续期、上传前校验 epoch），约 250 行，且引入一整类新的故障模式。

实际使用场景是单台常开的 Mac mini + 局域网访问，多端的必要性很低。

**决定：不实现租约，README 与首启引导中明确写「同一份 S3 备份只能被一个实例使用，
同时运行多个实例会导致数据丢失」。**

注意这是一条**靠文档约束的规则，没有代码兜底**。如果后续真要支持，租约是唯一正确的
入口，不要试图用「上传前比时间戳」之类的办法糊过去。

### 3. 不强制 S3

原始设想是首次启动强制配置 S3。评估后改掉。

个人用户第一次跑起来就被要求填 endpoint / region / bucket / AK / SK，劝退率会很高，
而这是用户对产品的第一屏。

**改为：允许无 S3 启动，功能完整、纯本地。未配置远程备份时在界面上挂一条持续可见的
警告条：「数据仅存于本机，未配置远程备份」。** 想要异地备份的人自然会去配。

## 本次不实现（明确记录）

以下几项讨论中提到，确认**不在本次范围内**：

- **本地目录备份**：把快照写到本地另一个盘 / 外接硬盘，作为 S3 之外的选项。
  后期可做，引导流程里预留位置。
- **本地图片资源向 S3 迁移**：已有的本地附件批量搬到 S3 的迁移工具。
- **多端 / 租约**：见决策 2。
- **MySQL / Postgres**：本地部署形态只支持 SQLite。

## 需要实现的内容

按重要性排序。第一项是唯一的硬阻塞，其余可以后加。

### A. 启动状态机 + 恢复路径（核心，约 400 行）

启动时从 S3 拉取最新快照并恢复。**这是 bug 密度最高的地方**，因为它要区分几种表面
相似、后果截然不同的情况：

| 本地 DB | 远端 | 网络 | 行为 |
|---|---|---|---|
| 无 | 确认为空（ListObjects 返回 0） | 通 | 初始化新库 |
| 无 | 有快照 | 通 | 下载 + 解压 + 校验，恢复 |
| 无 | 未知 | **不通 / 凭证错 / bucket 不存在** | **硬失败退出** |
| 有 | 任意 | 任意 | 直接用本地，不拉取 |

**最关键的一行代码**：只有在「本地无 DB」**且**「远端确认为空」时才初始化新库。把网络
故障误判成首次部署会建一个空库，然后下一轮备份把 S3 上的真数据覆盖掉。任何其他情况
一律退出并打印明确原因。

未配置 S3 时整段跳过，走纯本地。

### B. 备份频率可配 + 退出 flush（约 80 行）

**前置：先修掉 [02-backup-bugs.md](02-backup-bugs.md) 里的两个 bug**，否则这里改的间隔
不会有任何效果——现在的 runner 根本不触发。

- `runnerInterval` 从硬编码 7 天改为可配置，本地部署默认 10~15 分钟。
- 进程收到退出信号时同步跑一次备份再退出。

笔记本合盖休眠、系统更新重启是常态，不能指望每次都优雅退出，所以定时间隔要短
——间隔就是最坏情况下的数据丢失窗口。

### C. 首启引导 UI（约 300 行前端）

首次启动创建管理员账号，之后**可选**引导配置 S3。跳过则显示未备份警告条。

### D. 打包 CI（约半天）

GitHub Actions matrix：darwin arm64 / darwin amd64 / windows amd64 / linux amd64。

## 凭证与快照安全

### 快照无法被"清洗"

S3 凭证明文存在 `InstanceSetting` 里，而这个 DB 要被上传到 S3 —— 凭证跟着备份传上去了。

但**「备份前剔除 S3 凭证」是个假解法**，不要做。快照里的敏感数据远不止 S3 key：

- **PAT**（个人访问令牌），明文 —— [user_setting.go:224](../../../store/user_setting.go:224)
- **IdP OAuth client secret**，明文 —— [idp_bootstrap.go:139](../../../store/idp_bootstrap.go:139)

擦掉 S3 key，PAT 还在；擦掉 PAT，IdP secret 还在；全擦掉备份就不能用于恢复了。

**正确的前提：数据库快照本质上是一个全权凭证，不可能通过清洗降级。谁拿到快照 =
谁拿到整个实例。** 按这个前提设计和写文档。

### standalone：凭证走环境变量（结构上的必然，不只是安全考虑）

关键点：**恢复的时候 DB 还不存在 —— DB 正是要恢复的东西。** 不可能从一个尚未存在的
数据库里读出连接 S3 所需的凭证。这是死循环，与安全无关。

所以 standalone 模式下 S3 凭证**只能**来自环境变量：

```
TOUCAN_S3_ENDPOINT / _REGION / _BUCKET / _ACCESS_KEY_ID / _ACCESS_KEY_SECRET
```

副产品是 `InstanceSetting` 里那几个字段留空，快照天然不含 S3 密钥 —— **剔除逻辑是
零行代码**。

现有的界面配置路径保留给 docker 部署，env 存在时优先，不破坏老用户。

### 线上（docker）：靠权限收敛，不靠代码

线上仍从 DB 读凭证，env 方案救不了。已确认采用这两条：

1. **Access Key 权限锁死在单个 bucket**（附最小权限 IAM 策略，零代码，收益最高）
2. **确认 bucket 为私有**

做完这两条风险即回到可接受：备份里的 key 只能访问它自己所在的 bucket，
而能读到备份的人本来就已经在那个 bucket 里了。

### 风险告知

以上内容需向用户明示，已写入面向用户的文档：
[docs/manual/11-backup-and-storage.md](../../manual/11-backup-and-storage.md)。

要点：备份文件等同于账号本身，不可分享、不可放入自动同步目录、恢复后删除本地副本。

## 验收测试

用现有测试环境那批开发过程中积累的文档做端到端演练。**跑一遍「备份 → 恢复」不算通过**，
必须覆盖：

1. 首次启动，bucket 为空 → 建新库
2. 首次启动，bucket 有数据 → 恢复后文档数、附件数、文件夹树对得上
3. **拔网线启动 → 必须拒绝启动，绝不能建空库**（最关键的一条）
4. 备份中途 `kill -9` → 远端快照不能损坏（半个文件不能顶掉好文件）
5. 未配置 S3 → 正常启动，警告条可见
6. 恢复后 FTS 索引与 memogit 状态一致

第 6 条需要单独确认：`memo_chunk` 表里的全文/向量索引是否完整包含在 `VACUUM INTO`
快照中、恢复后能否直接使用，还是需要重建。这一点目前没有验证过。

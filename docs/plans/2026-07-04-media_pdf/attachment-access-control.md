# 附件访问控制与私密附件

两件事放在一篇里：**A. 让附件的可见性严格等同于所属文档**（修补残留缺口），**B. 私密附件**——
在文档可见性之上再加一道口令闸门，未解锁就取不到文件，文档公开也不外泄。

A 是修 bug，B 是新功能。B 的判定要挂在 A 收敛出来的那一个函数上，所以先 A 后 B。

---

## 一、现状调研

### 结论先行：「任何人都能下载非公开文档的附件」这条，主干上已经不成立

两条访问路径都已经在按文档可见性判定：

| 路径 | 判定函数 | 位置 |
| --- | --- | --- |
| 二进制下载 `/file/attachments/:uid/:filename` | `checkAttachmentPermission` | [fileserver.go:640](../../../server/router/fileserver/fileserver.go) |
| 元数据 `AttachmentService/GetAttachment` | `checkAttachmentAccess` | [attachment_service.go:836](../../../server/router/api/v1/attachment_service.go) |

规则都是：未挂文档 → 仅创建者/管理员；PUBLIC → 匿名可读（且实例本身允许匿名）；
PROTECTED → 需登录；PRIVATE → 仅创建者/管理员。另有 share token 兜底，且校验 token 与
memo 一一对应（[fileserver.go:674](../../../server/router/fileserver/fileserver.go)）。

历史上确实存在过「谁拿到链接谁能下载」的形态：S3 附件当年把 MinIO 预签名 URL 当
`external_link` 直接下发给浏览器，5 天内脱离 memos 权限体系。这条已经改掉了，现在只有
`EXTERNAL` 存储类型（用户自己粘的外链）才下发原始 URL，S3 一律走 `/file/` 代理
（[attachment_service.go:541](../../../server/router/api/v1/attachment_service.go) 的注释即为此事的落点）。

所以**需求 1 不是从零做，是补齐下面四个残留缺口**。如果你观察到的是别的现象（比如某个具体
文件退出登录后仍能下载），请把 URL 和文档可见性给我，那会是第五条，需要单独定位。

### 残留缺口

**缺口 1 · 归档文档的附件仍可下载。**
`checkMemoReadAccess` 明确规定归档（回收站）文档只有创建者可见
（[memo_service.go:70](../../../server/router/api/v1/memo_service.go)），但两个附件判定函数都
只看 `Visibility`、不看 `RowStatus`。一篇 PUBLIC 文档删进回收站之后，正文取不到了，附件还在。

**缺口 2 · 不继承父文档可见性。**
`GetMemo` 读子文档时会连父文档一起校验
（[memo_service.go:436](../../../server/router/api/v1/memo_service.go)），附件判定不会。
评论的可见性在创建时是强制继承父文档的（`memo_service.go:828`），子文档在
**更新**时会被拉齐（`:598-608`），但**创建**时用的是请求里带的值（`:118`）。于是可以造出
「PRIVATE 父文档下挂一篇 PUBLIC 子文档」—— 子文档正文因为父校验而打不开，它的附件却能下。

**缺口 3 · 两处判定是两份代码。**
`fileserver` 与 `api/v1` 各写了一遍等价逻辑，已经在归档这一条上漂移了。缺口 1、2 修完还会
继续漂移，除非合并成一个函数。B 部分要加的口令闸门如果也写两遍，漂移的后果就是私密附件
在某条路径上形同虚设。

**缺口 4 · 缩略图缓存不复判。**
`/file/...?thumbnail=true` 的缓存文件按 attachment uid 落在 `Data/.thumbnail_cache`
（[fileserver.go:452](../../../server/router/fileserver/fileserver.go)），不对外暴露路径，
目前不构成漏洞。B 部分要留意它是一份**脱离原文件存在的派生副本**。

### 会被私密附件波及的旁路

每一条都要显式处理，漏一条就是绕过闸门：

| 旁路 | 位置 | 处理 |
| --- | --- | --- |
| RSS enclosure | [rss.go:288](../../../server/router/rss/rss.go) | 只列 PUBLIC 文档，仍需排除私密附件 |
| share token 通路 | fileserver + `memo_share_service.go:175` | 私密附件一律不走 |
| memogit 推送附件字节 | [internal/memogit/attachments.go](../../../internal/memogit/attachments.go) | 跳过下载，留占位说明 |
| MCP / PAT 令牌 | `server/auth` | 不授予解锁态，Agent 拿不到私密附件 |
| 缩略图 / motion clip | fileserver | 派生副本同样受闸门管辖 |

## 二、A 部分：让附件可见性等同文档

### 方案

把判定合并成**一个**函数，两处调用：

```go
// server/auth 或 server/router/shared
func CheckAttachmentReadAccess(ctx, stores, attachment, viewer, opts) error
```

判定顺序（任何一步拒绝即终止）：

1. **私密闸门**（B 部分填充，先留出位置）。
2. `attachment.MemoID == nil` → 仅创建者 / 管理员。
3. 取所属 memo；**沿 `ParentUID` 向上取到根**，对链路上每一篇都套用 4、5 两条。
   深度设上限（如 16 层）并对环做保护，避免坏数据打成死循环。
4. `RowStatus == Archived` → 仅创建者。
5. PUBLIC 且实例允许匿名 → 放行；否则要求登录；PRIVATE → 仅创建者 / 管理员。
6. share token 有效且指向链路上的目标 memo → 放行。

`fileserver` 与 `api/v1` 的差别只剩两处，作为参数传入：前者要 `Profile.AllowAnonymous()`
（私有实例对匿名一律关门），后者的用户来自 Connect context 而非 header。

顺带把子文档创建时的可见性也拉齐：`CreateMemo` 在 `ParentUID != nil` 时按父文档取值，
与 `UpdateMemo` 现有行为一致。这是缺口 2 的另一半——只补下载侧不补写入侧，等于允许用户
造出一篇「自己看着是公开、实际打不开」的文档。

### 验收

Go 测试，落在 `fileserver_test.go` 与 `attachment_service` 测试里，每条缺口一个用例：
归档文档附件对非创建者拒绝；PRIVATE 父 + PUBLIC 子的附件对他人拒绝；share token 仍能
取到目标文档的附件；既有用例不回归。

### 风险

**这是一次收紧，会打断现存的外链使用。** 曾经把 PUBLIC 文档的附件链接发给别人、之后把文档
删进回收站的场景，链接会立刻失效——这正是期望行为，但如果实例上有人这么用，是可感知的变化。
建议在 CHANGELOG 里点名。

## 三、B 部分：私密附件（平台侧口令闸门）

### 先把威胁模型讲清楚，因为它决定了这个功能值多少钱

**文件在存储端（本地磁盘 / S3 / MinIO）原样保存，不加密。服务端持有明文。**
口令只决定「能不能通过 ToucanShelf 读到和下载」。

这句话展开的后果必须在 UI 上如实写出来，否则用户会以为自己得到了保险箱：

**挡得住：**

- 同实例的其他登录用户（含管理员——只要闸门也拦管理员）
- 文档设为 PUBLIC 后的匿名访客、share token 链接的接收者
- 会话被顺走的情况：偷到 cookie/PAT 也只是普通登录态，私密附件还要再过一道口令
- 无人看管的浏览器：会话上锁后，坐到你电脑前的人打不开
- MCP / Agent 令牌：不授予解锁态，AI 读不到

**挡不住：**

- 服务端本身。运维者、拿到服务器 shell 的人、拿到 S3 凭据的人，直接读文件即可
- 存储桶配置失误（bucket 误设为 public-read）——闸门在 ToucanShelf 里，绕开 ToucanShelf 就绕开了闸门
- 数据库/磁盘备份的持有者

一句话：**这是「别人在我的平台上看不到」，不是「别人拿不到」。** 与
[加密块](../2026-07-30-secret-block/requirement.md)（服务端全程不持有明文）是**两个不同的
安全等级**，UI 上的措辞必须区分开，不能都叫「加密」。建议私密附件的文案统一用「锁定 / 保险箱」，
把「加密」这个词留给密文块。

真需要「服务端也看不到」的文件，本期的答案是：把它做成密文块（贴文本）或干脆别传上来。

### 关键决策 1：复用账号主口令，不引入第二把

用密文块已有的那把账号主口令，不再单设附件口令。用户已经有一把了，再来一把是纯粹的成本
转嫁：同一篇文档里密文块和私密附件要输两次、跑两遍百万级 KDF。

难点在于**服务端要能验口令，但服务端不知道口令，也不知道主密钥 MK**——现有设计里
`user_setting` 只存 MK 的包装信封，解包全在浏览器闭包里
（[secret-session.ts](../../../web/src/utils/secret-session.ts)）。

解法：**客户端出示 MK 的持有证明，服务端比对一个预存的校验值。**

```
verifier = HMAC-SHA256(MK, "toucan-attach/unlock/v1")   ← 存 user_setting，服务端可见
解锁时：客户端本地解包出 MK → 算出同一个 verifier → 发给服务端比对
```

服务端因此永远看不到口令，也拿不到 MK（verifier 是单向的）。首次启用私密附件时把
verifier 写进去，一次性的。

被放弃的方案，记录在此以免重复讨论：

- ~~服务端直接存口令的 PBKDF2 哈希~~ —— 那等于给主口令开了第二个校验入口，且和密文块的
  KDF 参数是两套，改口令时要同步两处，漏一处就是「改了口令旧的还能开」。
- ~~不验口令，只按创建者放行~~ —— 那就退化成「私密 = 仅自己可见」，不需要口令这个概念。
  口令的全部价值在于**把会话态和解锁态分开**：偷到 session 不等于拿到文件。

**注意 verifier 的暴露面**：它是 `HMAC(MK, 固定串)`，拿到它无法反推 MK，但拿到数据库的人
本来就同时拿到了 MK 的包装信封（1.2M 次 PBKDF2），爆破成本由后者决定，verifier 不额外降低
强度。

### 关键决策 2：解锁态是一枚短时 cookie，不是每次请求带参数

解锁成功后服务端签发一枚 **httpOnly + Secure + SameSite=Lax 的 vault cookie**
（JWT：user_id / purpose / exp，用实例密钥签名，TTL 30 分钟、滑动续期）。
`/file/` 判定私密附件时校验这枚 cookie。

选 cookie 而不是「URL 带 token」或「JS 手动加 header」，理由是它**顺带解掉了原方案里最难受
的两个边界**：

- **内联媒体 `![](/file/...)` 能用了。** markdown 渲染器直接把 URL 交给浏览器加载，
  中间没有插 JS 的位置——但浏览器会自动带 cookie。私密图片可以正常内联显示。
- **视频/音频能流式播放了。** `<video src>` 的 range 请求同样自动带 cookie，
  `serveMediaStream` 那条路不用动。

（这两条在「端到端加密」方案里都是做不到的，需要 Service Worker 拦截才有戏。这是本次口径
调整最大的一笔收益，比省下来的加解密代码更值钱。）

SameSite 选 Lax 而非 Strict：下载走的是顶层导航，Strict 在部分跨站跳转回来的场景会丢 cookie。
Lax 对本功能足够——闸门要防的不是 CSRF，而且这些请求全是同站的。

上锁 = 清 cookie + 清前端解锁态。三种情况自动上锁，与密文块一致：闲置超时、登出、清 token。
**上锁必须真的把已展开的私密预览关掉**，不能只是按钮变个样子。

### 关键决策 3：私密是附件级属性，「整区私密」只是批量操作

`AttachmentPayload` 加一个字段：

```proto
message AttachmentPayload {
  // ...既有字段...
  // locked 标记该附件需要通过 vault 解锁才能读取。文件本身不加密，
  // 闸门只在 ToucanShelf 的访问路径上生效。
  bool locked = 13;
}
```

**不引入「附件区私密」这个独立状态位。** 那会造成「区是私密但里面某个文件不是」的矛盾态，
且新加进来的文件是否自动私密没有正确答案。UI 上的「整个附件区设为私密」按批量操作实现，
逐个打标，进度可见，失败的单独列出。

好处是「设为私密」变成一次纯元数据更新——不搬文件、不重新上传、不改 URL、正文里的引用
不用动。取消私密同理。这与端到端方案（必须重新上传密文、替换引用、删除旧文件，中途失败
留下半状态）相比是决定性的简化。

### 服务端改动

1. **判定**：`CheckAttachmentReadAccess` 第 1 步——`payload.locked` 为真时：
   必须 `creator_id == 当前用户` **且**携带有效 vault cookie。
   share token / 匿名 / PUBLIC 全部不适用，**管理员也拒绝**。
   （管理员在服务器上直接读文件当然可以，但那是另一条路径；平台接口不该替他开门。）
2. **派生物同样受管**：`thumbnail=true` / `motion=true` 走同一个判定。缩略图缓存文件本身
   是明文副本，落在 `Data/.thumbnail_cache`——可接受（原文件也是明文），但要在文档里记一笔，
   免得将来有人以为删了原文件就干净了。
3. **响应头**：私密附件加 `Cache-Control: no-store, private`，不落浏览器磁盘缓存，
   避免上锁后从 cache 里还能翻出来。
4. **旁路封堵**：RSS enclosure 跳过；memogit 的 `downloadMemoAttachments` 跳过并在
   `_attachments/` 下写占位说明（让 clone 的人知道这里有东西而不是数据丢了）；
   `ListAttachments` 一类批量接口正常返回元数据。
5. **令牌来源限制**：vault cookie 只在浏览器会话链路上签发。PAT / MCP 令牌的请求即便带上
   cookie 也不认——判定时要求「当前认证来自 session」。这条要写成显式检查，不能靠
   「PAT 用户不会有 cookie」这种间接推理。
6. **限速**：解锁接口按用户限速（例如 5 次 / 分钟），失败计数落库。verifier 比对本身是
   常数时间的（`hmac.Equal`），但不限速等于允许在线爆破 verifier 的输入空间。

新接口（都要登录，都不进 `PublicMethods`）：

```
AttachmentService/UnlockVault(proof) → 校验 verifier，Set-Cookie
AttachmentService/LockVault()        → 清 cookie
UserService  一处存/取 verifier（首次启用时写入）
```

Set-Cookie 走 `SetResponseHeader(ctx, "Set-Cookie", ...)`，与
[auth_service.go:383](../../../server/router/api/v1/auth_service.go) 签发 refresh token 同一个机制。

### 前端改动

- 附件卡片菜单加「设为私密 / 取消私密」；附件区标题栏加批量入口。
- 锁定态：卡片显示 🔒 与文件名，**不发起对文件本身的请求**，缩略图位置显示占位图。
  点一下 → 未解锁则弹口令框（复用密文块那套 `MaskedInput` 与解锁流程）→ 解锁后正常显示。
- 解锁后页面上的私密附件整体恢复（图片显示、视频可播、下载可点），因为闸门在 cookie 上，
  不需要逐个处理。
- 上锁时（手动、超时、登出）必须触发一次重渲染，把已加载的私密图片/视频从 DOM 里摘掉。
  已经加载进内存的那一份拦不住，但不能留在界面上。
- 首次启用要走一次「设置主口令 / 写入 verifier」的引导；已经在用密文块的用户直接复用。

### 文件名是否隐藏

服务端本来就知道文件名，隐藏只是 UI 层面的事，不是安全边界。但「离职协议.pdf」这种文件名
本身就是泄露源，在**别人看到你屏幕**这个场景下遮起来是有意义的。

建议：锁定态显示为「🔒 私密附件 · 2.3 MB」，鼠标悬停/解锁后显示真名。实现成本很低，
且明确标注为「显示层遮挡，非安全边界」。这条待你拍板。

### 手工验收清单（B3 之后，需你实机走一遍）

1. 未解锁时打开含私密附件的文档：DevTools Network 里**没有**对该文件（及其缩略图）的请求。
2. 解锁后：图片正常显示、视频能拖动播放、下载得到与上传前一致的文件。
3. 把该文档设为 PUBLIC，无痕窗口打开：正文可见，私密附件 403；直接敲
   `/file/attachments/<uid>/...` 同样 403。
4. 生成 share token 分享，无痕打开：同上。
5. 用另一个账号（含管理员账号）登录：403。
6. 已解锁状态下，用 PAT 调 `/file/...`：403（验证令牌来源限制真的生效）。
7. 等待闲置超时 / 手动上锁：页面上的私密图片消失，再次访问需要重新输口令；
   刷新页面后同样是锁定态。
8. 上锁后按浏览器后退：图片不能从 bfcache/磁盘缓存里复现（验证 `no-store` 生效）。

### 风险与已知局限

1. **最大的风险是措辞。** 用户很容易把这个功能理解成「文件被加密了」。文案、手册、
   设置项说明三处都要写明「文件在服务器上原样保存，此功能限制的是通过本平台的访问」。
   这一条比任何技术细节都重要——理解错了会导致用户把真正不该上传的东西传上来。
2. **S3 桶配置是闸门之外的洞。** 如果 bucket 允许公开读、或预签名 URL 从别处泄露，
   私密标记毫无作用。文档里要点名要求 bucket 关闭公开读。
3. **备份包含明文。** 数据库备份 + 附件存储，任一持有者都能拿到私密文件。
4. **解锁期间与普通附件无异。** 30 分钟窗口内，任何能操作这个浏览器的人都能拿到文件。
   超时时间可配，但默认值要偏短。
5. **缩略图缓存是脱离原文件的明文副本**，删除原附件时要一并清掉（现有代码是否清理需在
   B1 时确认；如果没清，那是个既有的小问题，顺手补上）。

## 四、待你拍板

1. **管理员是否拒绝**。方案里是拒绝（他能从服务器直接读，但平台接口不替他开门）。
   如果实例上有「管理员需要能导出所有原始文件」的运维需求，这条要另议。
2. **锁定态是否遮挡文件名**。我倾向遮挡并明确标注为显示层遮挡，成本很低。
3. **解锁 TTL 默认值**。我倾向 30 分钟滑动续期，与密文块的闲置上锁对齐。你如果主要在
   自己的机器上用，可以放宽到 2 小时。
4. **首次启用的引导**：没用过密文块的用户需要先设主口令。是做成独立的「安全设置」页，
   还是在第一次点「设为私密」时就地引导？我倾向就地引导。
5. **A 部分是否单独发一版先上线**——它是安全修复，不该等 B 做完。

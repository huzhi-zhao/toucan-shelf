# 附件对象迁移与存储后端锁定

附件的字节存在哪、用什么 key 存，是**运维可以改变的事实**；而附件在产品里的
身份（URL、权限、所属文档）不能因此改变。这篇写清楚两者的边界，以及为此
必须提供的迁移能力。

方案怎么落地见 [../../design/20260826-attachment-object-migration.md](../../design/20260826-attachment-object-migration.md)。
同域另两篇：[sqlite-as-sole-datasource.md](sqlite-as-sole-datasource.md)（数据源边界）、
[backup.md](backup.md)（全站备份，与本篇共用同一份 S3 配置但路径模板独立）。

## 1. 要解决的两件事

**一、桶和根路径要能换。** 换云厂商、换 bucket、把附件从 `assets/` 挪到别的
前缀，这些是正常的运维动作，不应该等价于"丢数据"或"重传一遍"。当前实例的
S3 配置改掉之后，读附件用的是新配置（见 §5 的既有事实），但**没有任何机制
把对象本身搬过去**——改完配置就是全站附件 404。这是一个能力缺口，不是 bug。

**二、旧附件没有知识库目录。** 附件路径模板加入 `{workspace}` 之后
（默认 `assets/{workspace}/{timestamp}_{uuid}_{filename}`），只有新上传的附件
落进了以知识库 slug 命名的目录，此前上传的仍平铺在 `assets/` 下。这是一笔
明确的技术债：当初只改了写入路径，没有处理存量。

两件事表面不同，本质是同一件——**把每个附件挪到"按当前配置它本该在的位置"**。
因此只提供一个迁移能力，不做两套。

## 2. 三条承诺

**承诺一：迁移不改变附件的对外 URL。** 附件地址是 `/file/attachments/{uid}/{filename}`，
从 UID 派生，与 S3 key 无关。迁移之后浏览器里的链接、文档正文里的
`![](...)`、已发布站点上的引用**全部原样有效**，不需要任何重写或重定向。

**承诺二：迁移过程中附件始终可读。** 不接受"迁移窗口期图片打不开"。达成方式是
迁移的语义为**复制 + 改指针**：先把对象复制到新位置，确认没问题再改数据库
里的指针。改之前读旧位置，改之后读新位置，两个位置在整个过程中都有对象。

**承诺三：迁移可以重复跑。** 中断、失败、只迁了一半，直接再跑一次即可，
已经在位的跳过。不需要人去判断"上次跑到哪了"。

## 3. 迁移不删源，这是产品事实不是偷懒

迁移**只复制、不删除**源对象，跑完之后同一份字节在桶里存在两份（换桶时是
两个桶各一份）。旧对象的清理不由本能力负责，交给运维：

- 换桶或换根路径：确认新位置一切正常之后，**手动整桶/整前缀删除**。
- 原地补目录（技术债那件事）：旧对象散落在 `assets/` 根下，跟新对象混在同一个
  桶里，**配 S3 生命周期规则按前缀清理**，或长期留着不管（量很小）。

理由：删除是唯一不可回滚的一步，而这个能力的全部价值在于"改错了能退回来"。
把删除留给人，等于把不可逆的决定留给人。

**这条必须在执行迁移前明确告知使用者**，否则会出现"迁完发现桶里体积翻倍"
的意外——见 [../../launch/20260826-attachment-object-migration.md](../../launch/20260826-attachment-object-migration.md) 的前置准备。

## 4. 存储后端不可中途切换

**一个实例要么全本地、要么全 S3，不存在两种存量并存的状态。** 设置页里的
"附件存储"下拉当前可以随时切换，切完之后：老附件按各自记录的 `storage_type`
继续从原后端读，新附件写新后端。这看起来"很灵活"，实际是一个陷阱——实例
处于混合状态，备份、迁移、容量核算全都要按两套路径讨论，而这个灵活性没有
任何人真的需要。

**因此：当实例里已存在某种后端的存量附件时，拒绝切换到另一种后端。**
要切必须先把存量迁过去。错误信息要说清楚"有多少个附件卡在哪种后端"，
而不是只说一句不允许。

外链附件（`EXTERNAL`，reference 是一个 URL）不参与这个判定——它的字节
本来就不在本实例手里。

**本期只实现 S3 → S3 的迁移**（换桶、换根路径、补知识库目录）。本地 ↔ S3
的迁移理论上应该支持，但当前实例全部附件都在 S3、且只有一个使用者，
没有真实场景，不实现。**锁定规则先于迁移能力落地**：宁可暂时"切不过去"，
也不要允许制造出一个没人能收拾的混合实例。

## 5. 事实依据（写方案前必须知道的现状）

这几条决定了上面的承诺能不能兑现，都可以通过读代码证伪：

- **URL 与 key 解耦**：`/file/attachments/:uid/:filename`
  （[fileserver.go](../../../../server/router/fileserver/fileserver.go)），S3 附件的
  `external_link` 刻意留空，所有读取走服务端代理（见
  [adr/0001](../../adr/0001-attachment-proxy-not-presigned-url.md)）。站点公开域名只由
  `.env` 的 `MEMOS_INSTANCE_URL` 提供，不进入附件记录。
- **key 存两处**：`attachment.reference` 字段与 `payload.s3_object.key`。
  实际读取只用后者，前者目前没有读取方，但仍须一并更新，否则两处不一致。
- **附件只记录对象 key，不记录 S3 配置。** endpoint、bucket 和凭证只保存在实例级
  `STORAGE` 设置中；`Store.ResolveAttachmentS3Config` 从该设置统一解析。
  旧版本写入 `payload.s3_object.s3_config` 的快照仅用于兼容尚未完成的迁移，
  `migrate-attachments --apply` 在对象成功就位后会将其删除。
- **缩略图与 motion 缓存按附件 UID 命名**（`.thumbnail_cache/{uid}.jpeg` 等），
  与存储路径无关，迁移不需要动它们。
- **数据库备份用同一份 S3 配置但独立的 `path_template`**，不在本能力范围内。
- **规模**：当前生产实例约 2000 个附件。这个量级下不需要并发、分片、断点续传，
  串行跑完即可——任何为吞吐做的复杂度都是纯负债。

## 6. 明确不做

- **S3 → 本地的迁移**（§4，无场景）。
- **多桶并存 / 按知识库分桶**：一个实例一个桶，路径前缀足够表达分组。
- **迁移过程的图形界面与进度条**：这是运维动作不是产品功能，命令行足够。
- **重命名文件本身**：迁移只改目录前缀，文件名那一段（`{timestamp}_{uuid}_{filename}`）
  原样保留。改文件名不产生任何价值，还会让"同一个附件"在两次迁移里算出
  不同结果，破坏承诺三。
- **自动触发**：不做定时任务、不做"检测到配置变化自动迁移"。迁移必须是人
  显式发起的动作。

## 7. 验收判据

- 改掉桶名 → 跑迁移 → 所有附件仍可正常打开，且 URL 一个都没变。
- 迁移前打开的页面，在迁移过程中刷新，图片不出现 404。
- 同一次迁移连续跑两遍，第二遍报告"全部已在位"，S3 里不产生第三份对象。
- 旧附件迁完后，其对象位于 `assets/<知识库 slug>/` 下；未挂到任何文档的
  孤儿附件位于 `assets/_unassigned/` 下。
- 实例里有 S3 存量附件时，在设置页把存储切成"本地"或"数据库"被拒绝，
  且提示里写明了存量数量。

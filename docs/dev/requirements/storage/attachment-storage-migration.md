# 附件存储迁移：换源、换桶、换根目录

> 技术方案见
> [design/20260902-attachment-storage-migration.md](../../design/20260902-attachment-storage-migration.md)。
> P0～P3 已全部实现，但**尚未在真实 S3 上端到端验证**。

## 一句话目标

让管理员能把附件的 S3 落点整体换到另一处——**换源**（endpoint + 凭证）、**换桶**、
**换根目录前缀**，三级任意组合——由服务把已有对象搬过去并改写映射，**全程不改变任何
附件的对外 URI**。旧位置的对象原样留着，由管理员自己核对无误后手动删除。

顺带把一个历史遗留一起收掉：早期上传的附件平铺在桶根，没有按知识库分目录
（见 [upload-and-inline-media.md §S3 附件按 workspace 分目录](../attachments/upload-and-inline-media.md)），
既然要逐条重算 key，就在同一趟里把它们归位。

## 为什么现在做不到

五条已核实的现状。前两条是缺口，第三条是**已经存在的坑**——即使不做迁移也该修。

### 1. 换桶会让全站附件立刻 404

[store/attachment.go:214](../../../../store/attachment.go) 的 `ResolveAttachmentS3Config`
规则是：只要实例当前的存储类型仍是 S3，就一律用**实例当前的** S3 配置，只有实例不再是
S3 时才回落到附件自己 payload 里的快照。读路径（[fileserver.go:431](../../../../server/router/fileserver/fileserver.go)、
[attachment_service.go:853](../../../../server/router/api/v1/attachment_service.go)）和删除路径
（[store/attachment.go:287](../../../../store/attachment.go)）都走它。

这个设计对"换凭证、换 region"是对的——同一份数据换个连接方式，所有附件跟着走。
但对"换 endpoint / 换桶 / 换前缀"是错的：对象没跟着走，key 却被拿去新位置找，结果是全站
老附件同时 404，且**没有任何提示**。当前 UI 也不拦——[StorageSection.tsx](../../../../web/src/components/Settings/StorageSection.tsx)
的 bucket 就是个普通输入框，改完点保存即生效。

换 endpoint 有两种完全不同的情况：同一份数据换个访问地址（MinIO 换域名、内外网地址切换），
和真的换成了另一份存储。**系统分不出来**，凭 URL 无从判断背后是不是同一个桶。因此把
endpoint 归入"位置"，与 bucket、root_prefix 一起管——三者任意一个变了都必须走迁移。
"其实是同一份数据"的那种情况走迁移也几乎不花钱：搬运是幂等的，逐条先看目标位置有没有，
有且大小一致就跳过，整趟下来只是一遍 `StatObject`。

因此本需求的第一条产出不是"迁移功能"，是**让换桶这件事从"静默炸掉"变成"必须走迁移流程"**。

### 2. 根目录前缀不是一个独立概念

现在只有一个 `filepath_template`（[instance_setting.proto:108](../../../../proto/store/instance_setting.proto)），
默认值 `assets/{workspace}/{timestamp}_{uuid}_{filename}`
（[store/instance_setting.go:265](../../../../store/instance_setting.go)），把三件事揉成一个字符串：
根目录（`assets/`）、知识库分目录（`{workspace}`）、文件名规则。用户可以把它改成任意形状，
包括把 `{workspace}` 删掉。

"换根目录前缀"要成为一个可以单独表达的动作，前缀就得从模板里拆出来。同时，中间那段
知识库目录**不应该继续留给用户改**——它是迁移和归位逻辑的基准，用户改一下就没有基准了。

### 3. 历史平铺的那批附件

`{workspace}` 占位符是后加的，改动之前写入的对象平铺在 `assets/` 下。当时的结论是
**不做统一搬迁**、新旧混存不影响访问，只打算搬个别重要知识库，脚本先出只读清单
（[upload-and-inline-media.md](../attachments/upload-and-inline-media.md)）。
代码库里找不到这个脚本，`TODO.md` 里原本挂着一条"是否已执行"的待确认项——现已核实
**它从来没写出来，也不必再单独写了**：本需求逐条重算 key，平铺附件的归位是免费搭车的，
那条待确认项随本篇一并注销。

### 4. 没有任何"迁移中"的状态

实例设置里只有一份 S3 配置，没有"目标配置"的位置；服务没有维护模式、只读开关或写入闸门；
附件的读路径也没有"这条已经搬完了、那条还没搬"的概念。这三样都得新建。

### 5. S3 客户端只有四个方法

[internal/storage/s3/s3.go](../../../../internal/storage/s3/s3.go) 只有 `UploadObject` /
`GetObject` / `GetObjectStream` / `DeleteObject`。**没有 Copy**——同一个 endpoint、同一套凭证下
换桶或换前缀，本来可以让 S3 自己做服务端复制，一个字节都不用经过 Toucan；**也没有 List**——
迁完之后想确认"新位置真的都在"、或者想知道旧桶里有多少个数据库里没有记录的孤儿对象，
现在都做不到。

## 产品边界

### 搬运，不接管

迁移只动 Toucan 自己写进去的对象。桶里其它东西（别的应用的数据、手工放进去的文件）不读、
不动、不统计。判定依据是**数据库里的附件记录**，不是对桶的扫描——扫描只用于事后对账。

### 不删旧数据，一次都不删

迁移全程不调用 `DeleteObject`。搬完之后旧位置的对象完整保留，由管理员自己确认新位置能正常
访问之后，去 S3 控制台手动清。理由是这类操作的错误代价不对称：多留一份垃圾的成本是存储费，
删错一份的成本是数据没了。

推论：**"回滚"是免费的**。既然旧对象还在，放弃一次迁移只需要把数据库里的 key 映射改回去，
不涉及任何数据搬运。

### 是管理员的运维操作，不是产品功能

入口在实例设置里，只有管理员看得见。不做进度推送、不做多任务并行、不做"给某个知识库单独换桶"。
一次只跑一个迁移。

### 只覆盖 S3 → S3

本期不做 `LOCAL → S3`、`S3 → LOCAL`、`DATABASE → 任意`。它们是有价值的（尤其是本地盘上云），
但读路径要同时处理两种引用形态，是另一个规模的改动。方案在数据模型上不给它们挖坑，仅此而已。

## 存储路径的三级模型

对象 key 定义为三段拼接：

| 段 | 谁定 | 用户能改吗 | 当前值 | 说明 |
|---|---|---|---|---|
| **根目录前缀** | 管理员 | 能 | 从旧模板里提取，通常是 `assets` | 新字段 `root_prefix`。**默认空**，即直接落在桶根下。这是迁移的第三级配置 |
| **中间路径** | 系统 | **不能** | 知识库的 `storage_slug` | 由 Toucan 内定。用户无权修改——它是归位与对账的基准 |
| **文件名** | 管理员 | 能 | `{timestamp}_{uuid}_{filename}` | 模板降级为**只管文件名**，不再能表达目录 |

也就是 `{root_prefix}/{workspace_slug}/{filename_template}`，`root_prefix` 为空时退化成
`{workspace_slug}/{filename_template}`。

知识库 slug 的生成规则不变（标题里的中英文数字，截 48 字符，冲突则接 UID，取不到字符回落
UID，一经生成不再变动——见 [store/workspace_slug.go](../../../../store/workspace_slug.go)）。
没有归属的附件仍落 `_unassigned/`。

### 与旧字段的兼容

旧 `filepath_template` 是自由字符串，可能是任何形状。规则：

- 保留 `filepath_template` 字段本身，只是**不再作为 S3 写路径的事实来源**，改由新的
  `root_prefix` + `filename_template` 决定。
- 老实例升级时做一次拆解：模板里 `{workspace}` 之前的部分进 `root_prefix`，之后的部分进
  `filename_template`。模板里没有 `{workspace}` 的（用户自己删掉了，或者是 `{workspace}`
  出现之前的老配置），整段目录部分进 `root_prefix`、文件名部分进 `filename_template`——
  这类实例的存量对象全部属于"平铺"，交给历史收编那一步处理。
- **LOCAL 存储的行为不变。** `{workspace}` 本来就只对 S3 生效，本地盘继续按现在的样子写。
  三级模型是 S3 概念，不外溢到本地目录。

## 迁移的生命周期

一次迁移是一个显式的、有状态的流程，不是"改个配置就开始搬"。

| 阶段 | 系统状态 | 用户能做什么 |
|---|---|---|
| **草拟** | 目标配置（源/桶/前缀）单独存着，不生效 | 填写目标配置，随时改，随时丢弃 |
| **预检** | 用目标配置试连、试写、试读、试删一个探针对象 | 看连通性结果；不通就回草拟 |
| **冻结** | 附件写入闸门关闭 | 文档照常读写，附件不能传/删/换 |
| **搬运** | 逐条搬，进度可查，可中断可续跑 | 看进度；可以中止（回到冻结态） |
| **对账** | 逐条核对新位置对象存在且大小一致 | 看对账结果；有缺失则不允许切换 |
| **切换** | 目标配置成为生效配置，映射全量改写 | —— |
| **解冻** | 写入闸门打开，新上传落新位置 | 恢复正常 |
| **收尾** | 旧位置对象仍在 | 自行核对后到 S3 控制台手动删除 |

预检必须真的写一个探针对象再读回来再删掉，不能只测连通——桶存在但没有写权限、
或者前缀被桶策略拒绝，都只有真写一次才发现。

## 五条不变量

这五条是验收的骨架，方案怎么变都得满足。

1. **附件的对外 URI 不变。** 附件永远是 `/file/attachments/{uid}/{filename}`
   （[fileserver.go:149](../../../../server/router/fileserver/fileserver.go)），文档正文里存的是
   `attachments/{uid}` 资源名，对外发布的链接也走同一形式
   （[internal/publish/refs.go](../../../../internal/publish/refs.go)）。S3 key 从来不出现在
   任何用户可见的地方，所以这条是**结构上天然成立**的，不需要额外机制，只需要不破坏它。
2. **迁移期间，每条附件按它自己的实际位置解析。** 已搬的走新配置新 key，未搬的走旧配置旧 key。
   这条是"迁移期间附件仍可正常访问"的全部内容，也是第 1 节那个坑的正解。
3. **不删旧对象。** 全流程零 `DeleteObject`（探针对象除外）。
4. **可中断、可续跑、幂等。** 进程重启、网络断开、手动中止之后再跑，从断点继续，
   已搬的不重搬，重复执行同一条不产生第二份对象。
5. **切换之前随时可放弃。** 放弃只改数据库指针，不搬数据，代价接近零。

## 历史平铺的收编

搬运时目标 key 是**重算**出来的，不是把旧 key 换个前缀。重算规则：

- 归属按附件关联的文档推导：`attachment.memo_id` → memo → workspace → `storage_slug`。
- **推不出归属的进 `_unassigned/`**：`memo_id` 为空的孤儿附件（被解绑过、或上传后从未插入
  任何文档）统一落到 `_unassigned/` 前缀下，与现在上传时不带 workspace 的处理一致
  （[attachment_service.go:892](../../../../server/router/api/v1/attachment_service.go)）。
- 文件名段沿用旧 key 的最后一段，**不重新生成**。重算目录、保留文件名，迁移才是可预测的——
  否则同一条附件跑两次会得到两个不同的 key。

因此"平铺"不是一种需要特殊处理的情况：所有附件都走同一套重算，平铺的那些只是恰好目录变了
而已。迁完之后新桶里不存在平铺对象。

### 副作用：知识库改名后目录不再跟着改的约束仍然保留

`storage_slug` 一经生成不再变动，是因为对象 key 已经写进去了、改名会让 key 指向不存在的路径。
迁移能力理论上让"改名时顺带搬目录"变得可行，但**本期不做**——把重算 slug 和换存储位置两个变量
叠在一次操作里，出问题时无从定位。留作以后。

## 冻结的范围

只冻结**附件写入**，不做全站只读，也不禁止登录。文档照常读写、搜索照常、附件照常读。

写入闸门要盖住的入口是三个，都在服务端：

- 新附件落盘：`CreateAttachment` → `SaveAttachmentBlob`
  （[attachment_service.go:731](../../../../server/router/api/v1/attachment_service.go)）
- 原地替换内容：`applyAttachmentContentUpdate`
  （[attachment_service.go:498](../../../../server/router/api/v1/attachment_service.go)）
- 删除对象：`DeleteAttachmentStorage` 及其批量入口
  （[store/attachment.go:237](../../../../store/attachment.go)）

闸门必须在**服务端**，不是把前端按钮置灰——memogit、MCP 都能创建文档，前端拦不住。
被拦时返回明确的"存储迁移进行中"错误，前端据此提示，不是一个笼统的 500。

删除也要拦：迁移期间删一个附件，会出现"数据库记录没了但旧对象还在"或者"刚搬过去的新对象被删了"
两种脏状态，都不值得为它写补偿逻辑。

## 附件的原地更新：同 key 覆盖，不换新 key

附件内容可以被原地替换（draw.io 存回自己的 SVG，见
[ADR-0017](../../adr/0017-drawio-svg-with-embedded-xml.md)）。这类更新**继续写回同一个 object key**，
不采用"先删旧对象、再按当前模板生成新 key 写入"的做法：

- `PutObject` 覆盖同一个 key 是一次原子替换，不存在"删掉了但还没传上去"的空窗。先删后建是
  三步非原子操作，任何一步失败都留下孤儿对象或坏链。
- key 稳定，迁移的目标 key 就永远可以从旧 key 重算出来，幂等性（不变量 4）不依赖任何状态位。
  key 会变的话，搬运中途被更新过的附件就对不上账了。
- 迁移期间附件写入本来就是冻结的（含原地替换），所以"边搬边被改"不需要额外处理。

代价是 `filename_template` 改了之后，老附件的文件名段不会跟着变。这是可以接受的：模板只影响
新写入的对象，历史对象的文件名没有任何人依赖——对外 URI 里根本不出现 object key。因此
**改 `filename_template` 不触发迁移**，它不属于位置的一部分。

## 明确不做

- **不自动删除旧数据。** 理由见产品边界。也不提供"一键清理旧位置"的按钮——那个按钮的存在本身
  就会让人在没核对的情况下按下去。
- **不迁移旧备份。** 同一个桶里还有 `backups/` 前缀的整库备份，走独立的
  `backup_setting.path_template`（[store/instance_setting.go](../../../../store/instance_setting.go)）。
  备份是可再生的、有保留期的、不被任何 URI 引用的，搬它没有收益。换桶后新备份自然写到新桶，
  旧备份留在旧桶随旧数据一起由管理员处理。
- **不做多存储源共存。** 不支持"这个知识库在 A 桶、那个在 B 桶"。实例只有一个生效的附件存储位置。
- **不做双写 / 灰度切换。** 冻结几分钟到几十分钟，比双写期间两边不一致的排查成本低得多。
- **不做迁移期间的自动降级读取。** 不去"新桶找不到就回旧桶试试"——那会把一个确定性问题
  变成两次 RTT 和一个说不清的状态。位置由每条附件自己的状态决定，不靠试。
- **不做跨实例迁移。** 本需求是同一个实例换存储位置，不是把数据搬到另一个 Toucan。

## 验收判据

1. 换桶之后，全站已有附件（含图片内联、视频播放、PDF 预览、对外发布页里的引用）全部正常打开，
   URL 与迁移前逐字节相同。
2. 迁移期间访问任意附件正常；上传附件被拒绝并给出明确原因。
3. 迁移中途 kill 掉进程再启动，能从断点继续，最终结果与不中断跑一遍一致。
4. 对账能报出"新位置缺失 N 个"，且缺失非零时切换被拒绝。
5. 迁移完成后，新桶里不存在平铺在根目录的附件对象；`memo_id` 为空的附件全部位于 `_unassigned/`。
6. 迁移完成后旧桶内容一个对象都没少。
7. 迁移完成后新上传的附件落在新配置的三级路径下。
8. 放弃一次未切换的迁移，系统回到迁移前状态，附件访问不受影响。

## 已定的边界

- **单条搬不动不中止整次迁移。** 源对象不存在（数据库有记录、桶里没有文件）时记为跳过，
  继续往下跑完，最后在对账结果里列出所有跳过项。存量里存在这类断链的概率不低，一条断链
  卡住整次迁移不合理。跑完之后如果结果不满意，新位置的数据删掉重来即可——旧数据一直没动。

  与"对账不通过就不许切换"的分界在于**为什么少了一个对象**，对账因此分成两类：
  源对象本来就不存在（断链）的记为跳过，**不阻塞切换**——这条附件在迁移之前就已经是坏的，
  拿它挡住迁移等于让任何有历史断链的实例永远迁不了；源对象存在而目标缺失或大小不符的记为
  失败，**阻塞切换**，那是真的没搬成功。两类都要在结果里显式列出来，不能悄悄跳过。
- **触发迁移的是位置三元组：endpoint、bucket、root_prefix。** 任意一个变了都要走迁移；
  三者的任意组合（只换节点、只换桶、只换前缀）都是成立的场景。凭证和 region 只说明"怎么连"
  到同一份数据，可以直接改——密钥轮换是日常操作，不该被迁移流程绑架。`filename_template`
  只影响新写入对象的文件名，同样不触发迁移（见上一节）。
- **目标配置的凭证可以与当前完全相同。** "只换桶"和"只换前缀"这两个场景里 endpoint 和凭证
  本来就没变，正好是服务端 `CopyObject` 的适用条件，也会是最常见的一类迁移。UI 上要显式
  告诉用户这次走的是服务端复制还是转存，两者的耗时差一个数量级。

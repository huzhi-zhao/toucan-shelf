# 对外发布（Publish）

把知识库里的单篇文档发布到一个对外站点，供不特定读者阅读。与"分享"
（给拿到链接的特定人看一份文档）是两条独立链路、两个动词。

本篇只写要做成什么样与依据；实施方案属于 [../design/](../design/)，
选型取舍属于 [../adr/](../adr/)。

## 1. 与分享的边界

这是本篇最重要的一条约束，其余设计都从它推出来。

| | 分享（share） | 发布（publish） |
|---|---|---|
| 主语 | 这份文档 | 作者 / 站点 |
| 读者 | 心里有数的那几个人 | 不特定读者 |
| 前提 | 链接先到人手里 | 读者能自己发现内容 |
| 核心难点 | 权限：谁能看、能不能改、是否过期 | 分发：目录、SEO、站点门面 |
| 更新语义 | 同一份文档的最新版本，实时 | 作者显式发布出去的那一版快照（§5） |

**不把发布做成"分享的加强版"。** 一旦给分享加聚合页、订阅、作者主页，
用户就无法预期"公开"这个开关到底做了什么——是给同事看，还是被搜索引擎收录。
这个歧义一出现，人会连普通分享都不敢用。因此发布是一个**独立的、显式的动作**，
两条链路各自演进；同一篇文档可以既被分享又被发布，互不影响。

## 2. 目标场景与不争的场景

**要服务的**：个人知识花园、团队对外文档站、产品帮助中心。这三类读者进站
不是"看最新一篇"，是"找某个东西"或"从头读一遍"。

**明确不争的是流量。** 掘金 / CSDN 的核心价值是流量池，发过去有人看；本站
没有天然流量，也不该去争"写技术文章涨粉"这个场景。

**唯一立得住的差异是单一信息源**：内容始终活在知识库里，站点上那份是它的投影，
不是另一份可编辑的内容。改文档之后点一次"更新发布"，站点就跟上（为什么不做成
实时跟随，见 §5）；哪些发、哪些不发是文档上的一个属性，不是两套内容。
"免去复制粘贴"只是这条差异的副产品，单靠它不足以支撑做这块能力——
复制粘贴的成本太低了。

## 3. 站点模型（blog 空间）

**站点是独立实体，不挂在知识库上。** 一个站点（下文也叫 blog 空间）有自己的
名字、域名、主题和首页，与知识库是多对多关系：

- 一个知识库里的文档，可以分别发布到不同的站点（技术笔记发去 A，产品说明发去 B）。
- 不同知识库里的文档，可以发布到同一个站点——**站点的内容边界由"作者一篇篇挑"
  决定，不由知识库边界决定**。

> 与早期方案的差异：最初写的是"一个知识库 = 一个站点，不同知识库不合并"，
> 理由是目录/成员/结构边界现成。但 §4 已经确定发布路径与编写路径解耦、URL 扁平，
> 站点根本不继承知识库的目录结构；剩下的只有成员边界，而成员边界是**作者侧**的
> 权限问题，跟读者看到什么无关。这条约束因此不成立，改为站点独立建模。

**归属：站点属于团队，不属于某个知识库。** 建站、配域名、改主题是团队级操作，
只有 admin 能做（角色模型见
[collaboration/workspace-member-access.md](collaboration/workspace-member-access.md)）。
一个团队可以建多个站点，彼此独立。

**多团队是未来可能的突破口，不是现状**：当前一个实例只有一个 admin，也就是
只有一个团队；真要突破，形态是每个团队一个 admin、一个团队多个站点，且
**团队之间资产完全隔离**（站点也不例外，不存在跨团队共享的站点）。
所以发布相关的数据模型从一开始就挂在团队上，而不是挂在"那个 admin 账号"上。

**Explore 不是站点门面。** Explore 定位为**工作区内部**的探索入口，不对外。
站点门面是 §6 的 dashboard——作者自己编排出来的，不是系统自动聚合出来的。

## 4. 发布单位与呈现

**发布单位是单篇文档，发布时要选一个目标站点。** 站点是发布动作的必填参数，
不由文档所在知识库推导（§3）。同一篇文档发到多个站点是允许的，每个站点上是
独立的一条发布记录（各自的 slug，见 §8）。

发布频率天然不高（对全网公开的内容需要有真知灼见，
即便大公司团队成员的发布频率也很低），子树批量发布不是常用场景，不做。

**发布权限：只有 admin 能发布。** member 对被分配的知识库有文档级读写，但
"把内容推给全网"是团队级动作，不随文档写权限一起给出去。

将来是否放开给 member（可能还要带审核）目前不定，但有四条约束现在就要守住，
守住了以后就只是"加一张授权表 + 换一个权限判定"，不用回头改模型：

1. 发布记录挂在**团队 + 站点**上，不挂在"那个 admin 账号"上（§3）。
2. 发布状态用**枚举**，不用 bool。以后要加 `PENDING`（待审核）不用改表。
3. 每条发布记录记下**发布者**（§5）。
4. **生成快照时的读取走发布者本人的权限上下文**，不走超级用户。这条是四条里
   唯一后补代价大的——一旦快照生成写成"以管理员身份读一切"，放开给 member 时
   越权检查没有落点。

**发布路径与编写路径解耦**——这是必须守住的一条。编写时的目录结构是给作者
自己用的（草稿箱、按项目分……），不该为了 URL 好看去迁就对外结构；反过来也
不该强制作者先在知识库里建出一棵"对外目录"才能发布。

由此确定：

- **URL 扁平**：站点域名下 `/<slug>`，与文档在树里的位置、在哪个知识库里都无关。
- **分组靠 tags**，不靠文件夹。tags 当筛选器用，不当主导航。
- **日期不做主序**：不做按日期倒序的时间流当主导航，日期只在文末显示
  "最后更新于"。首页的 feed 块（§6）是作者编排的列表，不是时间流。

## 5. 发布语义：快照 + 更新发布

**发布产出一份快照，站点上读者看到的是快照，不是知识库里的实时正文。**

一次发布做的事是：把当前正文过一遍发布管线（剔除加密块、按目标站点重写站内
链接、固定附件引用、跑完 §8 的全部检查），把管线的输出存成一份**只读产物**。
之后作者在知识库里怎么改，站点都不动；要让改动生效，作者显式点**更新发布**，
重新过一遍同一条管线、生成新快照。撤销发布就是把快照下线。

**为什么不做实时投影。** 实时投影和 §8 的可见性检查不能同时成立：检查只发生在
"发布"这个动作上，而正文之后仍然会被编辑器、memogit push、MCP agent 改动，
任何一次修改都能把新加的未发布引用、私密附件、加密块直接带上线，而且作者未必
知道内容变过。快照让"检查过的那份内容"和"对外的那份内容"是同一个东西——
这是本节存在的唯一理由，不是为了性能或缓存（那些是顺带的好处）。

**这不推翻 §2 的单一信息源。** 可编辑的内容源仍然只有知识库这一份，快照是它的
定格投影，只读、不可在站点侧编辑、随时可以从源文档重新生成。快照不是第二份内容，
它是构建产物。

由此还确定两条：

- **编辑器要能看出"已发布的那版落后于当前版本"**，并就地给出更新发布入口。
  没有这个提示，快照模型对作者就是"我明明改了但线上没变"。它顺带也解决了
  agent 悄悄改已发布文档的问题——改动不会自动上线，但作者能看见差异。
- **快照记录里要留下是谁发的、什么时候发的**。撤下、审计、以及 §4 提到的
  将来放开 member 发布，都要用到这个字段。

dashboard 是这条规则的一个例外，见 §6。

## 6. 站点首页（dashboard）

每个站点有一篇 dashboard 文档作为首页，访问站点根路径 `/` 落在这里。

**dashboard 就是一篇 `.view` 文档**，复用 gallery view 那套配置驱动渲染
（见 [views/gallery-view.md](views/gallery-view.md)）：content 只存结构化配置，
不存渲染产物，条目由渲染时查出来。好处是首页的排版能力（相册块、说明文字块）
现成，作者用编辑站点内容的同一套编辑器就能改首页。

为它新增一种 block：**feed layout**，与 gallery layout 同一类，区别只在呈现——

- gallery 是卡片网格，feed 是纵向条目列表（标题 + 摘要 + tags + 最后更新时间）。
- **数据来源是本站点的发布记录集合**（§5 的快照表），不是知识库的文档表。这是它跟
  gallery block 最实质的差别：gallery 按树的位置和属性筛，feed 只认发布记录，
  可以再叠 tags 过滤和排序。

**对外页面上的任何 block，数据源一律只能是发布记录集合。** 这条比"记得过滤掉
未发布文档"强：对外查询根本不接触知识库的文档表，未发布内容不是被规则挡住的，
是压根不在查询范围里。普通 gallery block 如果允许出现在对外页面，也照此收窄
——它在库内是按目录树扫文档，在对外模式下只能扫发布记录。

**dashboard 自己也走发布，但列表是活的。** dashboard 的排版配置是一篇文档，
跟别的文档一样要发布 / 更新发布（改了版式不点更新就不生效）；但 feed 列出的
条目是实时从发布记录来的——新发一篇文章，首页立刻出现，不需要重新发布 dashboard。
这是 §5 快照规则唯一的例外，且它不破坏边界：发布记录本身就是"已经过检查的内容"。

**dashboard 存在哪：就是某个知识库里的一篇普通 `.view` 文档**，站点上记一个
指针指向它。不新建"不属于任何知识库的系统文档"这种概念，也不给每个站点建一个
隐藏知识库。

理由是它得能被编辑——现有编辑器、权限、版本历史、memogit 全都直接可用，另造
一套入口不划算。站点与知识库解耦，解的是**内容边界**（站点收哪些文章不由库
决定），不是"站点相关的文档不许待在库里"；dashboard 是作者手写的内容，放在他
自己的库里很自然。

配套一条：**被站点指向的文档不许删除、不许归档**，照搬现有"被引用则拒绝删除"
的做法。删了站点就没首页了。

> 另两个方案被否掉的原因：给每个站点建隐藏知识库，会连带把标题全局唯一、书架
> 展示、成员授权、RAG 索引范围一整套东西拖进来，为一篇文档不值；让 dashboard
> 不属于任何知识库，要动 `memo.workspace_id` 非空和 `(库, 路径, 标题)` 唯一索引
> 的语义，风险大于收益。

其余几条跟着 §4 走：

- feed **不是按日期倒序的时间流默认页**。默认排序是作者在配置里定的（可以是手工
  排序、可以按 tags 分组），日期只是一个可选排序项，不是产品主轴。
- dashboard 本身不进知识库的 Explore feed（`.view` 的既有排除规则）。

## 7. 站内搜索

§2 说读者进站是"找某个东西"，那站点就必须能搜。只有一个 dashboard 加 tags
筛选，"团队对外文档站"和"产品帮助中心"这两个场景立不住。

**范围只限本站点的已发布内容**，因此不违反 §11——搜索是"人已经进了这个站点
之后怎么找东西"，不是让站外的人发现内容的机制。

**用独立索引，不复用知识库的 RAG 索引。** 检索算法（FTS + 向量混合、RRF 融合、
无 embedding 自动降级纯关键词）整套复用现有实现（见 [rag-search.md](../rag-search.md)），
但索引数据本身另存一份，在**发布 / 更新发布时建、撤下时删**。

理由不是隔离好看，是知识库索引里的文本**和线上页面不是同一份**：快照冻结之后
作者还会继续改正文，那些改动如果留在共用索引里，匿名读者用关键词就能召回这篇
文章——即使点进去看不到内容，"这个词出现在这篇文章里"已经漏出去了。索引隔离
把这个通道从结构上堵死，不用靠查询条件守。

顺带两个好处：知识库索引要追着每次编辑跑增量任务，站点索引的数据源只在发布
动作时变，不需要后台队列；两套索引各自重建互不影响。

**检索模式是站点级配置，不是用户偏好。** 现在的"混合 / 仅关键词 / 仅语义 / Like"
挂在用户 Preferences 上，匿名读者没有账号，站点侧只能有一份固定配置
（默认混合，实例没配 embedding 就自动降级为关键词）。

## 8. slug

- 与 `doc id` + `site id` 绑定：一篇文档在一个站点里有且只有一个 slug。
- **只在首次发布时生成一次，之后永久固定。** 改标题不重生成，重新发布不重生成——
  AI 生成不确定，slug 一变外链全断。
- 生成规则：规则式为主，中文标题走 AI 翻译取名。**AI 失败或超时必须有兜底**
  （拼音 / doc id 前几位），不能因为 AI 不可用就卡住发布。
- 生成后写进持久字段，允许用户手改。
- **同一站点内 slug 唯一**。不同库的同名文档发到同一个站点必然会撞——撞了就在
  生成时加后缀消歧（不是报错让作者自己想名字），手改时撞则直接拒绝并提示。
- **保留路径不许被 slug 占用**：`/d/`、搜索页、tags 筛选页、站点自己的静态资源
  前缀。生成和手改都要过这份保留字表，否则一篇文章能把站点搜索页顶掉。
- 另留一条永久短链 `/d/<doc-id>` 重定向到当前 slug，兜住 slug 被手改的情况。
  它是**站点内**的路径：只有当这篇文档已发布到**本站点**时才解析，否则 404——
  不能出现"在 A 站点的域名下用 doc id 探到发在 B 站点、或者压根没发布的文档"。

## 9. 可见性检查（安全边界）

发布是把内容推给全网，这一节的规则必须在**生成快照的管线里硬做**，不能靠前端
隐藏，也不能靠用户自觉。检查在**每一次生成快照时**跑——首次发布跑，每次更新
发布也跑，没有"首发查过了就不再查"这回事。

**所有检查都是按站点判的。** "已发布"永远指"已发布到本次这个目标站点"，不是
"在别的站点公开过"。同一篇文档发到两个站点，两次检查各算各的。

**生成快照时检查：**

- **文档引用**：引用了**未发布到本站点**的文档 → **发布失败**，报出具体是哪几条
  引用，要求作者改正后重新发布。链到 404 是明确的错误，不容降级。
- **引用解析要带源文档的知识库上下文**。站内链接的规范形式是工作区根相对路径
  （见 [cross-reference-repair-on-move-rename.md](cross-reference-repair-on-move-rename.md)），
  而这个路径只在**库内**唯一；一个站点混了多个库的文档之后，同一个路径可能指向
  两篇不同的文档，必须按"这篇文档属于哪个库"来解析。库内渲染那层"全树按标题
  兜底匹配"在发布管线里**关闭**——兜底会匹配到未发布文档，是泄露面而不是便利。
- **普通附件 / 图片**：**不硬失败，也不放开权限——发布只搬内容，不动附件。**
  发布时列出"这 N 个附件读者取不到"，作者要么自己去附件那边把文件设成公开、
  在正文里给链接，要么把它从文章里去掉。

  > 早先写的是"作者确认后由发布动作放开权限"。改掉的理由：文章公开和文件公开
  > 是两个决定，把后者做成前者的附带动作，等于让一次点击同时开两道门，而作者
  > 只看见一道。谁拥有这个文件、谁来决定它出不出去，这条线不该被发布流程模糊掉；
  > 顺带也省掉了"发布时放开、撤下时回收"那套引用计数——不放开，就没有回收。

- **私密附件（口令闸门那类）**：**硬失败**。作者给一个文件单独加了口令，就是
  明确表达过"这个不能随便给人"，发布不能替他推翻这个决定——连"提示一下让他
  自己去开"都不做，直接拒绝发布。
- **加密块**：快照里**不含那个块**——不是前端不渲染，是产物里根本没有。注意正文
  里的 `toucan-secret` 块本来就只有一个指针，密文在 `secret_block` 表里
  （见 [editor/secret-block.md](editor/secret-block.md)），所以这条真正要守的是
  两点：快照里不留指针块，以及 `SecretBlockService` 对匿名请求一律拒——否则
  剔了正文块，对外页面的脚本照样能把密文和 KDF 参数取走离线爆破。
- **内部元信息不出站**：评论、版本历史、内部 frontmatter 属性、memogit 身份标记、
  作者账号信息，默认都不进快照。这里的默认策略是**白名单往外放**，不是列黑名单
  往下挡——挡漏一条就是泄露，放漏一条只是少显示一个字段。

**撤下与删除：**

- 撤销发布 / 删除文档时，反向检查"谁引用了我"，本站点上有已发布页面引用它就
  给出警告。只在发布时查一次不够——A 发布时 B 是公开的，三天后 B 被撤下，
  A 的快照里就留下一条死链（快照不会自己跟着变，这是快照模型要付的代价）。
- 撤下**不动附件权限**：发布没放开过任何东西，也就没有可回收的。一个文件是公开
  的，是因为它的主人说它公开，文章下线不是推翻这个决定的理由。快照仍然记录它
  引用了哪些附件，那张表回答的是"这个文件要是转回私有，哪些线上页面会坏"。
- 文档进回收站（归档）等同撤下，与附件那边"归档文档一律 404"的既有判定对齐。

**链接重写**：站内文档链接、附件链接都在快照里重写到**站点自己的域名**下，
不指向主应用域名。读者在站点上点一个链接跳去主站是割裂的。

## 10. 域名

一个站点绑一个自定义域名（比如 `blog.huzhi.dev`），站点上存 domain 字段，
反代按 Host 找站点，走 CNAME + 自动证书。域名下的根路径 `/` 是该站点的
dashboard（§6），`/<slug>` 是具体文章。

同一个站点会有两个入口（平台路径与自定义域名），必须选一个作 canonical，
另一个 301 过去，否则 SEO 判重复内容。

**域名归属要验证**（DNS TXT 或指定文件），否则谁都能把别人的域名填进自己的
站点，配上自动签证书就是一条被人利用的路径。按 Host 自动签发也要限流。

**站点本身有上线开关。** 建好站、配好域名、编排好 dashboard 之前，站点不该
对外可访问；下线的站点整站 404，与单篇撤下是两个粒度。这也是 §11 里"匿名可读
由站点状态决定"的那个状态。

证书签发、CNAME 校验这些是纯工程活，不影响上面的产品设计，可以最后做；
但"站点带域名"这个建模要一开始就有，它是站点独立于知识库存在的理由之一。

**SEO 的最低配**（§1 把 SEO 列为发布这条链路的核心难点，不能只有 OG meta）：

- **sitemap 与 robots** 按站点生成，只列本站点已发布页面。
- 非已发布页面、平台路径入口（非 canonical 那个）一律 `noindex`。
- **撤下的页面返回 410 而不是 404**，让搜索引擎尽快撤索引；被撤下的 slug 记录
  保留，以便原样恢复。
- 同一篇文档发到多个站点是**跨站点重复内容**，上面的 canonical 规则只处理了
  "平台路径 vs 自定义域名"。这种情况下由作者指定一个主站点，其余站点上的这篇
  指过去；作者没指定就按最早发布的那个站点。

## 11. 与内部预览的关系

对外页面与知识库内部的文档预览差别不大——**这是好事**，说明渲染层可以复用：
不是再造一个阅读器，而是给现有渲染器加一个**对外模式**。

差异只有这几处：不要求登录；不出编辑相关 UI；**读的是快照而不是文档表**
（§5、§9 的硬边界）；站内链接重写；补 OG / SEO meta；主题可定制。

匿名可读这件事要与实例的 `AllowAnonymous` 解耦。那个开关现在等价于"实例配了
InstanceURL"，管的是主应用要不要对匿名开放；站点域名下的读者能不能读，应该只由
"这个站点上线了没有"决定。否则要么私有实例根本发布不出去，要么为了发一篇文章
被迫把整个主应用对匿名打开。

## 12. 明确不做

- **博客社区形态**：订阅 / RSS、关注、作者主页、面向陌生人的评论区、
  跨站点的全局聚合/发现页。判据：任何让**没拿到链接、也没进这个站点**的人
  主动发现内容的机制，都越界。
  站点自己的 dashboard（§6）不在此列——它是作者显式编排的门面，范围只限本站点
  已发布内容，跟"系统把全站公开内容自动汇总给陌生人"是两回事。
  站内搜索（§7）同理——范围只限本站点已发布内容，是进站之后的找东西，
  不是站外发现。
- **子树 / 批量发布**（§4）。成本不高，但场景不常用。
- **按日期的 feed 主导航**（§4）。feed **布局**要做，按日期倒序当默认首页不做。

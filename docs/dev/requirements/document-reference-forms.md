# 文档引用的路径表达形式

分阶段实施计划见
[design/20260829-relative-and-cross-workspace-refs.md](../design/20260829-relative-and-cross-workspace-refs.md)。
引用在移动/重命名/删除时的完整性维护（修复与拒绝）见
[cross-reference-repair-on-move-rename.md](cross-reference-repair-on-move-rename.md)，
本篇不重复那一层，只回答「一条引用可以怎么写」。

> 本篇 2026-08-29 新建，**部分推翻**上述那篇的两条结论：
> 「不保留对 `../` 相对路径的读取兼容」与「跨工作区引用被禁止」。推翻的依据是产品诉求
> 而非实现便利——见下文「为什么推翻」。那篇文档中依赖「所有链接目标都在同一工作区内」
> 这一前提的段落，以本篇为准。

## 背景

当前库内引用只有一种可写形式：**工作区根相对全路径**（`/设计/规范.md`）。它解决了
「目标移动后引用者的 href 只需算一次」的问题，但对写作者有两个现实痛点：

1. **同目录/近邻引用要写全路径。** `/a/b/c/` 下的文档引用同目录的兄弟文档，也得写
   `/a/b/c/兄弟.md`，而不是 `兄弟.md`。从外部（Obsidian、VSCode、任何 md 编辑器）
   带进来的文档，其相对链接一律失效。
2. **跨知识库引用没有可读形式。** 唯一能跨库的是 `/memos/{uid}`，一串不可读的 uid，
   没有自动补全，也无法用 `![[ ]]` 嵌入。

## 语法边界（先澄清：三种 markdown 形式各管什么）

这三种写法在本项目里是**三个互不相通的机制**，讨论引用时必须先分清：

| 写法 | 含义 | 实现 |
|---|---|---|
| `[锚文本](路径)` | **文档链接**，点击跳转 | [markdown/Link.tsx](../../../web/src/components/MemoContent/markdown/Link.tsx) |
| `![[路径]]` | **文档嵌入**，把目标正文并入当前文档流 | [MemoContent/Embed.tsx](../../../web/src/components/MemoContent/Embed.tsx) |
| `![alt](路径)` | **媒体**（图片/视频/音频），按扩展名分派 | [markdown/Image.tsx](../../../web/src/components/MemoContent/markdown/Image.tsx) |

**`![]()` 不是、也不会成为文档引用形式。** 除了语义冲突之外还有一条硬约束：
`ExtractLinks` 不覆盖 image 节点，`RewriteLinks` 也不改写 image
（[internal/markdown/markdown.go:62](../../../internal/markdown/markdown.go)、:71 明确
说明 image 是独立 AST 节点）。让 `![]()` 承担文档引用，等于要在 image 那条 AST 路径上
把 P0 反向索引与 P4/P5 修链整套复制一遍——**明确不做**。

本篇定义的所有路径形式，适用于 `[]()` 与 `![[]]` 两种写法，不适用于 `![]()`。

媒体引用不受本篇影响：附件 href 是 uid 寻址的 `/file/attachments/{uid}/…`
（[internal/publish/refs.go:16](../../../internal/publish/refs.go)），本来就没有路径概念，
跨库天然可用，且**跨库读取已被正确拦截**——见下节。

### 跨库内联附件的访问控制（已核实，无需改动）

「A 库的文档内联 B 库的附件」在跨库引用普及后会变常见。核实结论：**现有 ACL 已经正确覆盖，
本期无需改动。**

`attachmentacl.checkVisibility`
（[server/attachmentacl/attachmentacl.go:252](../../../server/attachmentacl/attachmentacl.go)）
按**附件自己所挂文档的 `WorkspaceID`** 解析 `ResolveWorkspaceAccess`，而不是按引用它的那篇
文档的库。因此读者对 B 库没有 grant 时，即使这张图被内联在他有权访问的 A 库文档里，也读不到
字节。二进制下载与元数据两条路径共用这一个判定（该包的包注释记录了它们曾经各写一份并发生
漂移的教训）。

两点需要在实现时注意，都不是安全问题：

- **失败返回 `ErrNotFound` 而非 `ErrForbidden`**，刻意不泄露存在性。代价是读者只看到一张
  坏图，没有任何解释。跨库引用普及后这个体验缺口会更常被撞见——建议 R2 一并给内联媒体
  加上与链接受限态一致的提示，但**提示只能说明「无权访问」，不得区分「不存在」**，
  否则会把 ACL 刻意隐藏的信息从渲染层泄露回去。
- `ACCESS_PUBLIC` 的附件在允许匿名访问的实例上**绕过知识库成员判定**（该包注释中的决策 7），
  跨库内联同样绕过。这是既有的、有意的设计，本篇不改变它。

## 四种路径形式（术语）

设当前文档位于知识库「技术笔记」的 `/fa/da.md`：

| 形式 | 术语 | 示例 |
|---|---|---|
| 以 `/` 开头的库内全路径 | **库根相对路径** | `[接口说明](/fa/db.md)` |
| 不以 `/` 开头的库内路径 | **文档相对路径** | 显式形式 `[接口说明](./db.md)`、`[规范](../fb/dc.md)`；裸形式 `[接口说明](db.md)` |
| 以 `@` + 库标题开头的跨库路径 | **库限定路径** | `[规格](@产品手册/fb/dc.md)` |
| `/memos/{uid}` 或 `{host}/memos/{uid}` | **UID 引用** | `[规格](/memos/abc123)` |

前两者合称**库内路径**。命名上刻意不把 `/fa/db.md` 叫「绝对路径」——`absolute` 一词在
现有代码里已经属于 `/memos/{uid}`（`ResolveAbsoluteMemoHref`），且它只是**库内绝对**。

四者的定位分工：

- **库根相对**：库内引用的规范形式，不变。它的值只是「目标在哪」的函数，与引用者在哪无关，
  这是自动修链能一次算完的基础。
- **文档相对**：为书写与外部导入而支持的**书写形式**。存储时原样保留（不做归一化改写），
  但在引用者自身被移动时会被固化成库根相对形式，见下。它再分显式（`./` `../` 开头）与
  裸（`db.md`、`sub/dd.md`）两种，解析规则完全一致，**只在解析失败时分岔**，见下一节。
- **库限定**：跨库引用的规范形式，人可读。
- **UID 引用**：不可读的稳定形式。保留两个用途——「复制链接」粘贴的产物，以及机器在
  无法表达路径时的降级目标（`rewriteOutboundLinksToUIDBestEffort` 已在这么用）。

## 为什么推翻原先的两条结论

原文档拒绝相对路径的理由是：相对路径会凭空多出「出向链接修复」一整类场景，成本是根相对
方案的 2～3 倍。这个判断在「把相对路径当作存储规范形式」的前提下成立，但本篇的定位不同——
**相对路径是书写形式，不是规范形式**。由此新增的场景只有一个，且是有界的：

> 引用者自身被移动时，重写**它自己这一篇**的相对出链。

单文档操作，内容就在手上，`MarkdownService.RewriteLinks` 是现成的通用原语，不需要新索引、
不需要反向扇出。触发点也已经存在：
[memo_service.go:832](../../../server/router/api/v1/memo_service.go) 的 `folderChanged`
分支上 `previousFolderPath` 是现成的。
[link_repair.go:61](../../../server/router/api/v1/link_repair.go) 那句
`source-moves-itself: its own outbound hrefs are root-relative and need no repair`
正是被打破的那条假设，缺口位置明确且唯一。

原文档禁止跨工作区引用的理由是「根相对全路径在跨库时无法表达」。这是形式的局限，不是产品
判断——而且**跨库的边在数据层早已合法**：`memo_link` 表只有 `(memo_id, target_memo_id)`
两列，没有 workspace 约束；`resolveMemoLinkTargets` 的 fallback 注释明写它覆盖跨 workspace
的目标；发布链路更是已经按「站点可聚合多个知识库」设计
（[site_publish.go:441](../../../server/router/api/v1/site_publish.go)）。给跨库引用一个
可读形式，是补齐表达，不是引入新的数据关系。

## 库限定路径的语法选型

选定 **`@库标题/库内路径`**。

依据两条既有事实：知识库标题**全局唯一**
（`CREATE UNIQUE INDEX idx_workspace_title`，[LATEST.sql:98](../../../store/migration/sqlite/LATEST.sql)），
且应用自身的文档 URL 第一段就是库标题（`{ path: ":workspaceTitle/:docId" }`,
[router/index.tsx:123](../../../web/src/router/index.tsx)）。因此跨库形式跟着 URL 走即可，
唯一要解决的是歧义：`/产品手册/fb/dc.md` 里的首段究竟是当前库的顶层文件夹，还是另一个库。
加一个 sigil 就足够。

选 `@` 而不选 `/w/{uid}/…` 或 `/workspaces/{uid}/…` 的理由：

1. **和应用 URL 同构**，只多一个符号，可读且可自动补全。
2. **不以 `/` 开头，现有解析入口天然不受影响。** `IsRootRelativeDocHref` 的判定是
   「以 `/` 开头且不是 `/memos/{uid}`」，极宽——任何 `/前缀/…` 形式都会被它吞下去当作
   「解析失败的库内路径」，即断链。`@` 开头它根本不碰。
3. 库标题唯一，标题足以定位，不必退到 uid。
4. 库改名会断链，但这是**有界且可修的**：`memo_link` 能精确捞出全部引用者，改的还是
   同一个值，比文档改名更简单。

### 由此产生的新约束（对存量数据）

知识库标题当前**没有任何字符校验**，只校验非空
（[workspace_service.go:34](../../../server/router/api/v1/workspace_service.go)）。
采用本形式需要新增两条约束：

- 标题不得包含 `/`（否则 `@a/b/c.md` 无法切分库段与路径段）；
- 标题不得以 `@` 开头。

含 `/` 的标题对现有的 `/{workspaceTitle}/{docId}` 路由其实已经是坏的，这条约束顺带修复了
一个既存缺陷。上线需要一次存量检查与改名引导，不能静默截断用户的库名。

### 显式相对与裸相对：解析失败时的分岔

`[x](example.com/page)` 是一条合法的站外链接，形式上与裸相对路径 `[x](db.md)` 无法区分——
两者都是「不以 `/` 开头、没有 scheme 的一段路径」。若一律按文档引用处理，凡是解析不到的
就标成坏链，那么现有内容里所有省略 scheme 的站外链接会集体变成坏链，这是纯粹的回归。

因此定这条规则：

- **显式相对**（`./` `../` 开头）是明确的文档引用意图。解析不到 = 坏链，照常标红。
- **裸相对**先按文档引用解析；解析不到则**退回站外链接语义**（新标签页打开），不标坏链。
  想要严格的坏链提示，写 `./db.md`。

同一条规则也约束移动时的固化（见下）：只有「移动前解析得到、移动后解析不到」的相对路径
才会被改写，否则 `example.com/page` 会被改写成 `/example.com/page`，把一条能用的站外链接
写坏。

## 需求边界

### 解析（读）

| 形式 | 用于 `[]()` | 用于 `![[]]` | 说明 |
|---|---|---|---|
| 库根相对 `/fa/db.md` | ✅ | ✅ | 不变 |
| 文档相对 `./db.md`、`../fb/dc.md` | ✅ | ✅ | 新增。基准是引用者所在文件夹 |
| 库限定 `@产品手册/fb/dc.md` | ✅ | ❌ **不支持** | 见下「跨库嵌入不做」 |
| 跨库的文档相对 `@产品手册/fb/../fc/dd.md` | ❌ | ❌ | 明确不做 |
| UID `/memos/{uid}` | ✅ | ✅ | 不变 |
| 其余 | 站外链接 | 断链提示 | 不变 |

**跨库的文档相对不支持**：跨库引用时写作者本来就不在目标库的目录上下文里，`..` 没有直觉
意义，只会制造理解成本。库限定路径的路径段只接受该库的库根相对形式。

**跨库嵌入不做（v1）**：`![[ ]]` 会把目标正文并入当前文档。当前文档一旦被分享或对外发布，
等于把另一个知识库的内容一并带出去。同样的警惕在发布链路里已有先例——site_publish 关掉了
一个 title 兜底，理由是「那是一条信息泄露路径，不是便利功能」。跨库嵌入要成立，需要先把
「嵌入内容随宿主文档外发」这条链路的可见性规则想清楚，不在本期范围内。

### 存储（写）

- **相对路径原样存储，不做保存时归一化。** 写作者敲什么，库里存什么，下次编辑看到的还是
  同一个字符串。归一化改写会让书写语义在再次编辑时丢失，是本篇明确拒绝的方案。
- **唯一的自动改写时机**：引用者自身被移动（含所在文件夹被移动/改名）时，把它的相对出链
  按**旧**位置解析出目标，改写为库根相对形式。相对语义在移动那一刻固化为绝对语义。
  这是有损的，但损失发生在确定的时点、结果确定且正确，好过静默变成断链。
- 库限定路径同理原样存储；库改名时统一改写库段。

### 渲染：三态

当前只有两态（可跳转 / 断链，`markdownStyles.brokenLink`）。跨库引入第三态：

| 状态 | 呈现 |
|---|---|
| 解析成功且有权限 | 正常链接，点击跳转（跨库时切换知识库上下文） |
| 解析成功但无权限 | 不可点击的受限标记，**只显示锚文本，不得泄露目标标题、路径或存在性细节** |
| 解析失败 | 现有断链样式 |

无权限与解析失败在视觉上必须可区分（否则用户无从判断是自己写错了还是没权限），但无权限态
对外泄露的信息量必须止于「你无权访问」。权限判定统一走 `store.ResolveWorkspaceAccess`——
该函数的注释已经写明它是 API 层与附件 ACL 的共同裁决点，不允许出现第二份实现。

### 完整性维护的增量

以 [cross-reference-repair-on-move-rename.md](cross-reference-repair-on-move-rename.md)
的边界表为基础，本篇新增/修改三条：

| 操作 | 原处理 | 新处理 |
|---|---|---|
| 移动文档 / 文件夹（同库） | 静默修复引用者 href | **额外**：把被移动文档自身的相对出链固化为库根相对 |
| 文档/文件夹跨工作区移动 | **拒绝**（库内有引用时） | 静默修复：库内引用者的 href 改写为库限定路径 |
| 知识库改名 | 无处理 | **新增**：所有指向该库的库限定路径，库段同步更新 |

第二条是产品价值最大的一处：跨库移动当前会被 P6 直接拒绝
（[memo_service.go:762](../../../server/router/api/v1/memo_service.go)、
[workspace_service.go:520](../../../server/router/api/v1/workspace_service.go)），
理由正是「根相对 href 只在单库内有意义」。这个前提被库限定路径解除后，拒绝可以改为修复。

## 验收判据

- `/fa/da.md` 中写 `[x](./db.md)`，渲染为指向 `/fa/db.md` 的可跳转链接；写
  `[x](../fb/dc.md)`，指向 `/fb/dc.md`。保存后再次打开编辑器，正文中仍是 `./db.md` 与
  `../fb/dc.md`，一个字节未变。
- 把 `/fa/da.md` 移动到 `/fc/`，其正文中的 `./db.md` 被改写为 `/fa/db.md`（指向不变），
  `../fb/dc.md` 被改写为 `/fb/dc.md`。链接在移动前后指向同一篇文档。
- 把包含 `/fa/da.md` 的文件夹 `/fa` 移动到 `/fx/fa`，同上：da 的相对出链固化，指向不变。
- 「技术笔记」库的文档中写 `[规格](@产品手册/fb/dc.md)`，当前用户对「产品手册」有读权限时
  渲染为可跳转链接，点击后切换到「产品手册」并打开 dc。
- 同一条链接，当前用户对「产品手册」无任何 grant 时，渲染为受限标记；页面上（含 DOM、
  网络响应）不出现目标文档的标题与路径。
- 「产品手册」改名为「产品规范」后，上述链接自动变为 `@产品规范/fb/dc.md` 并继续可跳转。
- `![[@产品手册/fb/dc.md]]` 渲染为明确的「不支持跨库嵌入」提示，而非静默展开或空白。
- 创建/改名知识库时，标题含 `/` 或以 `@` 开头被拒绝，错误信息说明原因。
- 文档 A（库甲）被文档 B（库甲）引用。把 A 跨库移动到库乙，操作**成功**，B 中的引用自动
  变为 `@库乙/…` 并可跳转——不再弹窗拒绝。
- 库内某文档写 `![](db.md)`，渲染为坏图（媒体语义），**不**被解析为文档引用，也不进入
  反向引用索引。这条作为回归判据固定下来。
- `[x](./missing.md)` 渲染为坏链；`[x](example.com/page)` 渲染为普通站外链接（新标签页），
  **不**标坏链。文档移动后 `example.com/page` 一个字节未变。
- 相对路径的固化是幂等的：同一文档连续移动两次，第二次不产生任何内容改写。
- 整个文件夹移动时，子树内文档之间的相对引用（如 `./Sibling`）保持相对形式不变——它们
  一起移动，相对关系没变；只有指向子树外的相对引用被固化。

## 非目标与已知取舍

- **不支持跨库嵌入**（`![[@库/…]]`），见上。
- **不支持跨库的文档相对路径**。
- **`![]()` 永不承担文档引用**，见「语法边界」。
- **memogit 导出后跨库链接是失效的。** memogit 完全不处理链接（整个
  `internal/memogit/` 不引用 `linkindex`），且是一库一 checkout
  （`Config.Workspaces`，[config.go:46](../../../internal/memogit/config.go)）。
  跨库链接导出到本地后指向另一个仓库的文件，本地编辑器点不动。这是已知限制，
  不作为缺陷处理；相对路径反而在本地是**更可用**的（这是支持它的附带收益）。
- **相对路径在文档移动时会丢失书写语义**（固化为库根相对）。接受。
- 不做跨库的搜索/自动补全性能优化，v1 按需拉取目标库的树即可。

## 开放问题

- **隐藏（软删除）的知识库能否作为库限定路径的目标？** `Workspace.Hidden` 是软删除，
  隐藏的库仍占用唯一标题。倾向：可解析、但渲染为受限态，避免"链接突然断掉"。待定。
- 知识库标题大小写敏感性：路由按大小写不敏感匹配，库限定路径的解析必须与之一致；
  但唯一索引是否大小写不敏感需要确认，否则会出现「路由能进、解析不到」的错位。

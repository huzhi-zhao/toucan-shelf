# 知识库内文档引用在移动/重命名/删除时的完整性维护

分阶段实施计划见
[design/20260807-cross-reference-repair-plan.md](../design/20260807-cross-reference-repair-plan.md)。

> 本版（2026-08-07 第二次对齐）推翻了初版的「需求边界」表。初版认为移动、文件夹改名
> 不会产生断链因而不做处理；该判断只成立于「链接点得开」这一层，不满足「正文里的路径
> 本身要正确」这一产品要求。本版按后者重新划定范围，并确定了链接的规范形式。

## 背景

类似 Obsidian、Notion 的知识库产品，在文档被重命名或移动时会自动维护/修复知识库内部
`[doc name](url)` 形式的引用链接。产品诉求：文档/文件夹移动、重命名、归档、删除时，
应检查知识库内部的引用依赖，并按操作类型分别做「静默修复」「弹窗告知并拒绝」。

## 现状事实（可证伪，来自对当前实现的调研）

- **文档详情页链接以 uid 寻址。** 复制链接生成 `{host}/memos/{uid}`
  （[web/src/components/MemoActionMenu/hooks.ts:126](../../../web/src/components/MemoActionMenu/hooks.ts)），
  `uid` 在文档整个生命周期内不变。这类链接不会因移动/重命名而失效，但它对人不可读，
  只作为「复制链接」的兼容形式存在，不是规范形式。
- **站内相对路径链接（多为 Obsidian 迁移遗留）在渲染时按标题兜底解析。**
  [DocumentLinkContext.tsx:81](../../../web/src/components/MemoContent/DocumentLinkContext.tsx)
  的 `resolveWorkspacePath` 依次尝试「相对当前文件夹 → 相对工作区根 → 全树按标题匹配」。
  最后那层兜底让链接在文档移动后仍能跳转，但代价是**正文里的路径永远是旧的**，且同名
  文档存在时会静默跳错。
- **以 `/` 开头的 href 当前不被视为站内文档链接。**
  `isRelativeDocHref`（[DocumentLinkContext.tsx:35](../../../web/src/components/MemoContent/DocumentLinkContext.tsx)）
  显式排除 `/` 前缀；后端 `internal/linkindex` 是照此 port 的同一套逻辑。
  采用根相对形式需要前后端同时新增解析规则。
- **文档路径在库内唯一。** `UNIQUE(workspace_id, folder_path, title)`
  （[store/migration/sqlite/LATEST.sql:49](../../../store/migration/sqlite/LATEST.sql)），
  因此「工作区根相对全路径」可以唯一定位一篇文档，不存在歧义。
- **没有 wiki-link / 插入文档引用的编辑器功能**，只有标准 markdown 链接语法。
  `@mention` 指向用户，与文档引用无关。
- **`memo_relation` 表**是用户手动设置的「关联文档」，与正文里的 markdown 链接完全独立，
  两套机制互不影响。

## 链接的规范形式

**工作区根相对全路径**，如 `/doc/api.md`、`/设计/规范.md`。

- 以 `/` 开头，其后为从工作区根开始的完整文件夹路径 + 文档标题。
- 扩展名可有可无；解析时按扩展名无关、大小写无关匹配标题。
- 含空格或括号时按 CommonMark 规则用 `<>` 包裹目的地。

选它而不选标准相对路径（`../src/guide.md`）的理由：**根相对 href 的值只是「目标文档在
哪」的函数，与「写这条链接的文档在哪」无关。** 由此，源文档自身被移动时，它正文里的所有
出向链接一个字都不用改；目标被改名/移动时，所有引用者的新 href 是同一个值，算一次即可。
标准相对路径则会凭空多出「出向链接修复」一整类场景（移动一个文件夹要遍历子树内每篇
文档的每条链接，逐条判断是否跨越子树边界），实现与运行时成本约为根相对方案的 2～3 倍，
且每次移动都要反复改写正文，产生持续的 diff 噪音。

代价是**导出到纯文件系统后 `/doc/api.md` 会被本地工具解析为磁盘根目录**。当前接受这个
代价：memogit 的定位是方便 AI 协作，可以通过 skill 让 AI 理解这套路径约定；若未来确有
刚需，在整库导出时对 md 做一次统一路径转换即可，不影响库内存储形式。

### 不保留对 `../` 相对路径的读取兼容

解析层只识别两种 href：规范形式的根相对全路径，以及兼容形式的 `/memos/{uid}`。
其余一律视为站外链接。同时**取消「全树按标题兜底匹配」这一层**——路径解析失败即判定为
断链，不再静默跳到某个同名文档。

这条决策的直接后果：**存量的 Obsidian 遗留相对链接会从「能跳」变为「显式断链」**，
且因为解析不出目标，它们也进不了反向引用索引，不会被后续的自动修复覆盖。这是已知且
被接受的取舍——显式断链好过静默跳错。建议（非本期必须）在实施时附带一次性归一化脚本，
把当前仍能解析的存量相对链接批量改写为规范形式，避免这部分数据永久沉底。

## 需求边界

| 操作 | 处理方式 |
|---|---|
| 重命名文档 | 静默修复：所有引用者的 href 末段更新为新标题；锚文本仅在等于旧标题时同步更新 |
| 移动文档（同工作区内） | 静默修复：所有引用者的 href 更新为新的根相对全路径 |
| 重命名文件夹 | 静默修复：受影响 href 的对应路径段前缀替换 |
| 移动文件夹（同工作区内） | 静默修复：同上，按新的根相对全路径整体替换前缀 |
| 文档/文件夹跨工作区移动 | **拒绝**：库内存在引用时弹窗列出引用来源并阻止操作 |
| 归档文档/文件夹 | **拒绝**：同上 |
| 删除文档/文件夹 | **拒绝**：同上 |

两类交互的边界是刻意划分的：**弹窗出现即代表这个操作做不了**。可以可靠且无损修复的
操作（同工作区内的改名与移动）一律静默完成，不打扰用户；无法自动修复的操作（引用会
真正失效的跨库移动、归档、删除）才弹窗，列出引用来源并要求用户先自行处理依赖。

跨工作区引用被禁止之后，库内所有链接的合法目标都在同一工作区内，根相对全路径因此总能
表达；`/memos/{uid}` 仅作为「复制链接」粘贴产生的兼容形式存在。

锚文本的处理规则不随本次调整：**只有锚文本完全等于旧标题时才同步更新**，用户手写的
自定义锚文本永远不动。href 的修复则与锚文本是否匹配无关——路径必须始终正确。

## 验收判据

- 文档 A 位于 `/设计/`，被文档 B、C 引用。重命名 A 后，B、C 中的 href 更新为新的根相对
  全路径；锚文本等于旧标题的同步更新，被手动改写过的保持不变。全程无弹窗。
- 文档 A 被文档 B 引用。在同一工作区内把 A 移动到另一个文件夹，B 中的 href 更新为新路径，
  无弹窗。
- 文件夹 `/设计/` 被改名为 `/规范/`，其中文档被外部文档引用。改名后所有引用者的 href
  前缀同步更新，无弹窗。
- 文档 A 被文档 B 引用。尝试归档、删除 A，或把 A 移动到另一个工作区，操作被拒绝，
  弹窗列出「文档 B」作为引用来源；B 中的引用不会被自动清理。
- 文档 A 未被任何文档引用。归档/删除/跨库移动 A 均直接成功，不产生任何弹窗。
- 文件夹 F 下的文档被 F 外的文档引用。删除/归档/跨库移动 F 时，弹窗列出 F 内被引用文档
  及其引用来源（不只是判断 F 是否为空）。
- 源文档自身被移动时，其正文内所有出向链接保持字节不变（根相对形式的直接推论，
  作为回归判据固定下来）。

## 非目标与已知取舍

- 不做「插入文档引用」的编辑器功能（自动补全、选择文档插入链接）。
- 不处理 `memo_relation` 的同步维护，它与正文链接是两套独立机制。
- **并发编辑不做保护。** 自动修复走 `UpdateMemo` 全量覆盖 content，若用户在改名/移动
  发生的同时正在编辑某篇引用文档，未保存的内容会被覆盖。这是已知且被接受的行为，
  由用户自行承担，不作为缺陷处理。
- **TODO（本期不做）：批量写入的事务与索引重建合并。** 文件夹改名/移动引发的引用修复
  会逐篇改写文档正文，当前每篇各自触发一次 RAG 索引任务。后续应改为：整批改写走一个
  事务，全部提交完成后统一触发一次索引重建。这个约定适用于所有「一次操作批量改写大量
  文档」的场景，不限于本需求。

# 团队成员与知识库授权

产品定位是小公司/个人自建实例，**一套服务只服务一个团队**，不引入多团队概念。
实例的第一个注册账号是团队 owner，其余账号是被 owner 邀请进来的成员，二者的
权限模型完全不对称——owner 管全局，成员只在被分配的知识库范围内做事。

技术方案见 [../../design/20260813-workspace-member-access/tech-design.md](../../design/20260813-workspace-member-access/tech-design.md)。

## 1. 角色

只有两种角色，不做角色矩阵：

- **admin**（团队 owner）：实例里有且只有一个，就是第一个注册的账号。
  隐式拥有一切权限——所有知识库的增删改查、成员管理、实例设置——不需要、
  也不允许被显式授权或撤权。
- **member**（团队成员）：默认对任何知识库都没有访问权限，权限来自 admin
  的显式分配。看不到未分配给自己的知识库，包括在书架、Explore、搜索
  （含 RAG 检索）里都不出现。

不做团队/多租户，不做自定义角色。`admin` 单例这条要在后端强约束，
不能通过 Member 页或 API 把第二个账号的角色改成 ADMIN——这不是留白，
是防止"隐式全权"意外长出第二份。

## 2. 知识库授权

- **知识库只能由 admin 创建**，member 没有建库入口。
- **知识库标题全局唯一**，不再按创建者区分同名库（现状是按
  `(创建者, 标题)` 查重，见
  [hierarchy-and-workspaces.md](hierarchy-and-workspaces.md)）。
- admin 把知识库分配给成员，分配是**成员级**的（哪个人能进哪个库），
  不做知识库内的文件夹级/文档级授权——那是后续阶段的收紧方向，见 §5。
- 库级管理操作（改名、删除、改设置、文件夹增删、分配/取消分配成员）
  **只有 admin 能做**，被分配的成员即使给了读写权限也碰不到这些操作。
- 成员对被分配的库，默认拿到的是**文档级读写**：能新建、编辑、删除库内
  文档（不含移出库/删库这类库级操作），第一期不区分"只读成员"和
  "可写成员"——这个区分留到 §5 的收紧阶段。

## 3. 库内文档可见性

文档已有的 `visibility`（PRIVATE / PROTECTED / PUBLIC）**降级为库内语义**，
不再是实例范围的语义：

- 先判"这个人对这个库有没有访问权限"（库级前置闸门）。
- 通过之后，再按 visibility 判库内可见性：
  - PRIVATE：仅作者本人 + admin。
  - PROTECTED：**本库内**有访问权限的成员都能看（现状是"全实例登录用户
    都能看"，这是需要一并收紧的口子，见 §6）。
  - PUBLIC：保持匿名可读，分享链接机制不变。

附件跟着文档走同一套判断，不能出现"文档看不到、附件直链能下"的情况。

## 4. 成员生命周期

Member 页（admin 专用）继续管理成员账号，新增"分配知识库"的动作。

- **归档（archive）**：账号登录被切断，但对知识库的授权记录原样保留。
  重新恢复（restore）后授权自动生效，不用重新分配。
- **删除（delete）**：授权记录级联清除。该成员创建的文档**不删除**，
  署名（`creator_id`）转给 admin，文档留在原知识库里，视为团队资产。
  这是"人可以走，文档留给团队"的落地方式——不是把知识库的归属改成
  admin（知识库本来就只由 admin 管理），而是把这批文档的作者身份
  收归 admin，避免出现"作者是一个已经不存在的账号"这种悬空引用。

admin 自己的密码在 my-account 里改，不在 Member 页里对自己操作
（Member 页对当前登录用户那一行本来就不出操作菜单）。

## 5. 后续收紧方向（不在本期）

现在的"分配到库 = 库内文档最大读写"是第一期的粗粒度方案。后续按需收紧成
"整库只读 + 部分文档标记为可写"，即在文档（或文件夹）粒度上叠加一层授权，
和库级授权用同一套 subject/role 语义，届时角色也会从"读写"细分出
"只读 / 可写"两档。这条路径要在数据结构设计时预留，不需要现在实现。

## 6. 与现状的差异（需要一并修的口子）

当前代码里 PROTECTED 文档是"任何登录用户可读"，RAG 检索的过滤条件也是
按这个语义写的（`creator_id == me || visibility in [PUBLIC, PROTECTED]`），
完全不看知识库归属。上线本方案前，这个口子必须先堵上，否则"分配知识库"
形同虚设——一个只被分配了库 A 的成员，理论上仍能通过直接访问文档 ID
或者搜索命中库 B 里的 PROTECTED 文档。这不是新增需求，是修复现状缺陷，
纳入技术方案的第一阶段。

## 7. 已知问题（暂不处理）

**secret block（toucan-secret 加密块）与库级授权脱节**：被分配了知识库
读写权限的 member，仍然读不到库内别人创建的 secret block，会报
"This secret block does not exist in the current instance"。

根因：secret block 的记录查询按 `creator_id` 过滤
（`server/router/api/v1/secret_block_service.go`），完全不看调用方对
所在知识库的访问权限；解密口令也是每用户各自的主密钥（PBKDF2 包裹，
存在 `{user}/settings/SECRET_KEY`），不存在"库内共享口令"这一说。也就是
说即使把 creator_id 过滤放开，member 也没有口令可解密——这是两层问题
叠在一起：一是可见性按创建者而非库授权判断，二是加密模型本身是端到端
的用户级密钥，没有库级共享密钥的设计。

目前影响不大（secret block 使用场景有限），暂不处理，留到后续和 §5
的文档级授权收紧一起考虑对策，届时需要重新设计密钥共享机制（比如库内
成员间的密钥分发），而不只是放开查询过滤条件。

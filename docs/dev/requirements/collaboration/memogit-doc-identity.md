# memogit：文档身份标记与移动语义

`memogit` 检出的每个文档文件都带一个本地专用的身份标记，使 `mv`/重命名在 push
时被正确识别成"移动"，而不是退化成"归档旧文档 + 新建一份"。选型依据见
[ADR-0007](../../adr/0007-memogit-doc-identity-marker-in-file.md)；这里描述标记
本身的编码规则、身份解析算法与已知边界。

## 1. 为什么移动必须被正确识别

如果把 `mv` 误判成"旧文档消失 + 新文档出现"，新建的 memo 会拿到全新 uid，以下
内容全部留在被误判归档的旧 memo 上，且不会自动迁移：

| 数据 | 后果 |
|---|---|
| 版本历史（`memo_history`） | 新文档历史清零 |
| 备注/评论、reactions | 挂在旧 memo 上，新文档看不到 |
| 其他文档对它的引用/链接 | 断链，指向已归档文档 |
| 分享链接 | 失效 |
| `node_overlays`、pinned、visibility、创建时间 | 丢失/重置 |

pull 方向本来就是对的（服务端移动 → 本地跟着移动，是真正的原地搬移）；缺陷只
在 push 方向。

## 2. 为什么身份必须写进文件本身，而不是靠事后配对

要把"消失的旧路径"和"出现的新路径"配成一对，候选方案：

| 方案 | 结论 |
|---|---|
| 内容哈希配对 | 不成立："先改后移"和"先移后改"都会让内容对不上 |
| git rename 检测（`--find-renames`） | 不成立：相似度启发式，改动大就失效 |
| 身份随文件走（写进文件） | 采纳：唯一在任意编辑顺序下都成立的方案 |

文档身份是客观事实，应该被记录，而不是被推断。

## 3. 标记的两种编码

实现见 `internal/memogit/localid.go`。

| doc_type | 标记 | 位置 |
|---|---|---|
| `MARKDOWN` / `HTML` / `PDF` | `<!-- memogit-id: memos/<uid> -->` | 文件最后一行 |
| `VIEW`（`.view.json`） | `"memogit-id": "memos/<uid>",` | JSON 对象内的第一个键 |

**为什么在文件末尾，不在开头**：文件的第一个 `---` 块永远保留给用户自己的
Obsidian frontmatter，标记绝不能出现在那之前，否则会打断那个块的解析。

**为什么 VIEW 单独处理**：`.view.json` 会被 agent 和 linter 当 JSON 解析，尾部
挂一段 HTML 注释会让它变成非法 JSON；做成顶层键则文件仍然合法，gallery
解析器只读 `viewType`/`blocks`，多一个键无害。插入点是跳过可选的 `---`
frontmatter 块后的第一个 `{`；找不到合法对象就原样返回，不去改动畸形文件，
退化为按路径跟踪。

## 4. 不变式：`StripLocalID(InjectLocalID(x)) == x`

这条必须逐字节成立——一旦破了，每个同步过的文件都会显得"本地已修改"，push
会开始伪造冲突。因此：

- 注入只有一个出口：`InjectLocalID` / `FileContent`。
- 剥离只有一个入口：`StripLocalID`，所有本地文件哈希计算都必须先过这一步
  （`localHash()`）。
- VIEW 的 JSON 形式连同前导换行和尾随逗号一起匹配删除，保证是插入的精确逆
  运算。

标记只存在于本地文件：push 前剥离，服务端 `content` 永远不含它；网页端对
view 的任何重新序列化都不会影响它。

## 5. 存量检出的补写

老检出的文件没有标记。`pull` 结束前会跑一次 `ensureLocalIDs`：逐个读取被跟踪
文件，标记缺失或指向错误 uid 就重写。因为哈希前会先剥离标记，补写本身不会被
判定为本地修改。这不是一次性的 schema 迁移，而是**每次 pull 都做**——用户手滑
删掉标记也能自愈，代价是每次 pull 多一次小文件读取，可忽略。

## 6. push 的身份解析

push 在遍历文件与基线之前，先做一个纯函数、无网络的身份解析阶段
(`resolveIdentities`)：

```
1. 文件自带的标记优先——这是唯一能在移动中存活的信号
2. 标记指向未跟踪的 memo（从别处复制来的、服务端已归档的）→ 不采信
3. 一个 uid 被两个文件认领 = 复制，不是移动：停在基线路径上的那份是正主，
   其余按新文档创建
4. 没有标记的文件退回路径索引（老检出的行为不回归）
5. 都不匹配 → 新文档
```

解析结果驱动后续动作：

| 情况 | 动作 |
|---|---|
| 解析出 uid 且路径与基线不同 | `MoveMemo`（`update_mask=[folder_path, title]`），uid 不变 |
| 移动 + 内容也变了 | 移动和内容更新是两件独立的事，都做，顺序无关 |
| 归档判定 | 按被认领的 uid 判断，不再按路径——移动过的文件不会被误判为删除 |

`memogit status` 复用同一套解析逻辑，用于展示"旧路径 → 新路径"，与 `push`
的口径保持一致。

`moveDoc` 会校验服务端返回的 memo 映射到的本地路径是否等于文件当前路径，不等
就明确报错——用"映射后的本地路径"而不是裸字段比较，可以顺带吸收服务端的
folder path 归一化和文件名清洗差异，防止旧版本服务端对不认识的 `update_mask`
路径静默跳过、被误记为"已完成"、下次 pull 又把文件拖回原处。

## 7. 已知边界

- 两个文件互换路径会撞上服务端 `(workspace, folder_path, title)` 唯一约束，
  第一次移动就报错；分两次 push 可绕开。
- 归档不腾出名字：归档文档仍占用 `(folder_path, title)`，删掉某文档后不能
  立刻用同名新建。
- 移动会把标题规范化：本地文件名是清洗过的，移动时按文件名回写 title，带
  保留字符的标题会在移动后被改成清洗后的形式，与新建时的行为一致。

# 对外站点的门面（Site Front-End）

对外站点的读者看到什么、作者能编排到什么程度。

与 [20260823-public-blog-publishing.md](20260823-public-blog-publishing.md) 的分工：
那篇管**发布这件事本身**——什么是快照、检查什么、slug 怎么定、站点和知识库的
关系；本篇管**发布出去之后长什么样**——导航、首页编排、主题、卡片。两篇合起来
才是一块完整能力，边界是"这条规则改的是内容能不能出去，还是出去之后怎么呈现"。

实施方案属于 [../design/20260823-public-publishing/front-end.md](../design/20260823-public-publishing/front-end.md)。

## 1. 门面分三层，`.view` 只占中间一层

这是本篇最重要的一条结论，其余都从它推出来。

| 层 | 是什么 | 存在哪 | 谁改 |
|---|---|---|---|
| **外壳** | 顶部菜单、导航树、页脚、主题 | 站点配置 | admin 在站点设置里改 |
| **编排** | 首页从上到下有哪些块 | dashboard 那篇 `.view` 文档 | 作者在文档编辑器里改 |
| **皮肤** | 这些东西具体长什么样 | 代码 | 开发 |

**外壳不能放进 `.view`。** 顶部菜单和导航树在**每一个**对外页面上都要出现——
文章页 `/<slug>`、搜索页、目录页都要有，而这些页面根本不渲染 dashboard 那篇
`.view`。硬塞的做法是每个页面都先去取一遍 dashboard 文档、只为读它的导航配置，
既别扭又多一次请求。主题同理：文章页也要按站点主题渲染。

所以 `.view` 承担的是"首页这一页的内容"，不是"整个站点的前端"。

> 与早期设想的差异：一开始想的是"dashboard 那篇 `.view` 就是站点门面的全部"。
> 做出前端原型之后这条不成立——门面里有一半东西的生命周期是**站点级**的，
> 不是**文档级**的。

## 2. 站点外壳

**顶部菜单是站点配置里的一个有序列表**，每项是"显示名 + 指向哪"。不自动从
内容推导——推导出来的导航永远差一口气，而这是读者进站第一眼看到的东西。

站点默认给两项（`Latest`、`Docs`）加一个搜索入口，但这只是初始值，作者可以删可以加。
搜索入口是不是显示，由站点决定（站点搜索见发布那篇 §7）。

页脚只放站点名和一句说明。**不放 RSS、不放订阅、不放"由 XXX 强力驱动"**——
前两个是发布那篇 §12 明确不做的博客社区形态，第三个是拿读者的页面给自己打广告。

## 3. 导航树（层级目录）

站点可以有一棵**作者手写的**导航树：分节、节里列文章，两到三层。

**树是作者写的，不从源文档的目录结构推。** 三个原因，任一条都足够：

- 发布路径与编写路径解耦（发布那篇 §4）。为了对外目录好看去迁就知识库里的
  目录结构，正是那条约束要挡的事。
- 站点可以汇聚多个知识库的文档，这时候**根本不存在一棵共同的源目录树**。
- 站点上收哪几篇、按什么顺序读，本来就是编排决定，不是存放位置决定。

**树只是导航，不是地址。** URL 仍然是扁平的 `/<slug>`（发布那篇 §4），
一篇文章挂在树的哪一节不影响它的地址，也允许一篇同时出现在两节里，
或者一篇都不挂——不挂的文章仍然能被搜索和 feed 找到。

树里指向一篇未发布到本站点的文章时，**这一项不渲染**，不显示成死链。
与发布检查的区别在于：正文里的引用链到未发布文档是**发布失败**（发布那篇 §9），
因为那是作者写在内容里的承诺；导航树是编排，编排里多一条暂时空着的项很正常。

## 4. 首页编排：三种块

dashboard 那篇 `.view` 的 content 是一个块数组，从上到下渲染。三种块：

- **markdown 块**：作者写的文字——分节标题、开场白、两块之间的说明。
  走和普通文档同一套 markdown 渲染，但标题用站点自己的字号（见 §6）。
- **gallery 块**：卡片墙。少数几张宽卡片，用来放精选。
- **feed 块**：纵向条目列表，左栏可选一个主题筛选。

**这三种块可以任意组合、重复。** 「标题 + 精选卡片 + 全部文章的 feed」只是一种
排法，不是版式模板；换成「feed 在前」「两个 gallery 分别放不同 tag」「整页只有
一段说明文字」都应该成立。编排是数据，不是版式选项。

### 块的配置项

| | gallery 块 | feed 块 |
|---|---|---|
| 范围 | tags（留空 = 全站） | tags（留空 = 全站） |
| 排序 | 手工指定顺序，或按最后更新倒序 | 同左 |
| 数量 | 可限制 | 可限制 |
| 呈现 | 列数 2/3/4 | 是否显示主题筛选栏 |

**没有 folder 规则，也没有 property 规则。** 库内的 gallery view 有这两种 scope
规则（见 [views/gallery-view.md](views/gallery-view.md) §3），对外一条都不能有——
快照里既没有目录位置，也没有 frontmatter 属性（内部元信息不出站，发布那篇 §9），
这两种规则在对外侧没有东西可以匹配。tags 是快照唯一携带的分组。

这不是"对外先少做两种规则"，是**这两种规则在对外侧不存在语义**。

### 数据源

**任何对外块的数据源都只能是本站点的发布记录集合。** 这条重复自发布那篇 §6，
在这里再写一遍是因为它是编排能力最容易被绕过的地方：块的配置越像库内那套，
越容易顺手把库内的查询接过来用。

判据很简单：对外页面的任何查询**都不接触知识库的文档表**。未发布内容不是被
条件挡住的，是压根不在查询范围里。

### dashboard 的更新语义

排版配置走快照（改了版式要点更新发布才生效），块里列出的条目是实时的
（新发一篇文章首页立刻出现）。这是发布那篇 §5 快照规则唯一的例外，理由在那边。

## 5. 皮肤：对外和库内是两套

对外的呈现**不复用库内的卡片组件**，是并存的另一套。

理由不是"想让它更好看"，是两边优化的目标相反：库内的卡片墙服务的是"在自己的
文件里找东西"，密度是它的价值，一屏能看到的越多越好；对外的卡片服务的是
"决定要不要读这一篇"，一屏放三张宽卡片、留白多、每张有明确的阅读入口。
把这两个目标塞进同一组组件，最后会变成一堆互相打架的密度参数。

共享的是下面这些，且只有这些：**块编排这个思路**、**正文的 markdown 渲染器**、
以及**配置解析要做兜底**这条工程约定。

## 6. 主题

**主题是一组受限的配置项，不是一段 CSS。** 允许作者定的是：配色、显示字体与
正文字体、圆角、卡片比例、内容最大宽度、留白密度这一类具名的值。
不允许任意 CSS、任意 HTML、任意 JS——理由和 gallery view 不许存渲染产物是同一条
（存储型 XSS），见 [views/gallery-view.md](views/gallery-view.md) §1。

**主题由站点决定，不受读者本地偏好影响。** 应用里那套主题切换挂在登录用户的
偏好上，对外站点没有登录用户；而且一个站点在不同读者眼里长得不一样，本身就不
是发布方想要的。所以对外页面**不读应用的主题**，一个变量都不读。

字体分两个角色：**显示字体**用在站点名、大标题、卡片标题，**正文字体**用在段落
和小字。这是站点气质最主要的来源，也是最应该让作者能换的一项。字体的取值基准
按西文定，理由见 §9。

## 7. 正文渲染复用，不重写

文章正文走应用自己的 markdown 渲染器（发布那篇 §11 已定），皮肤只改正文**外面**
的东西：栏宽、字号、页头页脚。

不重写的理由是**防漂移**：一旦对外有了第二个渲染器，编辑器里新增的块（sheets、
calendar、draw.io……）就要在两边各做一次，做漏一次读者看到的就和作者写的不一样。

代价是那个渲染器是按应用的主题变量写的，所以对外页面要把这些变量重新映射到
站点主题上（这属于实现，见 design）。

## 8. 卡片封面

gallery 块的卡片要有封面图，**封面在发布时确定并存进快照**，不是渲染时回源文档
去找。回源是不行的：源文档发布之后还会改，图换了、删了，线上卡片就跟着变或者
坏掉，这与快照模型直接冲突。

取值顺序：作者在 frontmatter 里显式指定的封面（走对外白名单放行）→ 正文里第一张
图 → 没有图就不显示图片位。**没有封面不是错误**，卡片要能在没有图的情况下依然
成立。

封面引用的附件同样适用发布那篇 §9 的规则：**发布不放开附件权限**。读者取不到的
封面，发布时列进"读者取不到"清单，由作者自己决定要不要把那个文件设成公开。

## 9. 站点语言：只有英文

**对外站点的界面只有英文，不提供语言选项。** 不跟应用的 i18n 走，不跟读者浏览器
的语言走，也不做站点级的语言配置——「Read article」「Last updated」
「Search this site」这些字就是写死的英文。

理由是这块能力的界面文案总共不到二十条，而支持第二种语言要付的是一整套对外
文案表 + 一个站点配置项 + 每加一个对外组件都要记得过一遍 i18n。为不到二十条字
背这套机制不划算。

由此还确定两件事：

- **字体先按拉丁文调**。字距、行高、字重的取值以英文长标题为准，中文靠字体栈
  兜底而不是反过来。显示字体上一个只有西文字形集的字体是可以接受的取舍。
- **默认值用英文写**。默认菜单项、空状态文案、新建站点时的占位内容都是英文。

**界面语言与内容语言是两回事。** 一篇中文文章发到站点上要能正常渲染，CJK 的
行高和标点不能崩——只是版式的**基准**按西文定。作者写的东西（站点名、说明、
markdown 块、导航树的节名）也全都是作者自己的语言，本节只管产品内置的那些字。

将来真要放开，是加一份文案表加一个站点字段，不用回头改结构；所以现在把文案
集中放在一处，而不是散在各个组件里。

## 10. 明确不做

- **读者侧的主题切换**（深色模式开关、字号调节）。站点长什么样是发布方的决定；
  真要做也是站点配置里"允许读者切"这个开关，不是默认给。
- **作者写任意 CSS / HTML / JS**（§6）。
- **可视化拖拽排版**。块是一个有序数组，用现有的表单编辑就够；上拖拽是另一个
  量级的工程，而首页的改动频率极低。
- **自动生成导航树**（§3）。
- **首页出现未发布内容的占位**（"敬请期待"这类）。首页只反映已经发布的东西。

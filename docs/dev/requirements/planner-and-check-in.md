# 计划与打卡工具（头脑风暴）

> 状态：**头脑风暴，未排期、未实现**。本篇只记方向和待回答的问题，细节以后慢慢补。
> 2026-10-17 起草。

## 1. 为什么做

- **这是做 app 端的初衷，也是项目成败的关键指标（KPI）**。
- 现在的做法是在 web 端用 Markdown 记：文档里写 calendar 块
  （[editor/calendar-block.md](editor/calendar-block.md)），用 `- [ ]` 记任务，
  用 `@事件` 打卡。这其实是偷懒：
  - 数据在 Markdown 文本里，查询、统计、提醒都只能先解析文本。
  - 手机上不好写，打卡要进文档、找到当天的位置。
  - 没有提醒，也没有重复任务。
- 目标是一个多功能的每日计划与打卡备忘工具，大致是这几样的合体：
  - **提醒事项**（类似 Apple Reminders）：到点提醒、重复。
  - **任务清单**（类似 Google Tasks）：清单、子任务、截止日期、完成状态。
  - **日历预览与打卡**：月历上看每天的计划和完成情况，习惯类事项每天打卡。
  - **每日计划**：每天早上排当天要做什么，晚上回顾。

## 2. 已定的方向

- **以 app 为主，web 端兼容**：主要在手机上用，web 端能看、能改，但不是主战场。
- **数据不放在 Markdown 里**：用一套独立的表结构存，不再解析文档正文。
  （按仓库规则，表结构只加在 `store/migration/sqlite/` 和 `LATEST.sql`。）

## 3. 待回答的问题

**产品**
- KPI 具体指什么：每天打开的天数、每天打卡数、计划完成率，还是连续打卡天数？
  这决定了首页先放什么。
- 任务、提醒、打卡三者的边界：习惯打卡算不算一种重复任务？
  "每日计划"是独立的东西，还是"今天要做的任务"这个视图？
- 任务和知识库文档的关系：任务能不能链接到文档？
  文档里的 `- [ ]` 要不要汇总进来？还是两边完全独立？
- 现有 calendar 块里的历史数据：迁移到新表、只读保留，还是两者并存？
- 是否和 Google Tasks、Apple 提醒事项、日历做导入导出或同步。
- 是否只给自己用，还是要支持团队成员之间共享清单、指派任务。
- agent 能不能通过 MCP 或 memogit 读写任务（比如让 agent 帮忙排计划）。

**技术**
- "app 端"是什么形态：
  - 延续一期的手机 Safari 加"添加到主屏幕"（PWA），还是要做原生 app？
  - **提醒是关键约束**：PWA 的推送通知在 iOS 16.4 以后才支持，而且只在
    "添加到主屏幕"后可用，需要用户授权，后端也要加 Web Push。
    做不到可靠提醒的话，"提醒事项"这一块就站不住，这可能是决定形态的那个问题。
- 离线：地铁里打卡、没网时勾任务，要不要支持离线写、联网后同步。
- 时区和"一天"的边界：跨时区出差、凌晨打卡算哪一天。
- 重复规则的表达（每天、工作日、每周几、每月几号），以及改一次和改全部的区别。

## 4. 数据模型草图（未定稿）

只是为了讨论，名字和字段都会变：

- **清单（list）**：名称、颜色、排序。
- **任务（task）**：所属清单、标题、备注、截止日期或时间、重复规则、
  状态（可沿用 `utils/task-status.ts` 的多状态）、父任务（子任务）、可选关联文档。
- **提醒（reminder）**：所属任务、触发时间、是否已推送。
- **习惯（habit）**：名称、颜色、目标频率（例如每周 3 次）。
  对应 calendar 块里的 `events:`。
- **打卡记录（check-in）**：习惯或任务、日期、完成时间、备注。
- **每日计划（daily plan）**：日期、当天选入的任务及顺序、晚间回顾。

# 计划与打卡工具

> 状态：**已上线**（手机端"计划"Tab）。第 2 节是已经定下的需求。
> 2026-10-17 起草。

## 1. 为什么做

- **这是做 app 端的初衷，也是项目成败的关键指标（KPI）**。
- 现在的做法是在 web 端的文档里写 calendar 块（[editor/calendar-block.md](editor/calendar-block.md)），
  用 `- [ ]` 记任务、`@事件` 打卡。这是偷懒的做法：数据在 Markdown 文本里，手机上写不方便，
  也没法查询和统计。
- 要解决的场景：
  - 脑子里一有对未来一周的安排，**马上能在手机上放到合适的那一天**。
  - 闲下来时看一眼近期计划，**分出轻重就能开始干**。
- 为什么不用 Google Tasks：
  - 几个关联度不高的任务并行时，明明没几个，看起来就很乱。把不同维度的事放到日历上更好管理。
  - Tasks 不常打开，任务做完了也没人去关，一直挂着不闭合。
  - 这个页面每天都要打卡，所以会经常打开，任务也就会被经常看到、及时关掉。

## 2. 已定的需求

### 2.1 形态与范围

- **只做网页（PWA）**，不考虑原生 app。手机端为主，用"添加到主屏幕"的方式使用。
- **web 端本期不做**。手机上用稳定了，再考虑 web 端兼容。
- **数据属于个人**，不挂在知识库下。和知识库在同一个数据库里，但是一套完全独立的业务表。
  按仓库规则，表结构只加在 `store/migration/sqlite/` 和 `LATEST.sql`。
- **入口**：手机端底部 Tab 新增一页，放在"书架"右边。

### 2.2 三种记录

过去在 calendar 块里，凡是不关联 event 的条目都写成了待办。新工具把它们分成三种：

| 种类 | 是什么 | 怎么结束 | 重要度 |
|---|---|---|---|
| **打卡（event）** | 对长期习惯的履约记录，记录今天做了哪件长期坚持的事 | 记下就完成 | 最重要，一直在用 |
| **待办（todo）** | 提前定下的计划 | 完成，或者取消（取消必须写原因） | 最重要，一直在用 |
| **备忘（memo）** | 简单记一下发生了什么 | 记下就完成 | 次要 |

- **打卡**：
  - 现有 calendar 块的打卡功能已经满足需要，**照搬过来，只做数据迁移**。
  - 习惯（`events:` 列表）有名称和顺序，可以带 emoji。
  - 一条打卡记录可以带一句备注。现有数据里有 `@1 备注` 这种写法。
  - 每周的履行度看日历上的彩色圆点，自己心里统计就够了。**本期不做统计，也不设每周目标次数**。
- **待办**：
  - 只要还没走到终点（完成或取消），就一直挂着，不管日期过没过。
  - **状态**（见 2.3）。取消必须写原因。
  - 没有"延后"状态：当天没做完，要么继续挂着（过期），要么取消；以后真要做，在那天重新记一条。
  - 字段（除标题外都可选）：
    - 日期：放在日历的哪一天；
    - 备注；
    - 关联知识库文档（点了在手机端内跳转阅读）；
    - 外部链接；
    - **重要程度**：只有"重要 / 普通"两档，默认普通。录入时不填，只有进详情页才能改；
    - **标签（tag）**：本期只是一个字段，界面上暂不按标签区分显示，用一段时间后再定怎么用。
- **备忘**：只有日期和内容。

### 2.3 待办的状态

| 状态 | 含义 | 怎么进入 |
|---|---|---|
| **进行中** | 定下了，还没到终点 | 创建后就是进行中。"未开始"和"进行中"不区分 |
| **已过期** | 进行中，但日期已经过了 | 自动：日期早于今天就是过期，不用手动改 |
| **已完成** | 做完了 | 手动 |
| **已取消** | 不做了 | 手动，必须写原因 |

- 实际存的只有三种：进行中、已完成、已取消。"已过期"由日期算出来，所以过了零点会自动变成过期。
- 另存一个字段 **"关闭时是否已过期"**：完成或取消的那一刻，日期是否已经过了。
  这样历史上哪些是按时关的、哪些是拖过期才关的，以后还查得到。
- 没有日期的待办永远不会过期。
- **延期**（2026-10-17 补充）：待办的日期就是截止日期。当天发现某件事做不完或者要往后放，
  在详情页"完成"下面点**延期**，给它重新定一个日期，很常见。
  - 只对进行中、有日期的待办；新日期可选明天、后天、下周一或自选，不能早于今天。
  - 只保留一个当前日期，日历、清单、过期都按它算。另记**原定日期**（第一次延期前的日期）
    和**延期次数**，只在详情页显示（如"原定 10/15 · 已延期 2 次"），用来看出哪些事一推再推。
  - 详情页的日期框照旧可改，用来纠正填错的日期，不算延期。

### 2.4 页面

- **上半部分：日历**。复刻现有 calendar 块的功能：
  - 月历网格，有打卡、有待办的日子打标记；
  - 点某一天，显示当天的打卡、待办、备忘，可以增删改；
  - 日历部分暂时不需要待办详情页那些新功能。
- **下半部分：待办清单**。列出所有没关闭的待办：
  - **按日期排序**，过期的在最前面；
  - **分组**（2026-10-23）：已过期、本周（今天起 7 天，不是自然周）、以后、无日期。选中今天时今天的待办已在上面列出，清单里不重复；
    选中别的日子时今天的待办在"本周"组里，日期写成"🟢今天"。
  - 点某条进入**待办详情**，维护上面 2.2 列出的字段。这是新功能。
- **过期没关的待办一直显示**，在清单里，也在"今天"那格里。
  这会影响使用，正好倒逼自己去处理：完成，或者取消并写明原因。
- **修改历史的限制**：沿用现有的 `allowMaxUpdateDays`（只能改最近 N 天），但只管打卡和备忘。
  待办不受限制，过期多久都能关掉。
- **允许没有日期的待办**：排在清单最后，日历上不显示。
- **一周从哪天开始**：有一个默认设置，日历上也可以随时切换。不同的标记看的周期可能不同。
  （2026-10-20 补充）默认设置存在服务端，所有设备和对外接口共用，见 2.4.3。
- **"一天"的边界**：按手机当地时间的零点划分。
- **2026-10-18 补充**：
  - "计划"是第一个 Tab，打开 app 默认进计划页。
  - 日历选中的日期和翻到的月份在这次使用期间记住：从待办详情等二级页面回来，还停在原来那天；
    重新打开 app，或者过了零点，回到今天。
  - **不能提前打卡**：打卡只记录已经发生的事，今天之后的日子不能打卡（备忘和待办不受限）。
  - 待办清单不重复列出上面"当天"已经显示的待办：选中今天时，今天的和过期的已在上面列出，清单里不再出现。
- **2026-10-20 补充**：当天列表里备忘条目前面用 📋 标出，和待办的圆圈区分开。

### 2.4.1 待办关联习惯（2026-10-19）

有些待办做完了，就等于某个习惯今天打了卡（比如待办"跑 10 公里"对应习惯"运动"）。让待办关联一个习惯，
完成待办时顺手把卡打上，不用再去日历上点一次。

- **一个待办最多关联一个习惯**，在待办详情里选"完成时打卡"。停用的习惯不能选。
- **完成待办就打卡**：打在完成那天（手机上的今天），不是待办上写的日期；打卡备注就是待办的名称。
  完成和打卡在服务端一次做完，不会只成功一半。
- **一个习惯同一时间只挂一个没关闭的待办**。否则完成第一个已经打了卡，第二个就没法再打。
- **习惯今天已经打过卡，就不能再被关联**。
- **习惯挂着没关闭的待办时，今天在日历上点这个习惯，弹出的是待办，不是打卡页**：只能在待办里完成，同时打卡。
  这样就不会出现"习惯打了卡、待办却没完成"。别的日子（补打过去几天的卡）照常打卡。
- **待办带出的打卡，点它打开的是那个待办**，不能在打卡页改备注或者撤销。
- **打过卡的待办不能重新打开，也不能取消、不能换关联的习惯，只能删除**。删除待办时连同它打的卡一起删，
  不受"只能改最近 N 天"的限制。
- 关联的习惯完成时已经停用了：待办照常完成，不打卡（停用的习惯不再接受打卡）。这样的待办和普通待办一样可以重新打开。
- 删除待办的按钮用红字。
- 日历下面的当天列表和待办清单里，关联了习惯的待办在标题后面显示"🔗 习惯名"（2026-10-20）。

> 这一节有几条已被 2.4.2 取代，见 2.4.2 第 6 小节。

### 2.4.2 习惯版本、每周目标与习惯待办（2026-10-20）

**为什么改**：日历每个格子底下固定 5 个圆点位，按所有习惯的排序一个萝卜一个坑，停用的习惯也占着位置和颜色，
第 6 个以后的习惯干脆不显示圆点。改成按版本：调整习惯就修订一个新版本，从生效那天起换成新的一组。

#### 1. 习惯池

- 习惯建了就不删，所有习惯组成一个只增不减、不重复的"习惯池"。
- 名称、表情、颜色是习惯自己的属性，随时能改，过去的记录也跟着显示新的，不用发新版本。
- **图标必填，名称可以不填**（2026-10-20 补充）：习惯的标题以一个表情开头，这个表情就是它的图标，后面的文字是名称，
  可以没有（例如只写"🚶🏻"）。编辑时分成"图标""名称"两格填。标题不以表情开头的老习惯，标题第一个字当图标。
- **颜色跟着习惯走**：一个习惯不管哪天都是同一种颜色。新建时自动挑一个当前版本里没人用的颜色，之后可以手动改。
- 不再有"停用"按钮。一个习惯在不在用，只看当天生效的版本里有没有它。

#### 2. 版本

- 一个版本（界面上叫"计划"）= 从习惯池里挑出的 n 个习惯（n ≤ 5，有顺序）+ 每个习惯可选的每周目标
  + 关联文档（2026-10-20 补充）。
- 某一天用的是"生效日期不晚于这天的最近一个版本"。
- **先存草稿，再启用**（2026-10-20 补充）：修订出来的计划先是草稿，不生效，可以反复修改或删除；
  在计划详情页点"启用"才生效。同一时间只有一份草稿，"修订"就是打开它（没有就从当前计划复制一份）。
- **生效日期就是启用那天**，不再手选。启用新计划的同时，旧计划从这天起停用；只有启用新计划才会停用旧计划。
- **启用后不能再改**：习惯、顺序、目标、关联文档都锁定，只能看。
- **一天只有一个版本**：同一天再启用一次，替换掉当天早些时候启用的那个（它一天都没完整用过，不进历史）。
- 启用会拿掉某个习惯、而这个习惯今天或以后还挂着习惯待办时，启用前先提示"这些待办会变成普通待办"，
  确认后这些待办解除关联。
- **圆点**：日历格子按当天版本里的顺序从左往右排，不留空位。颜色跟着习惯走，所以位置变了也认得出。
- **圆点改成图标**（2026-10-20 补充）：计划页的日历格子不再画彩色圆点，而是画当天打了卡的习惯的图标，
  按当天计划的顺序从左往右依次排、不留空位；格子宽度三等分，每个图标在自己那一份里居中，没排满也一样（超过三个换行）。图标本身就认得出是哪个习惯，不再靠位置和颜色。
  图标总在格子最下面一行；宽屏下中间最多两行文字，先放待办、不够再放备忘，关联了习惯的待办不进格子（它打了卡就是下面的图标）。
  宽屏下格子高度正好放下日期、两行文字和一行图标，不留白；日期右边“当天有待办”的方点从 4px 放大到 6px。
  （文档里的 calendar 块不变，仍是圆点。）
- **打卡按版本校验**：只有当天版本里的习惯才能打卡。
- **固定与折叠**（2026-10-23）：一个计划最多 10 个习惯（原来 5 个），其中最多 **3 个固定**到计划页。计划页当天那一行只放固定习惯的按钮，
  其余的收进最后一个"⋯"按钮，按钮上写"已打卡数/折叠数"（没打卡就只写折叠数；只数设了每周目标的折叠习惯，
  不设目标的照常折叠但不计数，全都不设目标时只显示"⋯"）；点开是一个弹窗，里面的习惯按钮和外面一样，点了照常打卡或定待办。
  日历格子里先画固定习惯、再画折叠习惯的图标（2026-10-24 起折叠的也画）；仍然一行三格，超过 3 个时前两格放图标、第三格写"+N"。
  打卡只看上面那排按钮和"⋯"弹窗，当天的待办 / 备忘列表里不列打卡（2026-10-24 试过列出折叠习惯的打卡，和"⋯"上的计数重复，撤掉了）。
  **当天列表的顺序**：习惯待办在最前，按今天计划里的习惯顺序（和上面的按钮一致），没完成的在前、完成 / 失败 / 取消的在这一组末尾；
  然后是普通待办（今天时先列过期的），最后是备忘。
  **固定是显示偏好，不跟版本走**（2026-10-24）：任何一天都按**今天生效的版本**决定哪些习惯固定、按它的顺序取前三个；
  那天的习惯不在今天版本的固定里就收进"⋯"。所以今天新固定一个习惯，翻到以前的日子也能看到它的按钮。
  那天有哪些习惯、每周目标、能不能打卡仍然按当天的版本。草稿要"启用"后才算数。新加进计划的习惯在固定不满 3 个时默认固定。已有的计划迁移时固定前 3 个。
- **颜色不再要求不同**（2026-10-23）：计划页用图标区分习惯，同一计划里的习惯可以同色。颜色仍保留，文档里的 calendar 块还用它画圆点。

#### 3. 每周目标

- 目标写在版本里（"🚶 每周 3 次"），不写在习惯上，所以改目标也是修订版本，旧的周按旧目标算。
- **一周按一个计划算**（2026-10-20 补充）：以这周最后一天生效的计划为准。周三启用新计划，这一整周（包括周一、周二）
  都按新计划的目标算；之前的周按旧计划。所以同一周里每一天显示的目标都一样。
- 一周从哪天开始，按计划设置里的默认值，不跟日历下面的临时切换走。
- 进度 = 那一周里这个习惯的打卡次数，直接打的和待办带出的都算。超额照写，例如"💪 3/2"。
- 显示在习惯待办那一行（见第 5 小节），按待办自己日期所在的那一周算。没设目标的只显示习惯，不显示数字。
- 也显示在日历下面**还没打卡的习惯按钮上**（2026-10-20 补充），例如"🚶🏻 2/3"，按选中那天所在的一周算。
  打过卡的按钮照旧显示打卡备注。

#### 4. 点习惯按钮

| 选中的日子 | 情况 | 弹出 |
|---|---|---|
| 今天 | 这个习惯有今天的习惯待办 | 这条待办，带"完成并打卡" |
| 今天 | 已经打过卡 | 原来的打卡窗口，改备注或撤销；如果是待办带出的打卡，打开那条待办 |
| 今天 | 都没有 | 选择：直接打卡，或创建今天的习惯待办 |
| 明天以后 | 这个习惯那天已经有习惯待办 | 这条待办 |
| 明天以后 | 没有 | 创建那天的习惯待办 |
| 过去 | 这个习惯那天有没完成的习惯待办 | 这条待办，带"补打卡"；补打后待办算完成（受"只能改最近 N 天"限制） |
| 过去 | 没有 | 只能直接打卡（照旧受"只能改最近 N 天"限制），不能创建待办 |

#### 5. 习惯待办

- 待办分两种：**普通待办**和**习惯待办**。习惯待办**只能从习惯按钮创建**，这是 app 里唯一的入口（bot 另有一个，见 2.4.5 §5）；普通待办的详情里不再有"完成时打卡"。
- 习惯待办一定有日期，就是创建时选中的那天。**同一个习惯同一天最多一条**。
- 标题默认填习惯名，可以改，例如"🚶 走 5 公里"。完成时打卡的备注就是这个标题。
- **只能在当天完成**：完成就是在待办自己的日期那天打卡。计划外的日子做了，就在那天直接打卡，只算进那一周的统计，
  不影响那条待办。例如周四的 🚶 待办，周三去走了，就是周三直接打卡；周四的待办还是周四的。
- **不能延期**：那天没打卡就是没打卡，算失败；想第二天做，就再建一条。
- **失败自动生效**：过了那天还没完成，就是"已失败"，不用手动处理。它从待办清单里消失，只在那天的日历里带失败标记；
  不能再完成，只能删除。"已失败"和"已过期"一样是按日期算出来的，不单独存。
- **忘了勾可以补**：在"只能改最近 N 天"范围内，点那天的习惯按钮会打开这条待办，带"补打卡"；补打后待办变成已完成，
  打卡记在那天。超过 N 天就改不了了。
- 列表里，习惯待办的标题后面显示关联的习惯和本周进度，例如"🔗 🚶 2/3"。详情页只读显示关联的习惯，不能改。
- 打过卡的习惯待办仍然不能重新打开、不能取消，只能删除，删除时连打卡一起删（同 2.4.1）。

#### 6. 取代 2.4.1 的地方

- "一个习惯同一时间只挂一个没关闭的待办"，改成"同一个习惯同一天最多一条"。
- "打在完成那天"，改成"打在待办自己的日期"：当天完成，或者在 N 天内补打。
- 普通待办详情里的"完成时打卡"去掉。2.4.1 时关联过习惯的待办，一律算作习惯待办。
- "停用的习惯不能选"，改成"不在当天版本里的习惯不能打卡"。

#### 7. 待办备注

- 平时是一块只读文字，高度随内容撑开，全部显示。
- 按简单 Markdown 渲染，只支持最常用的几种：段落和换行、加粗、斜体、行内代码、链接、无序和有序列表。网址可以点开。
- 点一下变成编辑框，但不弹键盘（方便滚动、选中复制）；再点一下才开始打字。离开时保存，和现在一样。

#### 8. 设置页

- 习惯一节改成"当前计划（10/20 起）"：它的习惯和目标，下面是它关联的文档，点开就能看。
- 再往下是草稿（有的话）或"修订"按钮。草稿页：从习惯池挑习惯（也可以新建）、调整顺序、设每周目标、
  关联文档；底部"保存草稿""启用""删除草稿"。
- 再往下是历史计划列表，历史习惯和当时关联的文档在这里看。
- 关联文档只是引用：文档内容在知识库里编辑，计划这边只决定关联哪几篇。
- 日历右上角的筛选，只列当前月份里出现过的习惯。

#### 9. 上线时的数据

- 自动生成两个版本：
  - "从最早那天起"：按现在的排序放前 5 个习惯，包括已停用的，保证过去的日历和现在一样；
  - "从上线那天起"：只放没停用的。
- 这样停用的习惯从上线当天起就不再占位置。

### 2.4.3 每周进度接口（2026-10-20）

toucan-base 的 Discord bot 要当健身监督：按每周进度提醒、周末评分；Claude Code 会话也要能问"这周、这个月履约得怎样"。
这个接口只读（bot 后来可以打卡，见 2.4.4）。达标判断必须和 app 上显示的一致，所以周怎么划、按哪个计划、怎么计数都由服务端算，调用方不自己拼。

#### 1. 每周第一天挪到服务端

- 计划设置里的"一周从哪天开始"原来存在每台手机本地，服务端不知道。现在存在服务端（用户设置 `PLANNER`），
  `GET/PATCH /api/v1/planner/settings`，所有设备共用。值：1 = 周一 … 7 = 周日，0 = 跟随实例设置。
- 老手机上已经选过的值，打开新版时自动上传一次（服务端还是 0 的时候），之后以服务端为准。
- 日历下面的临时切换不变，只影响日历怎么排，不影响周目标和进度。

#### 2. 接口

`PlannerService.GetWeekProgress`，`GET /api/v1/planner/weekProgress?date=YYYY-MM-DD&weeks=N`。

- `date`：调用方那边的今天。服务端不换算时区，调用方按自己的时区（bot 是温尼伯）算好再传。
- `weeks`：1～12，默认 1。返回 `date` 所在的周，再往前 N-1 周；第一项是本周，后面依次更早。
- 返回的每一周：
  - `weekStart` / `weekEnd`：按服务端的"每周第一天"划分；顶层 `weekStartDay` 是解析后的值（1～7，跟随实例时也给出实际的那天）。
  - `containsDate`、`daysLeft`：`date` 在不在这一周、这周还剩几天（含 `date` 当天）；更早的周是 false / 0。
  - `plan`：这周按哪个计划算，规则同 2.4.2 §3（周最后一天生效的那个）。`effectiveDate` 为空表示"从最早开始"的计划；
    计划没有名字，app 也是按生效日期称呼它。`replaced` 列出这周前几天用过、被它取代的计划的生效日期。
    `documents` 是计划关联的文档（名字和标题；调用方读不到的文档标题为空）。这周还没有任何计划时没有 `plan`。
  - `habits`：先按计划顺序列计划里的习惯，再列不在计划里、但这周打过卡的习惯（`inPlan: false`）。
    每个习惯有 `icon`、`label`（标题去掉图标的部分，可能为空）、`weeklyGoal`（计划没设目标、或习惯不在计划里时没有这个字段）、
    `checkInCount`（直接打的和待办带出的都算，和 app 的"2/3"一致，超额照写）、`checkIns`（日期、备注、带出它的待办；
    2026-10-20 起还有来源 `source` 和训练记录 `workout`，见 2.4.4）。
  - `habitTodos`：这周的习惯待办，按日期：标题、关联习惯、状态。状态 `ACTIVE` / `DONE` / `FAILED` / `CANCELLED`，
    以 `date` 为今天算：过了日子还没完成就是 `FAILED`（同 2.4.2 §5）。普通待办不在里面。
  - `notes`（2026-10-20 补充）：这周的备忘，每条 `date`、`content`，按日期排，同一天按记的先后。
    原因：习惯计划规定记了"病"或"旅行 到 YYYY-MM-DD"的备忘时 bot 要暂停提醒，而 bot 只调这一个接口。
    备忘原样返回，接口不解析内容；怎么读由调用方按计划文档的规则来。
- **不做判定**：及格、达标、连续几周这些规则写在知识库的习惯计划文档里（就是 `plan.documents`），随计划版本变，由调用方判断。

返回示例（每周第一天是周一；周三 10/21 启用了新计划，阅读被换下、加了走路）：

#### 3. 认证与范围

- REST 用个人访问令牌（PAT）：`Authorization: Bearer <PAT>`。返回的是令牌主人自己的计划。
- PAT 目前没有只读范围，技术上能调所有接口。约定：给 bot 单独建一个 PAT。原来约定 bot 只调这一个接口；
  2026-10-20 起 bot 可以打卡，约定改为只调计划的四个接口，见 2.4.4 §5。
- MCP 上是工具 `planner_get_week_progress`，只读，计划的其他操作都不进 MCP。原因和上下文成本见
  `docs/dev/adr/0020-mcp-planner-week-progress-read-only.md`；agent 怎么用写在 `docs/skill/references/mcp.md` §8。

### 2.4.4 训练记录挂在打卡上，bot 可以打卡（2026-10-20）

toucan-base 的 Discord bot（Jen）当健身教练：用户一边练一边在 Discord 里报每个动作，Jen 记下来。以前这份记录
写成 Markdown 存在 bot 那边，和计划页的打卡是两份，打卡还得用户自己再点一次。现在训练记录存在 ToucanShelf，
挂在打卡上，bot 练完直接打卡。决定和理由见 [ADR 0021](../adr/0021-bot-checks-in-with-workouts.md)，它部分取代了 ADR 0020
"agent 打卡就是造假""bot 只调一个接口"两条。

#### 1. 一次训练 = 一个打卡

- 打卡（习惯 + 日期）上可以带一份**训练记录** `workout`：总时长（分钟，可空）+ 动作列表。
- 动作的字段：名称（必填）、器械、重量（kg）、每组次数（如 15/12/12）、时长（分钟）、设置（坡度、阻力等，一段文字）、备注、
  动作库文档 `doc`（2026-10-24，见第 7 小节）。除了名称都可以不填。
- **不按动作拆习惯**：去健身房不分有氧无氧，整体算一次 💪；外面走路、滑冰、游泳算一次有氧。
  挂在哪个习惯由打卡的人定，服务端不判断。
- 只记事实，不判有效性：练够没有、算不算达标，由调用方按计划文档判断。服务端只挡明显的垃圾值
  （最多 30 个动作、每个动作最多 30 组、每组 0～1000 次、重量 0～1000 kg、时长 0～1440 分钟、名称器械设置最长 200 字、备注最长 500 字）。

#### 2. 来源

- 打卡多一个只读的来源 `source`：`MANUAL` 在 app 里点的、`TODO` 完成待办带出的、`AGENT` 程序打的。
- **服务端按凭证判定**，调用方不能自报：app 的登录会话是人，个人访问令牌（PAT，bot 用的）和 MCP 是 agent。
- 来源在第一次打卡时定下，之后谁改都不变（bot 给用户的打卡补训练记录，来源还是 `MANUAL`）。
- 上线前已有的打卡：待办带出的记 `TODO`，其余记 `MANUAL`。

#### 3. 谁能改什么

| | app（本人） | bot（PAT） |
|---|---|---|
| agent 打的卡 | 能看、改备注和训练记录、删除 | 能改、能删 |
| 手动打的卡 | 照旧 | 只能设训练记录，备注不动；不能删 |
| 待办带出的卡 | 只能改训练记录；备注是待办标题，要撤销就删待办（同 2.4.1） | 只能设训练记录，备注不动；不能删 |
| 习惯那天挂着没完成的习惯待办 | 照旧：只能在待办里完成 | 打卡就顺带完成这条待办，来源 `AGENT`；bot 删掉这个打卡，待办重新打开 |

- 不能提前打卡（同 2.4 的 2026-10-18 补充）。bot 按自己的时区传日期，服务端按全世界最早的时区（UTC+14）判"未来"。
- "只能改最近 N 天"是 app 上的限制，bot 不受。

#### 4. app

- 点开有训练记录的打卡、或者 agent 打的打卡，进**打卡详情页**：来源（agent 带 🤖）、完成的待办（有的话）、备注、
  总时长、动作列表。点动作可以改、删，也能添加动作。每次改动都把整份打卡（备注 + 完整训练记录）存回去。
  关联了动作库文档的动作，点名称打开文档，点其余地方改动作（第 7 小节）。
- 普通的打卡窗口多一个"训练明细 ›"，从这里给手动打的卡添加训练记录。
- 日历下面 agent 打的打卡按钮带 🤖。
- 不做统计（某个动作的重量曲线之类）。

#### 5. 接口

`PlannerService`，REST 用 PAT：`Authorization: Bearer <PAT>`（toucan-base 还要带 User-Agent，否则被 Cloudflare 拦）。
字段名 camelCase。约定 bot 只调这四个：

- **打卡 / 上报训练**：`POST /api/v1/planner/checkIns`，body 就是打卡本身：

  ```json
  {
    "habit": "planner/habits/run",
    "date": "2026-10-20",
    "note": "下肢 + 有氧",
    "workout": {
      "durationMinutes": 30,
      "exercises": [
        { "name": "跑步机", "equipment": "Spirit 跑步机", "durationMinutes": 5, "settings": "坡度 10，3.8–4 km/h" },
        { "name": "罗马尼亚硬拉", "equipment": "哑铃", "weightKg": 2.3, "reps": [15, 12, 12] }
      ]
    }
  }
  ```

  返回保存后的打卡（多 `todo`、`source`；没填的可选数字字段不出现，文字和数组给空值）。
  - **会话结束时一次上报**，不是每个动作报一次。按（习惯，日期）覆盖，所以**天然幂等**：重试、重复发送结果都一样。
    同一天第二次训练，要发合并后的完整列表。
  - 不带 `workout` 表示训练记录不动（只改备注）；带一个空的 `workout: {}` 表示删掉训练记录。
  - 习惯 `name` 从 `weekProgress` 的 `habits[].habit` 拿。
- **撤销**：`DELETE /api/v1/planner/checkIns?habit=planner/habits/run&date=2026-10-20`。那天本来没打卡也返回成功。
  删别人（app）打的卡返回 403。
- **拉近期训练**：`GET /api/v1/planner/workouts`，参数都可选：`startDate`、`endDate`（YYYY-MM-DD）、`habit`、
  `exercise`（动作名包含这段文字，不分大小写）、`doc`（含关联这篇动作库文档的动作，`memos/{uid}`，第 7 小节）、
  `limit`（1～200，默认 50）。只返回带训练记录的打卡，`{"checkIns": [...]}`，最新的在前（同一天按记录先后倒序）。
  "上次臀推多重"就是 `?doc=memos/{臀推攻略的 uid}&limit=1`；没关联文档的旧记录仍用 `?exercise=臀推`。
- **每周进度**：`GET /api/v1/planner/weekProgress`（2.4.3），打卡多了 `source` 和 `workout`。

错误：参数不对返回 400（`INVALID_ARGUMENT`），违反第 3 小节的规则返回 400（`FAILED_PRECONDITION`）或 403
（`PERMISSION_DENIED`），消息里写明原因。

#### 6. MCP

不加工具。`planner_get_week_progress` 的打卡已经带训练记录，Claude Code 问"这周练了什么"够用；
写入和 `ListWorkouts` 都不进 MCP（ADR 0021 第 4 条）。

#### 7. 动作库：动作关联攻略文档（2026-10-24）

动作名是自由文本，同一个动作每次叫法不同（"Hip thrust" / "Bench hip thrust"），按名字认不出是不是同一个动作。
用户在知识库里给每个动作写了一篇攻略（要点、常见错误、起始量、视频），**这些攻略文档就是动作库**，文档就是动作的身份。
不另建动作表。决定和理由见 [ADR 0023](../adr/0023-exercise-library-is-documents.md)。

- **攻略文档**：frontmatter 写 `kind: exercise`，可选 `group`（腿臀 | 推 | 拉 | 核心）和 `aliases`（别名列表，
  给 bot 和 app 匹配用）。放在哪个知识库、哪个文件夹都行（目前在 Life 知识库 `Health/Exercises/`）。
- **动作的 `doc`**：动作可以带 `doc`（`memos/{uid}`），指向它的攻略。打卡的训练记录和习惯待办的计划训练（2.4.5）
  共用这个结构，两处都有。
  - 名称照旧必填、自由文本，每次叫法可以不同。**认动作看 `doc`，不看名称。**
  - 不关联也行（例如热身走路），和以前一样。
- **写入校验**：`doc` 必须是调用者自己的、存在、未归档的文档，否则 400（`INVALID_ARGUMENT`），不静默丢弃。
  服务端不检查 frontmatter 有没有 `kind: exercise`：那是动作库列表的筛选条件，不是 `doc` 的合法性条件。
- **文档后来被归档或删除**：已存的 `doc` 保留，读出来照样返回；app 上动作名显示成普通文字（不能点）。
  重新保存同一份训练记录（例如在 app 上改另一个动作）时，原来已经挂着的 `doc` 不再校验，否则改不了别的动作；
  但不能把它新挂到别的动作、别的打卡或计划上。
  - 已知的边：计划里挂了一篇后来归档的文档，"按计划填"到一个新打卡会被拒（新打卡没有"原来已经挂着"的 `doc`），
    这时在计划里先取消关联再填。
- **app**（打卡详情、习惯待办的计划训练，两处一样）：
  - 有 `doc` 的动作，名称带链接样式，点名称打开那篇文档；点动作条的其他地方或右侧 › 进动作编辑。
  - 没有 `doc` 的动作和以前一样，点哪里都进编辑。
  - 动作编辑多一行"动作库"：从动作库选一篇（列出自己的、未归档的、带 `kind: exercise` 的文档，按 `group` 分组，
    能搜标题和别名），选了就填 `doc`，名称为空时（或还是上次选的文档标题时）自动填成文档标题，可以改；
    也可以不选、手写名称。已关联的可以改选或取消关联。
- **查询**：`ListWorkouts` 加 `doc` 参数（第 5 小节）。`weekProgress` 等返回训练的地方，动作都带 `doc`。
- **不做**：动作表、按动作的统计图；在计划页维护动作说明（写在文档里）；按名字自动猜 `doc`（旧数据由
  toucan-base 按 `aliases` 回填）；MCP 不变。

#### 8. 不同习惯记的字段不同：共用一套字段，编辑页按习惯显示（2026-10-24）

走路、健身、瑜伽要记的东西不一样（健身记重量组数，瑜伽记时长，走路几乎只记总时长）。

- **数据只有一套**：所有习惯共用 `Workout` / `WorkoutExercise` 这一套字段，除名称外都可空。服务端、bot、查询都不按习惯分支。
  缺的字段（例如距离）加进这一套里；训练存成 JSON，加字段不用迁移。
- **显示按习惯来，不用配置**：动作编辑页总是显示名称和备注，再加上**这个习惯最近 10 次训练里填过的字段**、这条动作本身有值的字段；
  其余的收在"更多字段（N）"后面，点开全部显示。健身自然显示重量、组数，瑜伽只显示时长。
- **字段名和中文名的映射只有一处**：`web/src/mobile/lib/workoutFields.ts` 的 `EXERCISE_FIELDS`，每个字段一行
  （key、中文名、占位、怎么读写、列表摘要里怎么写）。编辑页的输入框和动作列表的一行摘要都由它生成。
  加一个字段：proto + `store.PlannerExercise` + `planner_workout.go` 的校验和转换 + 这张表一行。

### 2.4.5 习惯待办挂训练计划，bot 可以排（2026-10-23）

用户在 Discord 里对 Jen 说"计划周六去健身房，帮我制定那天的锻炼计划"，Jen 排好一份动作清单。以前这份清单只留在聊天里：
周六在 app 里点开那天的"健身房打卡"待办看不到，练的时候也没法对着清单一项项做。训练记录已经挂在打卡上（2.4.4），
这次把**计划要练的**挂在习惯待办上，和**实际练的**（打卡上的训练记录）成对。决定和理由见
[ADR 0022](../adr/0022-bot-plans-workouts-on-habit-todos.md)。

#### 1. 计划训练 = 习惯待办上的一份训练

- 习惯待办可以带一份**计划训练** `plannedWorkout`，结构和 2.4.4 的 `workout` 完全一样（总时长 + 动作列表），
  校验上限也一样。动作同样可以带动作库文档 `doc`，校验和 app 上的点法同 2.4.4 §7。`reps` 在这里是目标次数，例如 2 轮每轮 12 下写 `[12, 12]`。
- 只有习惯待办能带，普通待办不能。
- 日期可以是未来（打卡不能提前，计划正是给未来用的）。
- 只是计划，不算打卡、不影响每周进度。
- 这次练的重点（例如"下肢为主，膝盖不舒服就换臀桥"）写在**待办备注**里，计划不另设备注。

#### 2. 两个来源

- **待办的来源** `Todo.source`：`MANUAL`（app 里建的）、`AGENT`（bot 用 PAT 建的）。只读，建的时候按凭证定下，之后不变。
  上线前已有的待办都是 `MANUAL`。决定 bot 能不能删这条待办。
- **计划的来源** `Todo.plannedWorkoutSource`：这份计划**最后一次**是谁设的，`MANUAL` 或 `AGENT`。app 上 bot 排的带 🤖。
  用户在 app 里改过计划，来源就变成 `MANUAL`；清空计划时来源一起清掉。
- 两个来源都按凭证判定（同 2.4.4 §2），调用方不能自报。

#### 3. 谁能改什么

| | app（本人） | bot（PAT） |
|---|---|---|
| 进行中的习惯待办 | 能看、改、清空计划 | 能设（整份替换）、能清空；标题、备注不动 |
| 没有那天的习惯待办 | — | 用户在聊天里同意日期后新建，见第 5 小节 |
| 已完成 / 已失败 / 已取消的习惯待办 | 只读 | 不能改（`FAILED_PRECONDITION`） |
| bot 建的待办（`source=AGENT`） | 照旧 | 能删 |
| app 里建的待办（`source=MANUAL`） | 照旧 | 不能删（`PERMISSION_DENIED`） |

#### 4. app

- 习惯待办详情页多一块"计划训练"：动作列表，和 2.4.4 打卡详情的动作列表长得一样，点动作可以改、删，也能添加动作。
  bot 排的标 🤖。待办完成、失败或取消后只读（关联了文档的动作名仍然能点开文档）。
- 完成这条待办以后，打卡详情页"训练明细"可以一键"按计划填"：把计划复制成训练记录的起点，再改实际做的数字。
  不自动复制：没练完的不能算进打卡。只在打卡还没有训练记录时出现。
- 日历格子里带计划的习惯待办的标记**先不做**：习惯待办不进格子，图标只给固定的习惯画（2.4.2），样式以后再定。

#### 5. bot 可以新建习惯待办

- 两种说法都要接住：
  - "周六去健身房，帮我排一下"：日期已经有了，直接排。
  - "下次健身练什么"：Jen 排好后**主动建议定个日期**（"Want me to put it on Saturday?"），用户同意才建。
    不定日期，计划就只留在聊天里，下次还得往上翻记录。
- 那天还没有这个习惯的待办，bot 就新建一条习惯待办再挂计划：标题默认习惯名，`source=AGENT`、带 🤖。
  这修改了 2.4.2"习惯待办只能从习惯按钮创建"：app 里仍然只能从习惯按钮建，PAT 另有这个入口。
- 只在用户在聊天里同意了具体日期时建；不能是过去的日期（按调用方传的 `localDate` 判断）。
  已有那天的待办就直接挂上，不重复建。
- 习惯必须在那天生效的计划里（同习惯待办的规则）。
- bot 建的待办，bot 能改计划、能删（用户反悔"周六不去了"）；用户在 app 里建的，bot 只能设计划，不能删。

#### 6. 接口

- **设计划**：`POST /api/v1/planner/plannedWorkouts`，body：

  ```json
  {
    "habit": "planner/habits/gym",
    "date": "2026-10-24",
    "localDate": "2026-10-23",
    "workout": {
      "durationMinutes": 60,
      "exercises": [
        { "name": "罗马尼亚硬拉", "equipment": "哑铃", "weightKg": 5, "reps": [12, 12] },
        { "name": "臀推", "reps": [15, 15, 15], "doc": "memos/abc123" }
      ]
    }
  }
  ```

  按（习惯，日期）找那条习惯待办（2.4.2：同一习惯同一天最多一条），整份替换，**天然幂等**；空的 `workout: {}` 清空。
  找不到就新建一条（第 5 小节）；清空时找不到不新建，直接返回成功、`todo` 为空。
  返回 `{"todo": {...}, "created": true}`，`created` 表示这次新建了待办。
  app 不用这个接口：app 在待办详情里用 `UpdateTodo`，update mask `planned_workout`。
- **删 bot 建的待办**：`DELETE /api/v1/planner/todos/{id}`，PAT 只能删 `source=AGENT` 的。
- **读**：`weekProgress` 的 `habitTodos[]` 多 `plannedWorkout`、`plannedWorkoutSource`、`source`。
  bot 在健身房带练时据此逐项对照，练完对账"计划里还差哪组"。
- MCP：`planner_get_week_progress` 自然带上，不加新工具。

### 2.4.6 备忘详情（2026-10-23）

- 点当天列表里的备忘，进入**备忘详情页**：内容（一句话）、日期、**备注**（较长的文字，可以写 Markdown）、**关联文档**（可以多篇，同待办）。
- 和日历一样受"只能改最近 N 天"限制：超出范围只能看，不能改，也不能删除。
- 周进度接口里的 `notes` 不带备注和关联文档，仍然只有 `date`、`content`。

### 2.5 KPI

- **每周有几天打开并打过卡**。这是刚需，会一直坚持下去。
- "打卡"就是 event 打卡，不包括勾掉待办。

### 2.6 数据迁移

- 上线时，用户从现有 calendar 块导出数据，在线上一次性导入（backfill）新表。
- **导出前先校对 `[ ]`**：以前没有备忘这一种，很多备忘被写成了 `[ ]`；
  过去没做完的待办也一直是 `[ ]`。导出前逐条判断（2026-10-17 已由 agent 校对过一遍）：
  - 其实是备忘的，改成不带方括号的纯文本条目 `- 内容`（calendar 块本来就支持这种写法）；
  - 过去没做完、已经不做的待办，改成 `[-]`；
  - 还在做的待办保持 `[ ]`。
  - 以前打卡不能写备注，备注只好单独写成一条待办（例如和 `@1` 同一天的一条待办其实是这次打卡的备注）。
    这种合并回当天的打卡：`@1 备注`。
- **转换规则**：

  | 原来的写法 | 导入成 |
  |---|---|
  | `@序号` / `@序号 备注` | 打卡（带备注） |
  | `- 内容`（不带方括号） | 备忘 |
  | `[ ]` | 待办，进行中（日期已过的就显示为已过期） |
  | `[x]` | 待办，已完成 |
  | `[-]` | 待办，已取消 |
  | `[>]`、`[?]`、`[!]`、`[/]`、`[<]` 等其他没完成的 | 待办，已取消 |
  | 只有日期、没有条目的日期行 | 丢弃 |

  - 导入的"已取消"一律记"关闭时已过期"，原因写"迁移时关闭"。
  - `[!]` 本来表示重要，导入后重要程度设为"重要"。
- 现有数据的格式特点，导入时要处理：
  - 习惯用 `@序号` 引用，有的带备注（`@1 备注`）；
  - 待办用到的状态有：`[ ]` 未开始、`[x]` 完成、`[-]` 作废、`[>]` 延后、`[?]` 有疑问、`[!]` 重要；
  - 有只有日期、没有任何条目的日期行；
  - 同一条待办会在不同日期重复出现。

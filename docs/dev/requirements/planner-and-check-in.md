# 计划与打卡工具

> 状态：**已上线**（手机端"计划"Tab）。第 2 节是已经定下的需求。
> 2026-10-17 起草。

## 1. 为什么做

- **这是做 app 端的初衷，也是项目成败的关键指标（KPI）**。
- 现在的做法是在 web 端的文档里写 calendar 块（[editor/calendar-block.md](editor/calendar-block.md)），
  用 `- [ ]` 记任务、`@事件` 打卡。这是偷懒的做法：数据在 Markdown 文本里，手机上写不方便，
  也没法查询和统计。
- 要解决的场景：
  - 脑子里一有对未来一周的安排，**马上能在手机上放到合适的那一天**。
  - 闲下来时看一眼近期计划，**分出轻重就能开始干**。
- 为什么不用 Google Tasks：
  - 几个关联度不高的任务并行时，明明没几个，看起来就很乱。把不同维度的事放到日历上更好管理。
  - Tasks 不常打开，任务做完了也没人去关，一直挂着不闭合。
  - 这个页面每天都要打卡，所以会经常打开，任务也就会被经常看到、及时关掉。

## 2. 已定的需求

### 2.1 形态与范围

- **只做网页（PWA）**，不考虑原生 app。手机端为主，用"添加到主屏幕"的方式使用。
- **web 端本期不做**。手机上用稳定了，再考虑 web 端兼容。
- **数据属于个人**，不挂在知识库下。和知识库在同一个数据库里，但是一套完全独立的业务表。
  按仓库规则，表结构只加在 `store/migration/sqlite/` 和 `LATEST.sql`。
- **入口**：手机端底部 Tab 新增一页，放在"书架"右边。

### 2.2 三种记录

过去在 calendar 块里，凡是不关联 event 的条目都写成了待办。新工具把它们分成三种：

| 种类 | 是什么 | 怎么结束 | 重要度 |
|---|---|---|---|
| **打卡（event）** | 对长期习惯的履约记录，记录今天做了哪件长期坚持的事 | 记下就完成 | 最重要，一直在用 |
| **待办（todo）** | 提前定下的计划 | 完成，或者取消（取消必须写原因） | 最重要，一直在用 |
| **备忘（memo）** | 简单记一下发生了什么 | 记下就完成 | 次要 |

- **打卡**：
  - 现有 calendar 块的打卡功能已经满足需要，**照搬过来，只做数据迁移**。
  - 习惯（`events:` 列表）有名称和顺序，可以带 emoji。
  - 一条打卡记录可以带一句备注。现有数据里有 `@1 备注` 这种写法。
  - 每周的履行度看日历上的彩色圆点，自己心里统计就够了。**本期不做统计，也不设每周目标次数**。
- **待办**：
  - 只要还没走到终点（完成或取消），就一直挂着，不管日期过没过。
  - **状态**（见 2.3）。取消必须写原因。
  - 没有"延后"状态：当天没做完，要么继续挂着（过期），要么取消；以后真要做，在那天重新记一条。
  - 字段（除标题外都可选）：
    - 日期：放在日历的哪一天；
    - 备注；
    - 关联知识库文档（点了在手机端内跳转阅读）；
    - 外部链接；
    - **重要程度**：只有"重要 / 普通"两档，默认普通。录入时不填，只有进详情页才能改；
    - **标签（tag）**：本期只是一个字段，界面上暂不按标签区分显示，用一段时间后再定怎么用。
- **备忘**：只有日期和内容。

### 2.3 待办的状态

| 状态 | 含义 | 怎么进入 |
|---|---|---|
| **进行中** | 定下了，还没到终点 | 创建后就是进行中。"未开始"和"进行中"不区分 |
| **已过期** | 进行中，但日期已经过了 | 自动：日期早于今天就是过期，不用手动改 |
| **已完成** | 做完了 | 手动 |
| **已取消** | 不做了 | 手动，必须写原因 |

- 实际存的只有三种：进行中、已完成、已取消。"已过期"由日期算出来，所以过了零点会自动变成过期。
- 另存一个字段 **"关闭时是否已过期"**：完成或取消的那一刻，日期是否已经过了。
  这样历史上哪些是按时关的、哪些是拖过期才关的，以后还查得到。
- 没有日期的待办永远不会过期。
- **延期**（2026-10-17 补充）：待办的日期就是截止日期。当天发现某件事做不完或者要往后放，
  在详情页"完成"下面点**延期**，给它重新定一个日期，很常见。
  - 只对进行中、有日期的待办；新日期可选明天、后天、下周一或自选，不能早于今天。
  - 只保留一个当前日期，日历、清单、过期都按它算。另记**原定日期**（第一次延期前的日期）
    和**延期次数**，只在详情页显示（如"原定 10/15 · 已延期 2 次"），用来看出哪些事一推再推。
  - 详情页的日期框照旧可改，用来纠正填错的日期，不算延期。

### 2.4 页面

- **上半部分：日历**。复刻现有 calendar 块的功能：
  - 月历网格，有打卡、有待办的日子打标记；
  - 点某一天，显示当天的打卡、待办、备忘，可以增删改；
  - 日历部分暂时不需要待办详情页那些新功能。
- **下半部分：待办清单**。列出所有没关闭的待办：
  - **按日期排序**，过期的在最前面；
  - 点某条进入**待办详情**，维护上面 2.2 列出的字段。这是新功能。
- **过期没关的待办一直显示**，在清单里，也在"今天"那格里。
  这会影响使用，正好倒逼自己去处理：完成，或者取消并写明原因。
- **修改历史的限制**：沿用现有的 `allowMaxUpdateDays`（只能改最近 N 天），但只管打卡和备忘。
  待办不受限制，过期多久都能关掉。
- **允许没有日期的待办**：排在清单最后，日历上不显示。
- **一周从哪天开始**：有一个默认设置，日历上也可以随时切换。不同的标记看的周期可能不同。
- **"一天"的边界**：按手机当地时间的零点划分。
- **2026-10-18 补充**：
  - "计划"是第一个 Tab，打开 app 默认进计划页。
  - 日历选中的日期和翻到的月份在这次使用期间记住：从待办详情等二级页面回来，还停在原来那天；
    重新打开 app，或者过了零点，回到今天。
  - **不能提前打卡**：打卡只记录已经发生的事，今天之后的日子不能打卡（备忘和待办不受限）。
  - 待办清单不重复列出上面"当天"已经显示的待办：选中今天时，今天的和过期的已在上面列出，清单里不再出现。
- **2026-10-20 补充**：当天列表里备忘条目前面用 📋 标出，和待办的圆圈区分开。

### 2.4.1 待办关联习惯（2026-10-19）

有些待办做完了，就等于某个习惯今天打了卡（比如待办"跑 10 公里"对应习惯"运动"）。让待办关联一个习惯，
完成待办时顺手把卡打上，不用再去日历上点一次。

- **一个待办最多关联一个习惯**，在待办详情里选"完成时打卡"。停用的习惯不能选。
- **完成待办就打卡**：打在完成那天（手机上的今天），不是待办上写的日期；打卡备注就是待办的名称。
  完成和打卡在服务端一次做完，不会只成功一半。
- **一个习惯同一时间只挂一个没关闭的待办**。否则完成第一个已经打了卡，第二个就没法再打。
- **习惯今天已经打过卡，就不能再被关联**。
- **习惯挂着没关闭的待办时，今天在日历上点这个习惯，弹出的是待办，不是打卡页**：只能在待办里完成，同时打卡。
  这样就不会出现"习惯打了卡、待办却没完成"。别的日子（补打过去几天的卡）照常打卡。
- **待办带出的打卡，点它打开的是那个待办**，不能在打卡页改备注或者撤销。
- **打过卡的待办不能重新打开，也不能取消、不能换关联的习惯，只能删除**。删除待办时连同它打的卡一起删，
  不受"只能改最近 N 天"的限制。
- 关联的习惯完成时已经停用了：待办照常完成，不打卡（停用的习惯不再接受打卡）。这样的待办和普通待办一样可以重新打开。
- 删除待办的按钮用红字。
- 日历下面的当天列表和待办清单里，关联了习惯的待办在标题后面显示"🔗 习惯名"（2026-10-20）。

> 这一节有几条已被 2.4.2 取代，见 2.4.2 第 6 小节。

### 2.4.2 习惯版本、每周目标与习惯待办（2026-10-20）

**为什么改**：日历每个格子底下固定 5 个圆点位，按所有习惯的排序一个萝卜一个坑，停用的习惯也占着位置和颜色，
第 6 个以后的习惯干脆不显示圆点。改成按版本：调整习惯就修订一个新版本，从生效那天起换成新的一组。

#### 1. 习惯池

- 习惯建了就不删，所有习惯组成一个只增不减、不重复的"习惯池"。
- 名称、表情、颜色是习惯自己的属性，随时能改，过去的记录也跟着显示新的，不用发新版本。
- **颜色跟着习惯走**：一个习惯不管哪天都是同一种颜色。新建时自动挑一个当前版本里没人用的颜色，之后可以手动改。
- 不再有"停用"按钮。一个习惯在不在用，只看当天生效的版本里有没有它。

#### 2. 版本

- 一个版本（界面上叫"计划"）= 从习惯池里挑出的 n 个习惯（n ≤ 5，有顺序）+ 每个习惯可选的每周目标
  + 关联文档（2026-10-20 补充）。
- 某一天用的是"生效日期不晚于这天的最近一个版本"。
- **先存草稿，再启用**（2026-10-20 补充）：修订出来的计划先是草稿，不生效，可以反复修改或删除；
  在计划详情页点"启用"才生效。同一时间只有一份草稿，"修订"就是打开它（没有就从当前计划复制一份）。
- **生效日期就是启用那天**，不再手选。启用新计划的同时，旧计划从这天起停用；只有启用新计划才会停用旧计划。
- **启用后不能再改**：习惯、顺序、目标、关联文档都锁定，只能看。
- **一天只有一个版本**：同一天再启用一次，替换掉当天早些时候启用的那个（它一天都没完整用过，不进历史）。
- 版本里有两个习惯同色时，不让保存。
- 启用会拿掉某个习惯、而这个习惯今天或以后还挂着习惯待办时，启用前先提示"这些待办会变成普通待办"，
  确认后这些待办解除关联。
- **圆点**：日历格子按当天版本里的顺序从左往右排，不留空位。颜色跟着习惯走，所以位置变了也认得出。
- **打卡按版本校验**：只有当天版本里的习惯才能打卡。

#### 3. 每周目标

- 目标写在版本里（"🚶 每周 3 次"），不写在习惯上，所以改目标也是修订版本，旧的周按旧目标算。
- 一周从哪天开始，按计划设置里的默认值，不跟日历下面的临时切换走。
- 进度 = 那一周里这个习惯的打卡次数，直接打的和待办带出的都算。超额照写，例如"💪 3/2"。
- 显示在习惯待办那一行（见第 5 小节），按待办自己日期所在的那一周算。没设目标的只显示习惯，不显示数字。

#### 4. 点习惯按钮

| 选中的日子 | 情况 | 弹出 |
|---|---|---|
| 今天 | 这个习惯有今天的习惯待办 | 这条待办，带"完成并打卡" |
| 今天 | 已经打过卡 | 原来的打卡窗口，改备注或撤销；如果是待办带出的打卡，打开那条待办 |
| 今天 | 都没有 | 选择：直接打卡，或创建今天的习惯待办 |
| 明天以后 | 这个习惯那天已经有习惯待办 | 这条待办 |
| 明天以后 | 没有 | 创建那天的习惯待办 |
| 过去 | 这个习惯那天有没完成的习惯待办 | 这条待办，带"补打卡"；补打后待办算完成（受"只能改最近 N 天"限制） |
| 过去 | 没有 | 只能直接打卡（照旧受"只能改最近 N 天"限制），不能创建待办 |

#### 5. 习惯待办

- 待办分两种：**普通待办**和**习惯待办**。习惯待办**只能从习惯按钮创建**，这是唯一入口；普通待办的详情里不再有"完成时打卡"。
- 习惯待办一定有日期，就是创建时选中的那天。**同一个习惯同一天最多一条**。
- 标题默认填习惯名，可以改，例如"🚶 走 5 公里"。完成时打卡的备注就是这个标题。
- **只能在当天完成**：完成就是在待办自己的日期那天打卡。计划外的日子做了，就在那天直接打卡，只算进那一周的统计，
  不影响那条待办。例如周四的 🚶 待办，周三去走了，就是周三直接打卡；周四的待办还是周四的。
- **不能延期**：那天没打卡就是没打卡，算失败；想第二天做，就再建一条。
- **失败自动生效**：过了那天还没完成，就是"已失败"，不用手动处理。它从待办清单里消失，只在那天的日历里带失败标记；
  不能再完成，只能删除。"已失败"和"已过期"一样是按日期算出来的，不单独存。
- **忘了勾可以补**：在"只能改最近 N 天"范围内，点那天的习惯按钮会打开这条待办，带"补打卡"；补打后待办变成已完成，
  打卡记在那天。超过 N 天就改不了了。
- 列表里，习惯待办的标题后面显示关联的习惯和本周进度，例如"🔗 🚶 2/3"。详情页只读显示关联的习惯，不能改。
- 打过卡的习惯待办仍然不能重新打开、不能取消，只能删除，删除时连打卡一起删（同 2.4.1）。

#### 6. 取代 2.4.1 的地方

- "一个习惯同一时间只挂一个没关闭的待办"，改成"同一个习惯同一天最多一条"。
- "打在完成那天"，改成"打在待办自己的日期"：当天完成，或者在 N 天内补打。
- 普通待办详情里的"完成时打卡"去掉。2.4.1 时关联过习惯的待办，一律算作习惯待办。
- "停用的习惯不能选"，改成"不在当天版本里的习惯不能打卡"。

#### 7. 待办备注

- 平时是一块只读文字，高度随内容撑开，全部显示。
- 按简单 Markdown 渲染，只支持最常用的几种：段落和换行、加粗、斜体、行内代码、链接、无序和有序列表。网址可以点开。
- 点一下变成编辑框，但不弹键盘（方便滚动、选中复制）；再点一下才开始打字。离开时保存，和现在一样。

#### 8. 设置页

- 习惯一节改成"当前计划（10/20 起）"：它的习惯和目标，下面是它关联的文档，点开就能看。
- 再往下是草稿（有的话）或"修订"按钮。草稿页：从习惯池挑习惯（也可以新建）、调整顺序、设每周目标、
  关联文档；底部"保存草稿""启用""删除草稿"。
- 再往下是历史计划列表，历史习惯和当时关联的文档在这里看。
- 关联文档只是引用：文档内容在知识库里编辑，计划这边只决定关联哪几篇。
- 日历右上角的筛选，只列当前月份里出现过的习惯。

#### 9. 上线时的数据

- 自动生成两个版本：
  - "从最早那天起"：按现在的排序放前 5 个习惯，包括已停用的，保证过去的日历和现在一样；
  - "从上线那天起"：只放没停用的。
- 这样停用的习惯从上线当天起就不再占位置。

### 2.5 KPI

- **每周有几天打开并打过卡**。这是刚需，会一直坚持下去。
- "打卡"就是 event 打卡，不包括勾掉待办。

### 2.6 数据迁移

- 上线时，用户从现有 calendar 块导出数据，在线上一次性导入（backfill）新表。
- **导出前先校对 `[ ]`**：以前没有备忘这一种，很多备忘被写成了 `[ ]`；
  过去没做完的待办也一直是 `[ ]`。导出前逐条判断（2026-10-17 已由 agent 校对过一遍）：
  - 其实是备忘的，改成不带方括号的纯文本条目 `- 内容`（calendar 块本来就支持这种写法）；
  - 过去没做完、已经不做的待办，改成 `[-]`；
  - 还在做的待办保持 `[ ]`。
  - 以前打卡不能写备注，备注只好单独写成一条待办（例如和 `@1` 同一天的一条待办其实是这次打卡的备注）。
    这种合并回当天的打卡：`@1 备注`。
- **转换规则**：

  | 原来的写法 | 导入成 |
  |---|---|
  | `@序号` / `@序号 备注` | 打卡（带备注） |
  | `- 内容`（不带方括号） | 备忘 |
  | `[ ]` | 待办，进行中（日期已过的就显示为已过期） |
  | `[x]` | 待办，已完成 |
  | `[-]` | 待办，已取消 |
  | `[>]`、`[?]`、`[!]`、`[/]`、`[<]` 等其他没完成的 | 待办，已取消 |
  | 只有日期、没有条目的日期行 | 丢弃 |

  - 导入的"已取消"一律记"关闭时已过期"，原因写"迁移时关闭"。
  - `[!]` 本来表示重要，导入后重要程度设为"重要"。
- 现有数据的格式特点，导入时要处理：
  - 习惯用 `@序号` 引用，有的带备注（`@1 备注`）；
  - 待办用到的状态有：`[ ]` 未开始、`[x]` 完成、`[-]` 作废、`[>]` 延后、`[?]` 有疑问、`[!]` 重要；
  - 有只有日期、没有任何条目的日期行；
  - 同一条待办会在不同日期重复出现。

### 2.7 本期不做，以后很可能做

**P4 候选**（2026-10-19 记，优先级最低，做不做都还没定）：

1. **打通 Google Tasks**：先评估，再决定做不做。
   - 意义：§1 写过不用 Tasks 的理由（看起来乱、不常打开、做完没人关）。所以要先想清楚打通是为了什么，
     比如在别的设备上也能看到待办，或者用它的提醒。如果答不上来，就不做。
   - 可行性：Google Tasks API 要走 OAuth、存用户的 refresh token；还要定同步方向（单向推送还是双向）
     和冲突怎么处理。另外 Tasks 没有"取消要写原因""关闭时是否已过期""延期次数"这些字段，映射过去会丢信息。
2. **手机端计划的 MCP 接口**：让 agent 能制定和维护待办（新建、改日期、延期、关闭）。

## 3. 数据模型草图（未定稿）

只是为了讨论，名字和字段都会变。所有表都按用户归属：

- **习惯（habit）**：名称、emoji、顺序、是否已停用。
  停用而不是删除，历史打卡记录还要能显示。
- **打卡（check-in）**：习惯、日期、备注。
- **待办（todo）**：标题、日期（可空）、状态（进行中 / 已完成 / 已取消）、关闭时是否已过期、
  关闭时间、取消原因、重要程度、标签、备注、关联文档、外部链接、原定日期、延期次数。
- **备忘（memo）**：日期、内容。表名要避开现有的 `memo`（知识库文档）。

## 一、前置准备

**数据与备份**

- [ ] `[P3]` 上线前做一次全站 SQLite 备份，并**实际验证能恢复**（见
      [backup.md](../requirements/storage/backup.md)），不是只确认备份文件存在。
      迁移改的是 `attachment` 表的 `reference` 与 `payload`，回滚只能靠这份备份。
- [ ] `[P3]` 记一份迁移前的基线：附件总数、S3 桶当前对象数与总体积。
      `TODO(定稿)`：填入实测数字。

**必须先让使用者知情的事**

- [ ] `[P3]` **迁移不删源，桶里会存在两份对象**（需求 §3）。确认清理方式：
      换桶/换根路径 → 验收通过后手动整桶或整前缀删除；原地补目录 →
      配 S3 生命周期规则，或因为量小而长期保留。这一条没确认之前不要执行 `--apply`。

**配置与依赖**

- [ ] `[P2]` 确认当前 `filepath_template` 的**目录部分不含 `{uuid}` / `{filename}`**
      （design §2），否则迁移会整体拒绝执行，需要先改模板。
- [ ] `[P3]` 准备一个**测试桶**（或当前桶下的一个测试前缀），先在上面走完
      一遍 `--apply`，再动生产数据。
- [ ] `[P3]` 确认 S3 账号的凭据具备 `CopyObject` 与 `HeadObject` 权限——
      现有凭据只用过 Put/Get/Delete，权限可能不够。

**开关与回滚**

- [ ] `[P0]` 回滚 = 回退版本。锁定规则只影响设置页的一个写路径，不动数据。
- [ ] `[P3]` 回滚方案：源对象没删，所以回滚等价于把 `attachment` 表的
      `reference` / `payload` 还原。手段是恢复上一步的 SQLite 备份。
      **不提供反向的 `--rollback` 子命令**——那是一条只在出事时才跑、平时
      没人测的代码路径，源对象既然不删，恢复备份就已经足够。

## 二、实操步骤

按顺序执行，每步做完确认再进下一步。

1. `[P0]` 部署带存储后端锁定的版本。到设置页尝试把附件存储从 S3 切成本地，
   确认被拒绝且提示里带了存量数量；再确认切回 S3（即不改变）不受影响。
2. `[P1]` 部署带 `CopyObject` / `HeadObject` 的版本。这一步没有可观察的行为变化，
   靠单测。
3. `[P2]` 在生产上跑 `memos migrate-attachments`（dry-run，只读）。
   **读报告，先不做任何事**：总数、已在位、待迁移（按知识库分组）、孤儿数、
   无法处理的条目及原因。`TODO(定稿)`：贴上实际报告。
4. `[P4]` 读报告里标了"slug 将被补齐"的知识库，确认目录名是对的。补齐已经
   并入子命令（design §3）：dry-run 只预览，`--apply` 才落库，所以这里不需要
   单独跑一遍，只需要在动手前把名字看一眼——slug 一旦写进去就不再改，
   将来重命名知识库也不会跟着变。
5. `[P3]` 切到测试桶，跑一次 `--apply`，走一遍 §五 的验收清单。
6. `[P3]` 切回生产配置，跑 `--apply`。
7. `[P3]` **立刻再跑一次 dry-run**，确认报告为"全部已在位"、待迁移为 0。
   这是幂等性的现场验证。
8. `[P3]` 走 §五 验收清单。
9. `[P3]` 验收全绿之后，按 §一 确认过的方式清理源对象。**这一步与上一步之间
   建议隔几天**，不要当天做。

## 三、重点盯盘

迁移执行后的一周内：

- **附件 404**：`/file/attachments/` 路径的 4xx 日志。正常应为零；出现即说明
  某条的指针改了但对象没到位，处置是把该条的 `payload.s3_object.key` 改回旧值
  （源对象还在，改回去立刻恢复）。
- **迁移命令自身的错误报告**：跳过和失败的条目逐条看，不要因为"总数看起来
  差不多"就放过。
- **S3 桶体积**：确认增长量与迁移的对象总量相符；若明显更多，说明可能重复
  复制了，检查幂等判定。
- **上传新附件**：迁移后立刻传一个新附件，确认它落进 `assets/<slug>/`，
  说明迁移没有破坏写入路径。

## 五、上线后的需求验证标准

逐条对照需求文档，人工验收。

### URL 不变（需求 §2 承诺一）

- [ ] 迁移前随手记下 3 个附件的 URL（图片、PDF、draw.io SVG 各一），迁移后
      逐个打开，URL 一个字符没变且能正常打开。
- [ ] 打开一篇正文里内联了图片的文档，图片正常显示，没有出现裂图。
- [ ] 打开一个已发布的对外站点页面，页面里的附件正常加载。

### 迁移期间可读（需求 §2 承诺二）

- [ ] 迁移执行的同时，在浏览器里反复刷新一个带图片的文档页，全程不出现 404。

### 可重复跑（需求 §2 承诺三）

- [ ] 连续跑两次 `--apply`，第二次报告"全部已在位"，且 S3 里没有产生第三份对象。
- [ ] 人为中断一次迁移（跑到一半 Ctrl-C），再重跑，能正常跑完且结果正确。

### 路径归类（需求 §1 二、§7）

- [ ] 迁移后在 S3 控制台查看：附件对象位于 `assets/<知识库 slug>/` 下。
- [ ] 未挂到任何文档的孤儿附件位于 `assets/_unassigned/` 下。
- [ ] 同一个知识库里迁移前后上传的附件，落在**同一个目录**下。

### 换桶（需求 §1 一）

- [ ] 在测试环境把 bucket 改成另一个桶 → 跑迁移 → 所有附件仍可正常打开。
      `TODO(定稿)`：这一条是否在生产上真的执行过，还是只在测试桶验证。

### 存储后端锁定（需求 §4）

- [ ] 有 S3 存量附件时，设置页切"本地"被拒绝，提示里写明了存量数量。
- [ ] 同样切"数据库"也被拒绝。
- [ ] 外链附件（EXTERNAL）不影响上面的判定。
- [ ] 拒绝之后设置页的其余项（路径模板、上传大小上限、S3 凭据）仍能正常保存。

### 不受影响的东西（需求 §5）

- [ ] 缩略图仍然正常（按 UID 缓存，不该受影响，但要看一眼）。
- [ ] 数据库备份仍然正常，备份文件路径不受附件模板变化影响。
- [ ] 删除一个已迁移的附件，S3 上的**新位置**对象被删掉（说明指针确实改对了）。

# 0019. 不做插件系统，用子域边界管理"核心 / 外围"

## Context

blog 站点、站点主题、未来可能的 AI Memory（把相册分析成回忆录）这类功能，
与层级知识库、附件管理、相册/日历视图这些能力，在项目里的分量显然不同：
后者拿掉系统就不成立，前者拿掉系统照常运转。诉求是把这条线画清楚，
避免外围功能持续往主干里渗。

第一反应是做插件系统——让 blog、主题这类东西以插件形式"装"进来。
评估后发现代价与收益严重不匹配，三个成本点都在本仓库的架构里是硬的：

- **API 面是静态的。** 所有 service 挂在同一个 `APIV1Service` 上一次性注册
  （`server/router/api/v1/connect_handler.go`），Go 与 TS 客户端都由 proto 生成。
  插件要加接口，要么参与构建（那就不是运行时插件），要么另开一条不走 proto 的
  泛化通道，并自行接入 ACL（`acl_config.go` 是集中白名单）。
- **存储契约是集中的。** `store.Driver` 是一个大接口，迁移集中在
  `store/migration/sqlite/`。插件自带表就要碰这两处；绕开的办法是只给它一张
  作用域化的通用表，代价是插件做不了复杂查询。
- **前端是编译产物。** 运行时加载 React 组件意味着远程 ESM/模块联邦，外加一套
  版本化的 host SDK（共享 React 实例、UI 组件、i18n、路由插槽）。而想外挂的东西
  （blog 皮肤、相册视图、日历视图）恰恰主要在前端——**后端插件化便宜，
  前端插件化贵，需求偏偏落在贵的那一侧。**

更关键的是收益侧：插件系统的价值几乎全部来自"第三方会写插件"。本项目是个人项目，
没有推广意愿，可预期用户极少，这份收益基本为零；而成本是长期的——一旦对外冻结
扩展契约，重构核心的自由就没了，而本项目的核心能力仍在快速演化。

## Decision

**不做插件系统**，任何形态都不做：Go `plugin`/`.so`、进程外扩展服务、
WASM 沙箱、前端远程 ESM，均不在计划内。同时**不做为插件化服务的中间设施**——
扩展点注册表、manifest、启停开关、事件总线、插件作用域存储：这些都是为
"不认识的第三方"付的钱。

边界改用 **DDD 的子域划分**来管理，只保留三样东西：

1. **两档分类。** 每块能力标为**核心域**或**支撑子域**（"外围"的正式叫法）。
   第三档**通用子域**不做分类用，只作为一条提醒：认证、对象存储、邮件、调度
   这类谁做都一样的东西，一律用现成的，不自己造。分类结果与判据维护在
   [subdomain-boundaries.md](../subdomain-boundaries.md)。
2. **一条依赖方向规则。** 外围可以依赖核心，核心不得知道外围存在。
3. **一条硬约束。** 外围功能不得修改核心数据模型。一个外围需求若非改不可，
   说明要么它其实是核心（重新分类），要么方案错了（换做法）。

判定一块能力属于哪档，按顺序问三条：要不要改核心数据模型 / 有没有别的能力
依赖它 / 拿掉它系统是否仍然自洽。

被否决的替代方案：

- **编译期插件化**（模块自注册路由与迁移 + 前端扩展点注册表，仍整体编译）。
  它确实比运行时插件便宜得多，但把"依赖方向"这一条规则包装成了一套注册机制。
  在没有第三方的前提下，注册机制本身不产生价值，规则才产生价值。**要的是规则，
  不是机制。**
- **按功能出多个构建变体**（build tag 切出"带 blog 版"）。解决的是分发问题，
  而当前的问题是代码耦合，答非所问。

## Consequences

- 保留了随时重构核心的自由。代价是外围功能永远只能用核心已公开的能力，
  遇到不够用时只能推动核心先变——这是有意为之的摩擦。
- 边界靠**机器**守，不靠记性：Go 侧用 `depguard` 按文件路径限制 import，
  前端用 Biome 的 `overrides` + `noRestrictedImports` 按目录限制。两者都是
  配置级改动，接入方式与当前偏离见
  [subdomain-boundaries.md](../subdomain-boundaries.md)。
- 机器守不住的是**影子耦合**——两处代码靠注释约定读同一份数据格式，编译器看
  不见，重构时无人提醒。这类只能靠"约定必须有单一出处"来避免，是本决策留下的
  已知盲区。
- 需求侧多一个字段：每篇需求文档标明所属子域。它的主要作用不是指导怎么做，
  而是给"外围做到够用就停"提供一个不用反复论证的理由。
- 本决策不阻断未来做插件系统。若某天真的出现第三方生态需求，届时的起点是
  一份已经理清的边界，而不是一团耦合的代码——那时再引入注册机制，是加壳，
  不是推倒重来。

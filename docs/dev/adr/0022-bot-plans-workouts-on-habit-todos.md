# 0022. bot 可以排训练：计划训练挂在习惯待办上，bot 可以建、删自己的习惯待办

## Context

[ADR 0021](0021-bot-checks-in-with-workouts.md) 让 bot（Discord 里的 Jen）在练完后打卡，训练记录挂在打卡上。
这记的是**练了什么**。用户还会在练之前让 Jen 排"周六去健身房练什么"，这份计划只留在聊天里：到了周六，app 里那天的
习惯待办看不到它，练的时候没法对着清单做，Jen 练完对账"计划里还差哪组"也只能往上翻聊天记录。

[ADR 0021](0021-bot-checks-in-with-workouts.md) 定下 bot 只调四个接口，而 2.4.2 定下习惯待办只能从 app 的习惯按钮创建。
要让计划落到那天的待办上，这两条都要动。

## Decision

**1. 计划训练挂在习惯待办上，结构和打卡的训练记录相同。**

- 习惯待办多一个 `plannedWorkout`（总时长 + 动作列表），校验上限同 0021。`reps` 是目标次数。
- 只有习惯待办能带。它是计划，不算打卡、不影响每周进度；日期可以在未来。
- 计划和实际成对：待办上是计划，打卡上是实际。完成后 app 可以"按计划填"把计划复制成训练记录的起点，但**不自动复制**，
  没练完的不能算进打卡。
- 计划不另设备注，这次练的重点写在待办备注里：避免一个页面上出现两块备注，bot 也不用选写哪个。

**2. bot 用一个按（习惯，日期）寻址的接口设计划，找不到待办就建一条。**

- `SetPlannedWorkout`（`POST /api/v1/planner/plannedWorkouts`）：按（习惯，日期）找习惯待办（同一习惯同一天最多一条），
  整份替换，天然幂等；空的训练清空。和 `SetCheckIn` 一样按自然键 upsert，bot 不用先查待办的 ID。
- 找不到就新建一条习惯待办，标题默认习惯名。这是 2.4.2"只能从习惯按钮创建"之外的第二个入口，只对 PAT 开放：
  app 里仍然只有习惯按钮，app 用 `UpdateTodo` 改计划。
- 不能建在过去（按调用方传的 `localDate`），习惯必须在那天的计划里；已完成、已失败、已取消的待办不能改计划。
- 只在用户在聊天里同意了具体日期时建，这是 bot 的约定（toucan-base 的提示词），服务端无法判断。

**3. 待办也有来源，按凭证判定；bot 只能删自己建的。**

- `Todo.source`：`MANUAL`（app 建的）或 `AGENT`（PAT 建的），建的时候定下，之后不变。判据同 0021：登录会话是人，PAT 和 MCP 是 agent。
- `DeleteTodo` 对 PAT 加一条规则：只能删 `source=AGENT` 的待办（用户反悔"周六不去了"）。用户建的待办 bot 只能设计划。
- 计划另有 `plannedWorkoutSource`，记**最后一次**设计划的是谁，app 上 bot 排的带 🤖。待办来源和计划来源分开：
  用户建的待办可以挂 bot 排的计划，bot 建的待办用户也可以改计划。

**4. 不加 MCP 工具。** `planner_get_week_progress` 的 `habitTodos` 带上计划和来源，Claude Code 能看到。
写入不进 MCP，理由同 0021 第 4 条。

## Consequences

- bot 的写入范围从"打卡"扩大到"建习惯待办、设计划、删自己建的待办"。PAT 仍然没有 scope（见 0021 的后果），
  所以这些仍然只是约定加服务端的来源检查；令牌泄露的风险和 0021 一样，收窄的办法也一样。
- `Todo.source`、`plannedWorkout`、`plannedWorkoutSource` 成了对外契约，toucan-base 的 bot 依赖它们。
- 2.4.2"习惯待办只能从习惯按钮创建"改为"app 里只能从习惯按钮创建"。
- 日历格子上带计划的待办暂时没有标记：习惯待办不进格子，图标只给固定的习惯画。以后要加，在 app 上加，接口不变。

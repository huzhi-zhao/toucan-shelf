# 0016. 不支持多端写入，靠文档约束

## Context

[单机本地部署](../standalone-local-deploy.md)原始设想里有"可多端启动"（比如同一份
S3 备份被多台机器先后使用）。评估后发现 SQLite + 对象存储备份这一架构**只能有一个
写者**：两台机器先后启动会出现 A 机启动、拉最新快照、写入一段时间、上传；随后 B 机
启动、拉到的是 A 上传前的快照、也写入、也上传——A 那段时间的数据被静默覆盖，用户收
不到任何错误。这比"数据没备份"更糟。

要安全支持多端，必须做 S3 租约（`owner.json` 记录持有者 + epoch，启动时抢占、后台
续期、上传前校验 epoch），预估约 250 行，且引入一整类新的故障模式。而实际使用场景
是单台常开的 Mac mini + 局域网访问，多端的必要性很低。

## Decision

**不实现租约机制。** README 与首启引导中明确写"同一份 S3 备份只能被一个实例使用，
同时运行多个实例会导致数据丢失"。

## Consequences

- 这是一条靠文档约束的规则，**没有代码兜底**——代码不会检测或阻止多实例同时使用
  同一份 S3 备份。
- 如果后续真要支持多端，S3 租约是唯一正确的入口，不要试图用"上传前比较时间戳"之类
  的办法绕过去（那类办法无法消除竞态窗口，只是把静默丢失变得更难复现和排查）。
- 用户教育成本转嫁给了文档和首启引导 UI；若引导流程缺失或用户跳过阅读，风险不会
  被系统拦截。

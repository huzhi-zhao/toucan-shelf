# 跨文档引用完整性维护 — 分阶段实施

需求、事实依据与验收判据见
[requirements/cross-reference-repair-on-move-rename.md](../requirements/cross-reference-repair-on-move-rename.md)。
反向索引的存量回填见
[20260807-memo-link-index-backfill.md](20260807-memo-link-index-backfill.md)。

原则：反向引用索引是地基，先做「只读」的检测与拒绝（风险低、立刻有产品价值），
再做「写」的自动改写（风险高，涉及自动改写用户正文，需要更谨慎的边界判断）。
每个阶段独立可提交。

> 2026-08-07 第二次需求对齐后，P0–P2 的结论保留，P2 的范围被 P4 扩大（从「只改锚文本」
> 扩到「href 也必须正确」），并新增 P3–P6。需求文档初版的「移动不必处理」结论已被推翻，
> 本文档中凡引用该结论之处以本版为准。

## P0 · 反向引用索引 ✅ 已实现

`memo_link` 表记录「某文档的正文里，出链到了哪些文档」，以 target memo id 存储，
目标改名后索引本身不失效。

- 解析时机：`CreateMemo` 与 `UpdateMemo` 命中 `content` 变化时，对本文档全量重新解析
  出链并覆盖写入（`syncMemoLinkIndex`，[link_index.go](../../../server/router/api/v1/link_index.go)）。
  不做增量 diff。
- 解析失败（目标不存在/歧义）的链接直接丢弃，不阻塞保存——索引是尽力而为的辅助数据。
- **存量回填**：`memo_link` 只在写路径写入，功能上线前既有的文档没有索引行，会静默
  失效 P1/P2。启动时跑一次全量回填，见 backfill 设计文档。

## P1 · 只读的依赖检查与拒绝弹窗 ✅ 已实现（P6 扩范围）

覆盖「归档 / 删除文档或文件夹」，复用 `DeleteWorkspaceFolder` 已有的「先查、非空拒绝」
模式，把查询目标换成「容器内文档是否被容器外的文档引用」。命中依赖时返回结构化列表
（引用来源的 uid + 标题），前端弹窗展示并阻止提交。

## P2 · 重命名时静默修复锚文本 ✅ 已实现（P4 扩范围）

由 `UpdateMemo` 的 `title` 分支触发，用 P0 索引反查引用者，对每篇引用者重新解析链接，
**只替换锚文本完全等于旧标题的节点**；被用户自定义过的锚文本不动。写回要求幂等。

## P3 · 确立规范路径形式（解析层）

把链接的规范形式切到**工作区根相对全路径**（`/doc/api.md`），这是后续所有修复阶段的
前提。**必须先于 P4/P5 上线**——否则被自动重写成新形式的链接在页面上点不开。

- 前端 `isRelativeDocHref` / `resolveWorkspacePath`
  （[DocumentLinkContext.tsx](../../../web/src/components/MemoContent/DocumentLinkContext.tsx)）
  与后端 `internal/linkindex`（照前端 port 的同一套逻辑）**必须同步修改，保持等价**。
  两边任一漏改都会造成「索引认得但渲染不认」或反之。
- 新的解析规则，按优先级：
  1. `/memos/{uid}` 或 `{host}/memos/{uid}` → 直接取 uid（兼容形式，保留）；
  2. 以 `/` 开头且能在工作区树中按「文件夹路径段 + 末段标题（扩展名无关、大小写无关）」
     命中一篇文档 → 该文档；
  3. 其余一律视为站外链接。
- **移除「全树按标题兜底匹配」层**，并**移除对不带 `/` 前缀的相对路径的解析**。
  解析失败即为断链。
- 与站内其他路由（`/shelf/…`、`/u/…`、`/attachments/…`）的冲突：规则 2 只在真的命中
  一篇文档时才成立，命中不了自然落到规则 3，不需要维护路由黑名单。
- 断链的呈现方式需要前端配合（区别于正常链接的视觉标记），否则用户无从知道哪些链接
  失效了——这是本阶段唯一的产品可见变化，需求文档已确认接受。
- 存量 Obsidian 遗留相对链接会集体变为断链。可选的一次性归一化脚本（把当前仍能解析的
  存量相对链接批量改写为规范形式）建议随本阶段一起做，否则这批数据会永久沉底：它们
  解析不出目标 → 进不了 `memo_link` → 后续所有自动修复都覆盖不到。

## P4 · 改名与同库移动时修复 href

把 P2 从「只改锚文本」扩到「href 必须始终正确」，触发点从 `title` 分支扩到
`folder_path` 分支（同工作区内）。

- 目标文档的新规范 href 是**一个值**（根相对全路径与引用者位置无关），算一次，
  所有引用者共用。
- 逐引用者重新解析链接节点，命中目标 uid 的替换其 destination。
  锚文本按 P2 原规则独立处理：**href 无条件修复，锚文本仅在等于旧标题时更新**。
- `/memos/{uid}` 形式的 href 不需要修复（uid 不变），只可能需要更新锚文本。
- 幂等性判据：同一次改名/移动重复触发不产生二次 diff；源文档自身被移动时，其正文内
  所有出向链接字节不变（根相对形式的直接推论，需固定为回归用例）。

## P5 · 文件夹改名与同库移动

挂在 `RenameWorkspaceFolder` / `MoveWorkspaceFolder`
（[workspace_service.go:272](../../../server/router/api/v1/workspace_service.go)）之后。

- 目标集合 = 子树内所有文档；引用者集合 = 通过 `memo_link` 反查、且在子树外的文档。
- 修复动作退化为**路径前缀替换**：把 href 中等于旧文件夹路径的前缀换成新路径。
  子树内文档之间的互相引用同样是根相对全路径，因此**同样需要更新**（这一点与标准
  相对路径方案相反，不要凭直觉跳过）。
- `RenameWorkspaceFolder` 走批量 SQL 绕过了 `UpdateMemo`，`reindexFolder` 是既有的
  补救；反向索引与引用修复同样要在这条批量路径上手动挂载，别重蹈只补一半的坑。

## P6 · 跨工作区移动纳入拒绝检查

把 P1 的依赖检查扩展到跨库移动，两个入口都要拦：

- 单文档跨库：`UpdateMemo` 的 `workspace_id` 分支；
- 文件夹跨库：`MoveWorkspaceFolder`。

检查逻辑与归档/删除完全一致，复用同一套查询与错误结构，前端复用同一个弹窗。

## 风险与历史教训

memogit 移动语义早期把「移动」实现成「归档旧的 + 新建一个」，导致所有引用该文档的
链接全部断链（详见
[../requirements/collaboration/memogit-doc-identity.md](../requirements/collaboration/memogit-doc-identity.md)
§4.2、§6.1）。

> 迁移脚注（2026-08-08）：上面链接的原文档已随
> [docs/plans → docs/dev 迁移](20260808-plans-to-dev-migration.md)拆入
> `requirements/collaboration/memogit-doc-identity.md`，原文的 §4.2、§6.1 编号未必仍对应，
> 本节论述不变，只改路径。当前 `UpdateMemo`/`RenameWorkspaceFolder` 已经是原地更新、uid 不变，
不会重蹈这个坑，但它确立的原则仍然适用：**自动改写文档内容必须幂等、可逆、
不产生误伤 diff**。P4/P5 是本计划里自动改写「别的文档」正文的动作，出错代价最高，
上线前需要至少覆盖：同一文档被多处引用、循环引用（A 引用 B、B 也引用 A）、
锚文本被自定义过、目标 uid 同时出现在代码块/非链接上下文中（不应被误改）、
子树内互相引用、href 含空格需 `<>` 包裹这几类用例。

## 已知取舍

- **并发编辑不做保护。** 自动修复走 `UpdateMemo` 全量覆盖 content，与用户同时编辑
  同一文档会覆盖其未保存内容。已在需求文档中确认接受，不作为缺陷处理。
- **TODO（本期不做）：批量写入的事务与索引重建合并。** P5 会逐篇改写正文，当前每篇
  各自触发一次 RAG 索引任务。后续应改为整批走一个事务、全部提交完成后统一触发一次
  索引重建。该约定适用于所有「一次操作批量改写大量文档」的场景。实施时在 P5 的批量
  改写入口处留同名 TODO 注释，便于日后统一处理。

# 附件存储迁移：技术方案

> 初稿，未冻结。需求见
> [requirements/storage/attachment-storage-migration.md](../requirements/storage/attachment-storage-migration.md)。
> 本篇只写方案取舍、被否决的选项、约束与假设、分阶段切风险，不写文件级改动清单。

## 1. 问题

管理员要把附件的 S3 落点换到别处（换源 / 换桶 / 换根目录前缀），已有对象得跟着搬，
对外 URI 一个字都不能变，旧数据一个都不能删。当前实现有三处结构性阻碍：

- **换桶是静默破坏。** [store/attachment.go:214](../../../store/attachment.go)
  的 `ResolveAttachmentS3Config` 无条件优先用实例当前的 S3 配置，改完 bucket 的那一刻，
  全站老附件带着旧 key 去新桶里找，全部 404。
- **根目录前缀不是一个概念。** 它揉在 `filepath_template` 这个自由字符串里
  （[instance_setting.proto:108](../../../proto/store/instance_setting.proto)），
  跟知识库分目录、文件名规则混在一起，没法单独表达"只换前缀"。
- **没有搬运原语。** [internal/storage/s3/s3.go](../../../internal/storage/s3/s3.go)
  只有 `UploadObject` / `GetObject` / `GetObjectStream` / `DeleteObject`，
  既不能让 S3 自己做服务端复制，也不能确认某个 key 到底存不存在。

## 2. 配置字段：哪些能直接改，哪些必须走迁移

### 一条判据把 S3 配置切成两半

这是整个方案的支点。`StorageS3Config` 的字段按语义分两类：

| 类别 | 字段 | 语义 | 能否直接编辑 |
|---|---|---|---|
| **怎么连** | `region`、`access_key_*`、`use_path_style`、`insecure_skip_tls_verify` | 同一份数据换个连接方式 | **能**。改完所有附件跟着走，这正是现有 `ResolveAttachmentS3Config` 想支持的场景 |
| **在哪儿** | `endpoint`、`bucket`、`root_prefix`（新增） | 数据存在哪一份存储的哪个位置 | **不能**。必须走迁移流程 |

`endpoint` 归到"在哪儿"是一个刻意的选择。它确实可能只是同一份数据换个访问地址，但**服务端
无从判断**——两个 URL 背后是不是同一个桶，只有真去 `StatObject` 才知道。判不出来就按最坏情况
处理：归入位置，一起拦。代价很低，因为"其实是同一份数据"走迁移时，搬运阶段每条都会发现目标
位置已有同名同大小的对象而直接跳过，整趟下来只是一遍 `StatObject`，不复制一个字节。

`root_prefix` 是三者里最软的一个：key 是逐条存在附件上的（`payload.s3_object.key`），
改前缀不会让已有附件读不到，只会让新旧对象永远分处两个目录。仍然拦，是为了让"附件在哪儿"
始终能用一个 (endpoint, bucket, root_prefix) 三元组说清楚——桶生命周期规则、迁移比对、
目标 key 重算，全都建立在这个可表达性上。

有了这条判据，第 1 节那个坑的修法就不是"改读路径的解析逻辑"，而是**在写入侧拦住**：
`UpdateInstanceSetting` 收到 `STORAGE` 更新时，若位置三元组中任意一个与现值不同，
直接拒绝并提示走迁移。UI 上这三个输入框在非迁移态是只读的。

拦住之后，`ResolveAttachmentS3Config` **一行都不用改**——它"优先用实例当前配置"的前提
（当前配置指向的是同一份数据）从此由不变式保证，而不是靠运气。只需要把这个前提写成注释，
让下一个人不会顺手把 bucket 改成可编辑。

另有两个必须一起堵的绕行口，否则拦截形同虚设：把 S3 配置整个删掉再以新桶建回来（等于换桶
但不经过比对），以及老前端不发 `filename_template` 时的空值——空值若按"清空"处理，下次读取
会重新拆解 `filepath_template`，把用户故意留空的 `root_prefix` 覆盖成 `assets`，等于静默搬家。
前者拒绝，后者按"不修改"处理。

### proto 怎么放

- `root_prefix` 加在 `StorageS3Config` 上，跟 `bucket` 同级。它属于"数据在哪"，
  跟 endpoint、bucket 是同一个维度的东西；放在外层 `InstanceStorageSetting` 上会让
  "三级落点"散在两个 message 里，迁移时要比对的东西也散了。
- `filename_template` 加在 `InstanceStorageSetting` 上。它是跨存储类型的命名规则，
  不属于任何一个后端的连接信息。
- `filepath_template` 保留字段但降级为 LEGACY-COMPAT，不再作为 S3 写路径的事实来源。
  不删除，因为它是老实例升级时唯一能拆解出 `root_prefix` 的依据。

### 兼容：惰性拆解，不写 SQL 迁移

实例设置整体是 `instance_setting` 表里的一个 JSON blob，拆一个自由字符串这种事 SQL 表达不了。
跟 `storage_slug` 的惰性 backfill 同款做法（[store/workspace_slug.go:72](../../../store/workspace_slug.go)）：
在 `GetInstanceStorageSetting` 里做，读到没有 `root_prefix`/`filename_template` 的老配置时，
按 `{workspace}` 的位置把旧模板切成两半，前半进 `root_prefix`、后半进 `filename_template`；
模板里没有 `{workspace}` 的，目录部分整段进 `root_prefix`。拆解结果在下一次设置写入时落盘。

`{workspace}` 之后如果还夹着别的目录段（用户自己加的），归到 `filename_template` 里会产生
一个带斜杠的"文件名"。这是可以接受的——它只影响老配置的呈现，而这类配置在第一次迁移之后
就会被重算掉。

### LOCAL 存储不受影响

`{workspace}` 本来就只对 S3 生效（[attachment_service.go:886](../../../server/router/api/v1/attachment_service.go)
的 `dropWorkspace`），三级模型也只是 S3 概念。本地盘继续按现在的样子写在 `Profile.Data` 下，
不引入 `root_prefix`，不改布局。

## 3. 迁移期间"每条附件在哪"：把改写推迟到切换那一刻

这是方案里唯一真正需要想清楚的地方，也是简化空间最大的地方。

### 方案 A：边搬边改（否决）

搬一条改一条 payload，附件读路径改成"按这条附件自己的状态选配置"。需要给 payload 加位置标记、
需要读路径分支、需要保留旧 key 才能回滚、需要处理"标记改了但对象没复制成功"的半状态。
每一样都是新的失败模式。

### 方案 B：存储世代（否决）

实例维护一个存储位置列表，附件 payload 记录自己属于哪个世代，读路径按世代号查连接参数。
模型确实干净，能同时表达任意多个历史位置。但**不变量 3 保证了同一时刻只可能有两个位置**
（旧的和新的，因为旧对象永不删除但也永不再被写入）。为"任意多个"付一层间接的代价，
是拿一个不会发生的场景换真实的复杂度。

### 方案 C：先全量复制，切换时一次性改写（采纳）

搬运阶段**完全不碰 `attachment` 表**。每条的 `旧 key → 新 key` 映射写在迁移任务表里，
对象复制到新位置，数据库里的一切保持原样。切换时在一个事务里把任务表的映射批量写回
attachment payload，同时把实例配置从旧落点换成新落点。

这样：

- **迁移期间附件读路径完全不用改。** 数据库还是旧 key、实例配置还是旧落点，
  读附件跟平时一模一样。需求篇的不变量 2 不是"实现出来的"，是"没机会被破坏"。
- **回滚是删一张表的行。** 没有任何数据库状态需要还原，新位置多出来的对象就搁那儿。
- **切换是原子的。** 一个 SQLite 事务，要么全改要么全不改，没有中间态。

代价是**冻结窗口等于整个搬运时长**——方案 A 理论上能把冻结压到只有切换那一瞬。
这个代价可以接受，理由见 §4 的复制速度，以及 §8 里那个被推迟的两轮搬运优化。

### 批量写回的规模

附件表规模是几千到几万量级（`TODO(确认)`，见需求篇开放问题），一个事务内 UPDATE 几万行
对 SQLite 不构成问题。写回时除了 `payload.s3_object.key`，把 `payload.s3_object.s3_config`
快照也一并更新成新配置——它只在"实例改成非 S3 之后回落"这条冷路径上被读，但留着一份指向
旧桶的快照没有意义。

`attachment.reference` 字段存的也是 object key（[attachment_service.go:800](../../../server/router/api/v1/attachment_service.go)），
同一个事务里一起改。

## 4. 搬运：什么时候能让 S3 自己干

### 两条路径

| 条件 | 做法 | 数据流 |
|---|---|---|
| 目标位置已有同名、同大小的对象 | 跳过 | 无 |
| endpoint、凭证、`use_path_style` 全部相同，只有 bucket / 前缀变了 | `CopyObject`，`CopySource = 旧桶/旧key` | 不经过 Toucan |
| 其余情况（换源、换账号） | `GetObjectStream` 旧 → `UploadObject` 新 | 整份数据过一遍 Toucan |

第一行既是断点续跑的实现方式，也顺带让"换 endpoint 但其实指向同一份数据"这种迁移变成一次
纯 `StatObject` 扫描。它不是特例，是幂等性自然的产物。

服务端复制那条路径快到几乎与对象体积无关，几万个对象是几分钟的事——这是 §3 敢让冻结窗口
覆盖整个搬运的底气。跨源转存则是真的要搬字节，慢，但这类迁移本来就罕见。

判定必须严格按"三个连接参数全等"，不能只比 endpoint。同一个 endpoint 下换一套 AK/SK
很可能是换了账号甚至换了租户，跨账号的服务端复制需要桶策略配合，不能默认它成立。
判不准就走转存——慢，但一定对。

### 转存路径的已知陷阱

[server/backup/backup.go:91](../../../server/backup/backup.go) 留了一条踩过的坑：
`io.Reader` 背后是 `*os.File` 时长度对 SDK 不确定，某些 S3 兼容实现会因此算出不匹配的
body hash，报 `SignatureDoesNotMatch`。备份的解法是整份读进内存再用 `bytes.Reader` 传。

附件最大 100MB（`upload_size_limit_mb` 默认值），整份进内存单条没问题，但搬运是连续跑的，
逐条 100MB 的峰值加上并发就不好看了。倾向先落临时文件、再以已知长度上传；如果实测该 S3
实现对流式上传没问题，再退回纯流式。这一条在 P2 实测时定，**不要提前假设**。

### 体积上限

`CopyObject` 单次最大 5GB，超过要走 multipart copy。附件上限 100MB，撞不到。
前提写进代码注释：如果哪天上传上限放开到 GB 级，这里要补 multipart。

### 目标 key 是重算的，不是替换前缀

`目标 key = root_prefix / workspace_slug / 旧 key 的最后一段`。

- 目录重算，所以历史平铺附件在这一趟里自动归位，不需要单独的搬迁脚本
  （[TODO.md](../../../TODO.md) 里原有的"附件搬迁脚本是否已执行"待确认项已随需求篇注销）。
- 文件名段沿用，所以同一条附件算多少次都得到同一个目标 key——**幂等的来源是这个，
  不是任务表的状态位**。状态位只用来省掉重复的网络往返。
- 归属按 `attachment.memo_id` → memo → workspace → `storage_slug` 推导，推不出的落
  `_unassigned/`。这里要一次性批量查，不能每条附件查一次数据库。

## 5. 状态与队列：blob 放设置，明细放表

迁移的**状态机与目标配置**放进 `instance_setting` 的一个新 key（`STORAGE_MIGRATION`）。
它是单例、字段会随实现反复调整、没有查询需求，正好是 JSON blob 的形状——改字段不用写
SQL 迁移。

**逐条明细**放新表 `attachment_migration_job`，形状照抄 `memo_index_job`
（[0.30/08__rag_search.sql:31](../../../store/migration/sqlite/0.30/08__rag_search.sql)）：
`attachment_id` 作主键，加 `source_key` / `target_key` / `status` / `attempts` / `last_error`
和两个时间戳，`status` 上一个索引。主键即附件 id 使得"同一条附件在一次迁移里只会有一行"
是数据库保证的，不是代码保证的。

一次迁移开始时全量灌入任务行（附件表的一次分页扫描），之后 worker 按 `status='pending'`
批量认领。重启后从表里恢复，天然断点续传。切换完成时整表清空——它是一次迁移的工作区，
不是历史归档；需要留痕的信息（迁移了多少条、什么时候、从哪到哪）写在设置 blob 里。

worker 复用现有 runner 的形态（[server/runner/backup/runner.go](../../../server/runner/backup/runner.go)
那种 ticker + `RunOnce`），不需要引入新的调度设施。

## 6. 冻结闸门：拦在服务端的三个点

前端置灰不算数——memogit 和 MCP 都能创建文档和附件，拦不住。闸门必须在服务端，
盖住三个真正会写 S3 的位置：

- `SaveAttachmentBlob`（[attachment_service.go:731](../../../server/router/api/v1/attachment_service.go)）——新对象落盘，唯一入口
- `applyAttachmentContentUpdate`（[attachment_service.go:498](../../../server/router/api/v1/attachment_service.go)）——原地替换内容
- `deleteAttachmentStorageImpl`（[store/attachment.go:237](../../../store/attachment.go)）——删除对象

删除那一处在 store 层，它本来就在读实例存储设置，加闸门不引入新的依赖方向。

返回的错误要能被前端识别成"存储迁移中"而不是一个笼统的内部错误——用一个明确的
`FailedPrecondition` 加上可读的 message，前端据此提示。

**只冻结这三处。** 文档读写、搜索、附件读取全部照常。附件的缩略图和 motion 缓存落在本地盘、
按附件 UID 命名（[store/attachment.go:322](../../../store/attachment.go)），与 S3 位置无关，
迁移不影响它们，也不需要在迁移后清理。

## 7. 预检与对账：只需要给 S3 客户端加两个方法

### `CopyObject` 和 `StatObject`

- `CopyObject` 是 §4 那条快路径的全部依赖。
- `StatObject`（`HeadObject` 的封装，返回存在性 + 大小）同时服务三件事：预检探针的读回、
  搬运前跳过已存在的目标对象、对账逐条核对。

**不加 `List`。** 需求篇提到"想知道旧桶里有多少孤儿对象现在做不到"——那是个诊断能力，
不是迁移的必要条件。对账按数据库记录逐条 `Stat` 比按桶枚举更准（枚举会把别的应用的对象
也算进来），也不用处理分页。List 留到真的要做孤儿对象诊断时再加。

### 预检必须真写一次

试连接不够。桶存在但没有 `s3:PutObject` 权限、前缀被桶策略拒绝、endpoint 前面挂了个
改写 header 的 CDN（[s3.go:52](../../../internal/storage/s3/s3.go) 那段注释里的
`Accept-Encoding` 问题就是这么来的）——这些全都只有真写一个对象再读回来再删掉才发现。
探针对象是全流程唯一允许调用 `DeleteObject` 的地方。

### 对账不通过就不许切换

对账逐条 `Stat` 目标 key，核对存在性与大小。有任何一条缺失，切换按钮不可用。

源对象本身就不存在的情况（数据库有记录、桶里没文件的断链）单独记一类状态，不算失败、
不阻塞切换，最后在结果里列出来。存量数据里存在这类记录的概率不低，让一条断链卡住整次迁移
不合理——但也不能悄悄跳过，得让人看见。

## 8. 分阶段切风险

### P0 —— 先把坑堵上（已实现）

三级路径模型（`root_prefix` + `filename_template` + 惰性拆解）、位置三元组
（`endpoint`/`bucket`/`root_prefix`）的直接编辑拦截、UI 上这三个字段在非迁移态只读。

**这一阶段不含任何迁移能力，但独立有价值**：改完之后"换桶导致全站附件 404"这个现存缺陷
就不存在了，代价只是这三个字段暂时完全不能改。证伪的是"三级模型能不能兼容老配置"。

### P1 —— 目标配置与预检（已实现）

`STORAGE_MIGRATION` 设置、目标配置的录入与保存、`StatObject`、预检探针的写-读-删闭环。
到这一步为止一个附件都没搬，但"新落点到底通不通"已经能回答了。
证伪的是"预检能不能真的发现权限和策略问题"。

几个落地时定下来的细节：

- **目标配置改了，预检结果就作废。** 预检是关于某一个具体目标的陈述，目标一变陈述就不成立，
  状态退回 `DRAFT`。目标没变时（客户端回传空密钥的那种保存）保留原状态和原结果。
- **状态机归服务端所有。** 客户端只能写 `target_s3_config`，`state` 和 `precheck` 从请求里
  丢弃——否则客户端直接发一个 `READY` 就跳过了对账。
- **目标等于当前位置的迁移直接拒绝。** 它什么都不搬，却照样要冻结写入、重写全部映射。
- **探针删不掉不算预检失败。** 迁移本身从不删对象，删除权限不是它需要的能力；
  `probe_key` 记在结果里，留给管理员手动清理。
- **服务端复制的判定条件是"除了位置以外全都相同"**（`canServerSideCopy`）。比"只看 endpoint"
  严格：同 endpoint 换一套 AK/SK 很可能是换了账号，跨账号复制需要两边桶策略配合。
  判不准就走转存，慢但一定对。

### P2 —— 搬运、对账、切换（已实现）

`CopyObject`、任务表、worker、冻结闸门、对账、批量写回的切换事务。这是主体。
先只做单轮搬运，不做并发、不做限速——实测慢了再说。
证伪的是"服务端复制的判定条件对不对、切换事务扛不扛得住"。

几个落地时定下来的细节：

- **闸门关上和灌任务之间有一条缝。** 一个刚好在闸门关闭前一瞬通过检查的上传，会在附件表扫完
  之后才落盘，于是它不在任务表里、任何计数都看不见它，切换之后它的 key 会被拿到新桶里找。
  修法不是加锁，是让灌任务变成**只增不改**的幂等操作，并在"重试"和"切换"时各重跑一次扫描：
  切换时扫出新增的就退回搬运态并明确告诉管理员"有 N 条是开始之后新增的，正在搬"。
- **worker 的写回是带前置状态的。** 一趟搬运可能跑很久，管理员可能中途放弃或切换。写回前
  重新读一次状态，对不上就丢弃这次进度写入——丢一批计数只是重新 stat 一遍，把一个已经被清掉的
  迁移写回去则是让实例带着空任务表永久冻结。
- **跨源转存整份读进内存再传**，不流式。流式上传时长度对 SDK 不确定，某些 S3 兼容实现会因此
  算出不匹配的 body hash（备份那条 `SignatureDoesNotMatch` 就是这么来的）；附件有上传上限，
  单线程一次一个，内存是有界的。
- **搬运前先 stat 目标。** 已存在且大小一致就跳过。这既是断点续跑的实现方式，也让
  "换 endpoint 但其实是同一份数据"退化成一趟纯 stat。
- **对账重新 stat 一遍已经搬完的对象。** "PUT 返回 200"和"对象在那儿"是两个不同的断言，
  实例是要被指到第二个上面去的。
- **闸门的报错必须能被前端认出来**（`FailedPrecondition` + 固定文案），迁移期间它是预期答案，
  "过会儿再试"是真的正确建议，不能混在笼统的 500 里。

### P3 —— UI（已实现）

设置页里的迁移面板：目标配置表单、预检结果、进度、对账结果、切换按钮、
以及切换后那句"旧数据还在，请自行核对后删除"的说明。

落地时的几个判断：

- **面板自己管状态，不进 `InstanceContext`。** 搬运期间要轮询，塞进全局 context 会让整个应用
  跟着重渲染；而且 context 的 `fetchSetting` 取过一次就不再取，正好和轮询相反。
- **表单默认从当前配置预填。** 迁移多数情况只改一两个字段（换个桶、换个前缀），让人重新抄一遍
  连接信息没有意义。轮询回来的数据只在用户没有未保存改动时才覆盖表单。
- **"重试"在搬运态也要能按。** worker 遇到自身错误会带着原因停在搬运态（不解冻，因为解冻会让
  新上传落进一个即将失效的位置），此时如果只有"放弃"可按，就等于把一次可恢复的中断变成必须重来。
- **切换成功后整页刷新。** 生效的存储配置在服务端被换掉了，而它没走 context 的更新路径、
  context 又缓存了 STORAGE，让它重取是个空操作。刷新很钝，但一次迁移只发生一次，
  切完之后页面还显示旧桶更糟。

### 被推迟的优化：两轮搬运

冻结窗口等于搬运时长（§3 的代价），跨源迁移大数据量时可能是几小时。缓解办法是分两轮：
第一轮**不冻结**先搬一遍（安全的——目标 key 确定性重算、旧对象不删、数据库不改），
冻结后第二轮只处理这期间新增和变更的附件，把窗口压到分钟级。

不放进 P2，因为它引入了"第一轮之后被删除的附件"这类增量对账问题，而同源换桶（最常见的
场景）走服务端复制根本不慢，做了也没人受益。等真的遇到慢的跨源迁移再做。

## 9. 约束与假设

- **单条对象搬不动不中止整次迁移**：源对象不存在时记为跳过、继续跑完，跳过项计入对账缺失，
  因此仍然拦住切换。见需求篇「已定的边界」。
- **附件的原地更新写回同一个 object key**，不换新 key。目标 key 能从旧 key 重算是幂等性的
  全部依据，key 若会变，搬运中途被更新过的附件就对不上账。见需求篇「附件的原地更新」。
- **附件数量在几千到几万量级**（`TODO(确认)`，不阻塞开工）。单线程搬运可接受、切换事务一次改几万行
  可接受，都建立在这个假设上。数量级不对要重新算。
- **单实例、单份 SQLite**（[sqlite-as-sole-datasource.md](../requirements/storage/sqlite-as-sole-datasource.md)），
  没有多进程同时跑迁移的可能，因此不需要分布式锁。
- **附件上限 100MB**，因此不需要 multipart copy、整份进内存是可选项而不是禁区。
- **对外 URI 与 S3 key 完全解耦**：附件走 `/file/attachments/{uid}/{filename}`
  （[fileserver.go:149](../../../server/router/fileserver/fileserver.go)），正文里存
  `attachments/{uid}` 资源名，对外发布同样走这个形式
  （[internal/publish/refs.go](../../../internal/publish/refs.go)）。
  这条是"URI 不变"的结构性保证，方案不依赖任何额外机制，但也**不能破坏它**——
  任何把 object key 泄漏到 URL 里的改动都会让这个需求塌掉。

## 10. 验收判据

需求篇那八条是产品侧的。技术侧另外三条：

- **幂等**：同一次迁移的搬运阶段重复跑任意次，新位置的对象数量与内容不变，
  任务表最终状态一致。
- **切换的原子性**：在批量写回的事务提交前后各 kill 一次进程，重启后系统只可能处于
  "全部未切换"或"全部已切换"两种状态之一，不存在部分改写。
- **拦截的完整性**：冻结期间，通过 Web、memogit、MCP 三条路径分别尝试上传/替换/删除附件，
  全部被拒绝且错误可识别。

## 11. 明确不做

- **不改 `ResolveAttachmentS3Config` 的优先级逻辑。** 它现在是对的，前提由 §2 的编辑拦截保证。
- **不给附件加位置标记字段。** §3 方案 A/B 已否决。
- **不做 `List`。** §7。
- **不迁移 `backups/` 前缀下的整库备份。** 见需求篇"明确不做"。
- **不做并发与限速。** P2 单线程起步，实测不够再加。提前做并发只会让第一次跑出来的
  失败更难归因。
- **不在迁移中重算 `storage_slug`。** 知识库改名不搬目录的约束保持原样，
  别把两个变量叠在一次操作里。

# 外部资源根：技术方案初稿

> 初稿，未冻结。需求见
> [requirements/storage/external-resource-roots.md](../requirements/storage/external-resource-roots.md)。
> 本篇只写方案取舍、被否决的选项、约束与假设、分阶段切风险，不写文件级改动清单。

## 1. 问题

要索引 NAS 上已经存在的文件，而不要求用户重新上传。当前实现结构上做不到：

- [internal/storage/s3/s3.go](../../../internal/storage/s3/s3.go) 无 `List`，
  bucket 是只写下水道，看不见非自己创建的对象。
- `Attachment.MemoID` 使附件从属于文档，不存在"无宿主的文件"这一概念。
- `AttachmentStorageType.LOCAL` 在
  [fileserver.go](../../../server/router/fileserver/fileserver.go) 中被
  `filepath.Join(s.Profile.Data, ...)` 限定在 data 目录内。

三者中任意一条不破，方案都不成立。

---

## 2. 接入协议：为什么选文件系统而不是 S3 网关

用户侧的文件由 NAS 上的工具（File Browser 一类）管理，它们操作的是**文件系统目录**；
Toucan 现有的外部存储能力说的是 **S3**。中间这道缝有两种补法。

### 方案 A：在 NAS 上套一层 S3 网关（否决）

让 MinIO 一类的网关把现有目录暴露成 bucket，Toucan 侧只需补 `List` 与"外部对象"概念，
协议不变。

否决理由：

1. **可行性存疑。** MinIO 的 filesystem / gateway 后端模式在较新版本中已废弃。
   这条路当前是否还成立需要实测确认，不能作为方案基础。
2. **协议错配是本质的，不是形式的。** S3 协议是为"应用独占的存储"设计的，
   其对象是不可变的、由应用命名的。而本场景恰恰是**多方共享的目录**：
   File Browser 在翻、相册工具在扫、Toucan 在读，同一堆文件。
   文件系统是这几方唯一天然的公约数。
3. 套网关只是为迁就 Toucan 现有代码，属于用架构债换短期省事。

### 方案 B：新增"外部资源根"，直接读文件系统（采纳）

允许配置若干个只读的本地文件系统路径（NAS 上的挂载点）。

代价与收益：

- 代价：多一套存储后端要维护；`Profile.Data` 沙箱边界要被打开（见 §5）。
- 收益：不依赖任何网关；**并且使"把 Toucan 的 bucket 放到 NAS 上"这条路线变得
  不必要**——不需要 S3，直接读目录。

> 注意区分两件常被混为一谈的事：「Toucan 的 bucket 恰好放在 NAS 上」今天就能做，
> 零代码，但它对本需求毫无帮助——那些数据仍然是"因 Toucan 而生"的。
> 本方案解决的是"数据先于 Toucan 存在"。

## 3. 数据模型

### 独立表，不扩展 `AttachmentStorageType`

一个看起来更省事的做法是给 `AttachmentStorageType` 加第四个枚举值
（如 `EXTERNAL_ROOT`）并放宽 `MemoID` 为可空，这样 fileserver 代理、预览、
`MemoContent` 的内联渲染管线全部白拿。

**不采纳。** 理由不是语义洁癖，而是两个量级上的事实：

| 维度 | `attachment` | 外部资源 |
|---|---|---|
| 行数量级 | 与文档数同阶 | 单个相册目录即可达数万 |
| 生命周期 | Toucan 创建与销毁 | 完全不由 Toucan 控制，只能被动发现 |
| 删除语义 | 删行即删文件 | 删行**绝不能**触及文件 |

混表的后果是每一个现有附件查询都要背上一个过滤条件，且删除路径上多一个
"这行能不能真删"的分支——那是最不该出错的地方。

### 代价：渲染管线要接一次

独立表意味着 fileserver 的读取路由与前端的预览/内联渲染需要为新实体接一遍。
这是本方案已知的最大一笔重复工作，接受它换取上表中的隔离。

`TODO(确认)`：能否让新实体在**读取路径上**复用 `GetAttachmentBlob` 的分发结构
（共享字节流读取与 Content-Type 协商），只在存储层分叉，从而把重复限制在存储层。

### 稳定 id

引用锚定 Toucan 自发的稳定 id，不锚定路径。扫描时以
`(size, mtime, filename)` 三项全中做启发式匹配续接被移动的文件。

取舍已在需求文档中记录：误判代价是"引用断裂"而非"引用到错误文件"，
前者可见可修复，后者不可接受。三项全中使后者概率极低。

**被否决的替代**：用内容 hash 做身份。它能给出完全正确的移动检测，但要求全量读取
文件内容——TB 级数据下每次扫描的 I/O 成本不可接受，且在网络文件系统上尤其糟糕。

## 4. 扫描

`fsnotify` 在 NFS / SMB 挂载上不可靠（改动发生在 NAS 端，客户端内核收不到事件），
**实时监听整体排除**。

因此只有手动触发与定时扫描两种。增量判定使用 `path + mtime + size`，不读内容。

约束与假设：

- 假设 NAS 挂载点在扫描期间稳定可达。挂载丢失必须与"文件被删除"区分开——
  **根不可达时不得将其下的资源标记为消失**，否则一次网络抖动会清空整个索引。
  这是扫描器必须显式处理的失败模式。
- 假设单次扫描可能耗时数分钟。扫描需可中断、可续，且不阻塞正常请求。

## 5. 安全：打开 `Profile.Data` 沙箱

本方案风险最高的一处。允许配置任意路径后，`Profile.Data` 这条既有边界失效，
而这是一个可能面向公网的服务，做错即任意文件读取。

必须处理：路径规范化后再校验（先 `filepath.Clean` / 求绝对路径，再判断是否落在
已配置的根之内）、`..` 穿越、符号链接跟随（尤其是根内指向根外的链接）、
多个根之间的相互隔离。

**假设**：校验在**服务端**进行，且以规范化后的真实路径为准，不信任任何来自请求的
路径片段。前端的任何限制都只是体验，不是安全边界。

> 与既有决策的一致性：[ADR-0001](../adr/0001-attachment-proxy-not-presigned-url.md)
> 已确立"文件一律走服务端代理，不对外暴露可直连 URL"。外部资源沿用同一原则，
> 不因为文件在本地就走静态目录直出。

## 6. AI 标注

### EXIF 与模型推理分两级

EXIF（拍摄时间、GPS）是确定性的、无调用成本的，且是"回忆录 / Day of History"
类用法唯一必需的信息。模型生成的 caption 描述的是画面而非情境，对检索有增益，
但不是能力成立的前提。

因此 EXIF 提取与 AI 描述**分属不同阶段**，前者不依赖任何模型配置即可工作。

### 向量空间：不引入第二套

图文共享向量空间（CLIP 一类）可直接支持自然语言搜图与以图搜图，诱惑很大。

**首版不采用**，理由是它与当前文本 embedding 模型的向量空间不同，余弦相似度
不可混算；混入同一张表会得到无意义的排序结果，而分开存储则意味着一套并行的
向量表、索引与检索路径。

首版走 **图像 caption → 文本 embedding**，完整复用
[internal/rag](../../../internal/rag) 现有的嵌入、余弦排序与 FTS + 向量混合融合，
以及 [worker.go](../../../internal/rag/worker.go) 的后台索引调度。
新增检索基础设施为零。

以图搜图作为后续增强，届时单独评估是否值得为它引入第二张向量表。

### 幂等

AI 结果绑定稳定 id，只对新增或变更对象计算。用户编辑过的 tag / desc 与 AI 生成的
必须可区分，后续扫描不得覆盖前者。

## 7. 分阶段切风险

分阶段的依据是"每一阶段结束时都有一个可以证伪整体方案的判断点"。

### P0 —— 证伪"能不能读到"

外部资源根的配置、路径安全校验、扫描与独立表、EXIF 提取、以及 UI 上的
「测试该路径」。不含 AI，不含 view 集成。

**判断点**：在真实 NAS 上（standalone 与 Docker 各一次）配置一个数万文件的目录，
扫描能在可接受时间内完成，且 SQLite 的体积与查询延迟仍在
[sqlite-as-sole-datasource.md](../requirements/storage/sqlite-as-sole-datasource.md)
的容量边界内。**若此处不成立，整个方案应当中止**，而不是继续往上叠功能。

### P1 —— 证伪"找不找得到"

资源浏览页：列表、缩略图、按元数据检索、手工 tag 与 desc。仍不含 AI。

**判断点**：作者本人用两周。如果确实会回到这个页面找东西，方案成立；
如果扫完就再没打开过，则"个人数据流动性"这个假设本身不成立——此时省下的是
后面所有阶段。

### P2 —— AI 标注

caption 生成 → 文本 embedding → 复用 RAG 检索。含幂等与"人工编辑不被覆盖"。

### P3 —— view 集成

gallery view 的 scope 增加「外部资源根 + 过滤条件」。
「Day of History」在此阶段成为一个配置，而非一个功能。

### P4 —— 编辑器引用入口

插入媒体时的「从外部资源选择」。放在最后是因为它依赖前面所有层，且在
P1 之前它没有可选的东西。

## 8. 验收判据

- 在 Toucan 中对外部资源执行任何操作，**NAS 上的文件字节与元数据不发生任何变化**。
  这条要有测试守，不能只靠约定。
- 删除一条外部资源索引记录，对应文件仍然存在。
- 外部资源根不可达时，其下资源不被标记为消失；恢复可达后索引自动一致。
- 构造路径穿越与符号链接逃逸的请求，均被服务端拒绝。
- 在 File Browser 中移动一个目录后重新扫描，已有文档引用仍然有效。
- Docker 形态下按文档配置只读挂载，「测试该路径」能正确区分：路径不存在、
  权限不足、未挂载、目录为空。

---

## 9. 明确不做

- 不在 Toucan 内写文件（移动 / 重命名 / 删除）。
- 不搬运字节进 Toucan 的 bucket 或 data 目录。
- 不做 fsnotify 实时监听。
- 不做全量内容 hash 做身份。
- 首版不引入图文共享向量空间。

# 子域边界

本项目用 DDD 的**子域划分**管理"哪些能力是核心、哪些是外围"，不做插件系统，
取舍见 [ADR-0019](adr/0019-subdomain-boundaries-not-a-plugin-system.md)。
本篇是常青文档，描述**当前**的分类结果、边界规则与现实偏离，随系统变化原地改写。

## 一、分类

- **核心域（Core Domain）**——拿掉系统就不成立的部分，也是本项目区别于
  通用笔记应用的地方。质量要求最高，允许演化数据模型。
- **支撑子域（Supporting Subdomain）**——业务上需要，但不构成差异化。
  够用就停，不追求完备，不得改动核心数据模型。
- **通用子域（Generic Subdomain）**——谁做都一样的能力。**一律用现成的**，
  这一档不参与"核心/外围"的判断，只是一条别自己造轮子的提醒。

| 子域 | 归属 | 说明 |
|---|---|---|
| 层级知识库（workspace → 目录树 → 文档） | 核心 | 产品定位本身 |
| 文档内容模型与渲染（自定义块、sheets、加密块…） | 核心 | 所有能力的公共底座 |
| 权限与可见性（含"能否被匿名访问"） | 核心 | 不变量所在，不可拔 |
| 附件管理 | 核心 | 被文档、发布、相册共同依赖 |
| 相册 / 日历等视图 | 核心 | 知识库的表达形式，非外挂 |
| RAG 检索**底座**（写入路径 hook、索引） | 核心 | 拔掉会破坏写入链路 |
| 对外发布的**站点形态**（皮肤、导航、布局、主题 token） | 支撑 | 换一套不影响系统自洽 |
| AI Memory 类衍生内容生成 | 支撑 | 只消费核心的公开能力 |
| 导入导出、通知渠道 | 支撑 | 可替换、可缺席 |
| 认证、对象存储、邮件、定时任务 | 通用 | 用现成实现，不自研 |

两处**横跨边界**，必须把缝划在能力内部而不是整块归边：

- **对外发布**：「一篇文档能不能被匿名读到」是核心（属于权限模型）；
  「它长成什么样」是支撑。发布快照的存在与生命周期是核心，快照的呈现是支撑。
- **RAG**：索引与写入路径是核心，问答/搜索界面是支撑。

判定顺序（新能力按序问，第一个"是"即定档）：

1. 它要不要修改核心数据模型？要 → 核心（若答案应该是外围，则方案错了）。
2. 有没有别的能力依赖它？有 → 核心。
3. 拿掉它系统是否仍然自洽？自洽 → 支撑。

## 二、边界规则

**规则只有一条：依赖方向单向——外围可以依赖核心，核心不得知道外围存在。**

"知道"的判据比 import 宽：核心代码里出现外围的**名词**（类型名、接口方法名、
字段名、枚举值），即使不 import，也算越界。

由此派生两条可执行的约束：

- 核心的公共契约（`store.Driver`、核心 proto service、核心组件 props）
  只允许出现核心域的概念。
- 外围要让核心配合时，核心提供的是**中性的接缝**，不是针对某个外围功能的分支。

## 三、边界的三种长相

三种形态在本仓库都有实例，可以直接当标尺用。

### 正例：接缝（seam）

[PublicSiteRenderContext.tsx](../../web/src/components/MemoContent/PublicSiteRenderContext.tsx)
在核心渲染器里放了一个**可空的 context**：填了就按外链只读态渲染（tag 不可点、
站内链接重定基），不填就是知识库内的普通文档。核心不 import 任何 `BlogSite/`
的东西，外围通过 Provider 把自己的需要注入进来。

这是正确的形态：**核心只知道"存在这样一种渲染模式"，不知道是谁在用。**

瑕疵在命名——`PublicSite` 是外围的名词，出现在核心目录里。严格说该叫中性名字
（如"只读外链渲染模式"）。不影响正确性，但知道它为什么是瑕疵。

### 灰色：渗透

[store/driver.go](../../store/driver.go) 的 `Driver` 接口里直接列着
`CreateSite` / `ListSitePublications` 等十余个方法——外围的概念进了核心的存储
契约。它没有 bug，但**核心开始认识外围的名词了**，是渗透的典型长相。

现状不回滚（收益不抵改动风险），约束是**不再往这个接口里加新的外围方法**。
后续外围能力若需要持久化，走自己的 store 包，不扩核心 Driver。

### 危险：影子耦合

[web/src/components/GalleryView/types.ts](../../web/src/components/GalleryView/types.ts)
中 `parsePublicTags` 的注释写明它与 `BlogSite/blocks.ts` 的解析"互为镜像"，
两边读同一份存储 JSON。**不是 import，编译器看不见，但两边必须同步修改，
否则线上行为分叉。**

这类比显式依赖危险得多，因为重构时没有任何提示。唯一的解法是让那份约定有
**单一出处**——谁需要谁引用，而不是各抄一份。

## 四、边界如何影响需求

每篇需求文档标明所属子域。分类结果直接决定四件事：

| | 核心域 | 支撑子域 |
|---|---|---|
| 抽象 | 值得，会长期演化 | 别抽象，直写，先跑通 |
| 测试 | 完整覆盖，尤其是不变量 | 主路径即可 |
| 数据模型 | 可演化 | **不得修改** |
| 完成度 | 做透 | 够用就停 |

"数据模型"一行是唯一有硬约束力的一条，其余三条是资源分配的默认值。
这套划分最大的作用不是指导怎么做，而是**给"外围少做一点"提供一个不必反复
论证的理由**。

## 五、边界如何影响代码

新增能力时，落点按子域走：

| 关注点 | 核心域 | 支撑子域 |
|---|---|---|
| proto | 扩核心 service | 独立 service 文件 |
| 存储 | 可扩 `store.Driver` | 自带 store 包，不扩核心接口 |
| 迁移 | 正常写 | 正常写，但表只被自己读写 |
| 前端 | 可进 `components/` 公共层 | 独立目录，不被公共层引用 |
| 核心要配合 | 直接改 | 只能请求核心开一个**中性接缝** |

## 六、边界怎么守

**靠机器，不靠记性。** 两侧各有一个配置级手段：

- **Go**：`golangci-lint` 的 `depguard` 支持按文件路径配置 deny 规则，
  可表达"核心包不得 import 外围包"。当前 `.golangci.yaml` 未启用它。
- **前端**：Biome 2 的 `overrides[].includes` 配合 `noRestrictedImports`，
  可按目录限制 import 来源。当前 `web/biome.json` 未配置该规则。

两者都拦不住第三节的**影子耦合**——那是本方案的已知盲区，只能靠代码评审时
追问"这份约定的单一出处在哪"。
